## Known Limitations

- **Comment anchoring:** Programmatically created comments appear in "All Comments" but aren't visibly anchored to text in the UI
- **Resolved status:** May not persist in Google Docs UI (Drive API limitation)
- **editTableCell:** Not implemented (complex cell index calculation)
- **fixListFormatting:** Experimental, may not work reliably
- **ClickUp Docs search is entirely client-side:** `GET /api/v3/workspaces/{id}/docs` has **no text-search parameter and no sort parameter**, and `limit` defaults to **50** (max 100, min 10) with opaque `cursor`/`next_cursor` paging. `listDocs` and `searchDocs` hit the *same* endpoint — `listDocs` is just the unfiltered call — so matching, paging, and ordering all live in `ClickUpClient` (`matchesDocQuery`, `sortDocsNewestFirst`, `searchAllDocs`) and both the MCP tools and the REST handlers share them; do not re-add a per-caller filter. `searchDocs` **auto-pages** the whole workspace (cap `DOCS_MAX_PAGES = 20` → 2000 docs) then sorts newest-first, and **always reports the scan extent** — a bare "No docs found" reads as "that doc doesn't exist" and is the bug this replaced (ticket 86cb5r680). Title matching is **token-AND, not substring**: every whitespace-separated word must appear, in any order, because titles are punctuation-heavy (`"AWESOME Sync"` must match `[AWESOME] Sync - 08/15/2026`). `parentType: 'EVERYTHING'` is **dropped rather than forwarded** — ClickUp accepts it but matches nothing, whereas omitting the filter returns the whole workspace; `SPACE`/`FOLDER`/`LIST` require `parentId` (Zod-enforced). `request()` has no 429 backoff, so a mid-scan rate limit returns partial results flagged `rateLimited` instead of throwing away the pages already fetched. Note `createDoc.parentType` is a **different** parameter (numeric 4/5/6 in the POST body) — do not unify it with `searchDocs.parentType`.
- **ClickUp Doc images are self-hosted:** ClickUp has no image-upload API for Docs, and its SPA `/v1/attachment` route needs a browser session JWT this server doesn't have (ClickUp auth here is a per-user OAuth token). So `insertImageIntoPage`/`uploadClickUpDocImage` re-host the image themselves: fetch a public image URL (SSRF-guarded, 20 MB cap), store the bytes in Postgres (`clickup_doc_images`, `src/clickup/docImageStore.ts`), and embed `![](BASE_URL/images/clickup-doc/<id>)` via the existing markdown `editPage`. The serve route (`registerClickUpDocImageRoutes` in `webServer.ts`) is public/unauthenticated (ClickUp's renderer must fetch it; ids are unguessable UUIDs). Requires `DATABASE_URL` + `BASE_URL`; without Postgres the tools return a clear error. Input is a remote URL only (no base64 yet). **These images must never be stored `ephemeral`:** ClickUp's renderer re-fetches the URL on every page view, so an expiring blob would 404 the day it lapses — retention in `image_blobs` is opt-in per call site precisely so a global TTL can't break this path.
- **Re-parenting a ClickUp task goes through `updateTask.parentTaskId`, and the wrapper is most of the feature:** ClickUp's `PUT /task/{id}` has always accepted `parent`, and `ClickUpClient.updateTask` has always declared it — it was simply never populated, and FastMCP's `additionalProperties: false` meant an LLM could not pass it at all, so restructuring a hierarchy meant recreating tasks and losing their comments, history and custom fields (ticket 1245xawcebz). `parentTaskId` is **`.nullable()` and deliberately not `.min(1)`**: a Zod-level rejection surfaces as FastMCP's generic `InvalidParams` ("Expected string, received null"), which is the unexplained failure the parameter exists to replace — letting `null`, `''` and self-reference reach the body is what buys one clear voice for all of them. **ClickUp cannot clear a parent**, so null is refused rather than sent: a subtask can be moved between parents but never promoted back to top level. The re-parent path costs **three calls; a plain update still costs exactly one** and returns the byte-identical string it always did (there is a test on that). The **pre-flight `getTask(parent)` is the only source of the parent's name** — ClickUp's payload carries `parent` as a bare ID and no name anywhere — and it also yields the parent's list and turns an unknown ID into a message naming it instead of the raw 400 body `request()` would surface (it has no 400/404 special-casing). It is a **hard gate because nothing has been mutated yet**; the post-write re-read is the opposite, **best-effort**, because failing a move that did happen is worse than not confirming it. The re-read exists because **a stale PUT echo would let a silent no-op read as success** — the exact bug the ticket is about — so a mismatch is reported as `⚠ Re-parent did NOT take effect`, never as "updated successfully". The cycle check only sees the candidate's immediate parent and its root, so **a deeper cycle still relies on ClickUp's own rejection** (wrapped with the parent's name and list). The PUT is **atomic**, so a rejected parent loses the other fields in the same call — hence the tool description telling the model to re-parent standalone. **ClickUp emits no webhook event for a parent change at all** (`taskMoved` is a LIST move), so `getTaskEventHistory` can never show one and an empty result there never means "nothing was re-parented"; do **not** synthesise a row for it — it would capture only moves made through this MCP, leaving a ClickUp-UI drag invisible, so the history would be partial in a way that reads as complete (and `ClickUpTaskEvent` requires a `subscriptionId` FK a user without a subscription does not have). `formatTask` renders `Parent:`/`Top-level parent:` for **all five** task tools and the REST `Accept: text/plain` twin from one place; `Top-level parent` is suppressed when it merely repeats `parent` or the task's own id, so it only appears when nesting is deeper than one level. Finally, the uncatalogued **`PATCH /api/v1/clickup/tasks/:taskId` forwards `parent` raw and bypasses every guard above — on purpose**: those guards are error-message quality for an LLM, not integrity checks (ClickUp itself rejects null parents and cycles), and that route's caller is a dashboard API key holder. **Cross-list parents: unverified.** The tool reports the parent's list and the task's list after the move rather than asserting a rule; fold the observed answer into this bullet and the tool description once a real cross-list move has been run.
- **Email sign-up is verify-first — the account does not exist until the link is clicked:** `POST /api/auth/register` creates **nothing** in `users`. It bcrypt-hashes the password, parks it in `pendingRegistrationStore.ts` (Redis `pending_registration:<sha256(token)>`, 24h TTL, memory fallback bounded at 10k with oldest-first eviction), and mails a link; `GET /auth/verify?token=…` is **inert** — it only serves `public/verify.html`; the `POST /auth/verify` that page submits is what calls `createPasswordUser` and opens the session. **That split is load-bearing, not ceremony:** when a single GET both consumed the token and created the account, a mail scanner following the link (Outlook SafeLinks and friends do) completed the sign-up on the recipient's behalf and burned their link, so the human then clicked it and was told it was invalid. Single-use does *not* prevent that on its own — it only stops a second account — which is why the redemption had to move to a request a prefetch will not make. Consequences worth knowing: **the token is stored only as a SHA-256** (it is a bearer credential that can bring an account into existence, so a Redis dump must not yield a usable one — no work factor needed, the input is 32 CSPRNG bytes); it is **single-use, deleted before the record is returned**, so one link can never create two accounts; and unknown/used/expired all answer the **same** `/login?verify=invalid`, because distinguishing them tells a probe which tokens once existed. `/auth/verify` sets `Referrer-Policy: no-referrer` — the token rides in the query string and would otherwise leak in the Referer of anything the next page loads. **Registration answers 202 identically whether or not the address is taken** (`REGISTRATION_ACCEPTED`), replacing the old 409: the owner of a taken address gets a "someone tried to sign up" mail carrying **no link**, and the password is hashed on *both* paths so the ~190ms bcrypt cost cannot be used as a timing oracle for what the identical body refuses to say. Two sign-ups for one address mint two valid tokens (nothing exists yet to reject the second); whichever link is clicked first wins and the other gets `?verify=exists` — `DuplicateEmailError` is caught rather than 500ing, and the loser is **not** signed in, since that request never proved its password. **Mail goes through Resend over plain `fetch`** (`mailer.ts`, no new dependency; `RESEND_API_KEY` + `MAIL_FROM`). Without a key: outside production the message body — including the link — is logged so local sign-up works with no provider; in production `register` throws `MailNotConfiguredError` → **503, nothing created**, because reporting "check your email" for a mail that was never sent strands the user. `isMailConfigured()` requires **`MAIL_FROM` as well as the key in production** — the fallback sender is Resend's sandbox address, so a key-only deployment would otherwise pass preflight, build pending state, and fail at the provider (or send from an identity nobody chose). **Pending records are cleaned up when we fail, not when the user does:** an undelivered link's record is deleted (it is unreachable — the token existed only inside that request), and a redemption that fails for a non-duplicate reason *restores* the record, so a database outage does not spend a valid link. A `DuplicateEmailError` keeps it consumed, since an account now exists. Registration logs one **branch-independent line with no address**, so the logs cannot answer what the identical 202 refuses to. The per-email rate-limit bucket is what stops this endpoint being used to mail-bomb an arbitrary address.
- **`HIDE_GOOGLE_SIGNIN=true` hides the Google button, but never the route:** the `<!-- google-signin:start/end -->` block in `public/login.html` and `public/dashboard.html` is stripped **server-side** by `sendSigninPage` (`webServer.ts`), so the button never reaches the browser and cannot flash before a script removes it — which is why `/login` and `/dashboard` are read-and-sent rather than `sendFile`d. **`GET /auth/google` stays live on purpose:** a Google-created account has `password_hash` NULL, so the email form cannot sign it in (`verifyPassword` against a null hash is always false) and there is no password reset, so removing the route would strand every such account with no way back in. The flag is presentation only, defaults to showing the button, and is reported at `/api/config` as `googleSigninHidden`. The dashboard overlay's focus call falls back to the email link (`'.btn-google-login, .login-alt a'`) so hiding the button does not leave focus nowhere. Note `public/index.html`'s marketing copy still mentions signing in with Google — it is not behind the flag.
- **Dashboard login is Google OAuth *or* email+password:** `/login` serves `public/login.html` (both methods side by side) — it used to 302 straight to `/auth/google`, which is why `/connect/:mcpSlug`'s park-and-login now also targets `/login`. `POST /api/auth/register` + `POST /api/auth/login` (`webServer.ts`) back the email path; hashing lives in `src/auth/password.ts` (bcrypt cost 12). **Passwords over 72 bytes are rejected, not truncated** — bcrypt silently discards past that, so accepting them would claim a passphrase protects the account when only its first 72 bytes do. Login runs `verifyPassword` **unconditionally**, including for unknown emails and Google-only accounts (hash `null` → compared against a dummy hash of the same cost), so response time is not an account-existence oracle; registration no longer answers 409 at all — it returns the same 202 either way and mails the owner instead (see the verify-first entry above), so neither endpoint is an existence oracle. `src/website/loginRateLimit.ts` caps attempts per **IP and per email** (8 / 15 min, Redis-backed, in-memory fallback that is per-process); it counts **every** attempt, not just failures — counting failures alone lets one valid login reset the window — and the **email bucket is the load-bearing half**, since `trust proxy: true` makes `req.ip` spoofable via `X-Forwarded-For`. **The load-bearing change is that sessions are keyed by `userId`, not `googleId`:** ~13 dashboard routes did `getUserByGoogleId(req.session.googleId)` inline, which 401s for an account whose `google_id` is NULL, so all of them now go through `resolveSessionUser` (userId first, googleId fallback so pre-existing sessions survive their 7-day TTL). The `/connect/:mcpSlug` OAuth state carries `userId` for the same reason — without it a password user consents at the provider and gets "User not found" on the way back. `regenerateApiKey(googleId)` was **deleted rather than kept**: its `WHERE google_id = $1` matched zero rows for these accounts and reported "user not found" on a valid one; `regenerateApiKeyByUserId` is the only version. Linking Google to an existing password account (same email) **updates that row and keeps the password + `auth_method='password'`** — both the DB `ON CONFLICT (email)` path and its file-store sibling — because the dashboard renders `authMethod` verbatim and relabelling would announce the loss of a credential that still works. `password_hash` is deliberately absent from `DB_USER_COLUMNS` and from `UserProfile`, so nothing that serializes a user can leak a hash it never selected. **There is still no password reset**, but the blocker is gone: `mailer.ts` + `authEmails.ts` now exist, so a reset is a token store and two routes away rather than a mail-provider decision. Until then a forgotten password has no self-service path.
- **HubSpot auth is OAuth 2.0 by default:** the catalog always advertises the OAuth endpoints, so the dashboard always shows "Connect with HubSpot" (the paste-token form is not shown). The client_id/secret come from `HUBSPOT_CLIENT_ID`/`HUBSPOT_CLIENT_SECRET` (a registered HubSpot app) and MUST be set on both the web service and the hubspot MCP service, or the connect flow has no client and fails. OAuth access tokens expire (~30 min) and are refreshed at tool-call time via `maybeRefreshHubSpotToken`. The paste-token path (`connectToken.ts`, the `/api/connect-token` hubspot branch) still exists server-side as an API-level escape hatch and skips refresh, but the dashboard no longer surfaces it.
- **HubSpot `searchData` not registered:** the reference's 16th tool did semantic search over a local FAISS vector index; this codebase has no vector store, so the tool is intentionally omitted rather than advertised as a throwing stub. The 29 registered HubSpot tools are implemented against the official HubSpot REST API. (`searchCompanies`/`searchContacts` cover the CRM search endpoint — the free-text/property lookup the omitted FAISS tool was reaching for.)
- **`getDeal` needs an ID only `getCompanyDeals`/`searchDeals` can produce:** a company record carries `num_associated_deals` — a plain **company** property, no deals scope — so a caller could see *that* a company had deals while having no route to their IDs. `getCompanyActivity` reads `/associations/engagements` (notes/calls/meetings, never deals) and `getActiveDeals` is a global recent-N with no company filter, so "show me this company's deals" dead-ended and the model reported it as **a permissions problem it was not**. `getCompanyDeals` closes it: associations v4 for the IDs, then `readDealsByIds` for the records. **Both sides page, at different sizes, and neither may truncate silently** — the association read follows `paging.next.after` 500 at a time (bounded at `ASSOCIATION_MAX_PAGES` = 10, i.e. 5,000 IDs) while the batch read chunks at HubSpot's **100-input cap**. Hitting the page bound returns `truncated`, which the op renders as "of N**+**": a bounded scan is a floor, not a count, and a truncated "Found 25 deals" would read as the company's whole pipeline. `searchDeals` is the by-name route, and widening `opSearchObjects` to a third label is why deals now share one search implementation with companies/contacts. **Do not diagnose a deal failure as missing scopes when other deal tools work:** `getActiveDeals` (`POST /crm/v3/objects/deals/search`) and `getDeal` (`GET /crm/v3/objects/deals/{id}`) gate on the *same* `crm.objects.deals.read`, so no scope grants one and denies the other.
- **HubSpot deals need the deals scopes + a reconnect:** deal tools (`getActiveDeals`, `getDeal`, `searchDeals`, `getCompanyDeals`, `createDeal`, `updateDeal`, `listPipelines`) and deal support in `getProperty`/`createProperty`/`updateProperty` require the `crm.objects.deals.*` + `crm.schemas.deals.*` scopes now in the catalog seed (`mcpCatalogStore.ts`). `seedDefaultCatalogs` re-seeds on boot and the upsert overwrites `oauth_scopes`, so the *catalog* is current after any deploy — but a **token is frozen at the scopes it was minted with**, so **already-connected users must reconnect/re-consent** before deal calls work; until then they 403. HubSpot tokens never expire in a way the dashboard flags, so such a connection looks perfectly healthy while failing every deal call — which is why the 403 is no longer reported as a bare "check your scopes". `parseHubSpotMissingScopes` (`hubspot/apiHelpers.ts`) detects it (`category`/`errorType` = `MISSING_SCOPES`, scope list from `context.requiredScopes` *or* the prose `requires any of [...]` — HubSpot sends one or the other, not both), and `withHubSpotClient` then spends one round-trip on `fetchHubSpotGrantedScopes` (`GET /oauth/v1/access-tokens/{token}`) so the message names **needed *and* granted** and points at the dashboard's Reconnect button — the Slack `formatScopeDetail` contract. Granted is the load-bearing half: it is the only way to tell *"the reconnect never happened"* from *"it happened and still didn't grant it"*, and in the latter case the message **stops telling the user to reconnect** (the HubSpot app config or the portal is the problem, not consent). The lookup is best-effort — a failed lookup degrades to the needed-only message, never to a second error. `listPipelines` returns each pipeline with its ordered stages (covering both list-pipelines and list-stages); use it to resolve `dealstage` IDs to names.
- **HubSpot engagement writes (`createNote`/`createTask`/`logCall`/`logMeeting`):** create the engagement standalone then attach it via a v4 **default** association (`PUT /crm/v4/objects/{type}/{id}/associations/default/{toType}/{toId}`), avoiding the direction-sensitive association-type-ID table. `hs_timestamp` defaults to now when omitted (the #1 documented create failure). `deleteEngagement(engagementType, engagementId)` is the cleanup counterpart — HubSpot's DELETE archives the engagement (off every timeline, recoverable from the recycling bin), which is what makes the create tools safely testable against a real portal; it needs the same contacts scopes as the writes. Success only claims a timeline attachment once the association call returns 2xx; a failed association is reported as an orphaned engagement, not a silent success. **Scopes:** these need no extra scope — HubSpot documents the notes, tasks, calls, and meetings APIs as requiring `crm.objects.contacts.read` + `crm.objects.contacts.write`, both already in the catalog seed. **Do not add `crm.objects.{notes,tasks,calls,meetings}.*`**: no such scope exists in HubSpot's public scope list, and an unknown scope makes the entire consent flow fail (every HubSpot connection, not just these tools). If an engagement write 401/403s, inspect the scopes actually granted on the token (`GET /oauth/v1/access-tokens/{token}`) instead of guessing a scope string.
- **HubSpot read/write contract:** reads that request explicit `properties` flag unknown keys HubSpot silently drops (`getCompany`/`getContact`, and `searchCompanies`/`searchContacts` via `formatObjectList`, which renders every requested property — unset ones as `(empty)` — and appends a ⚠ note listing keys HubSpot never returned, so "no value on this record" is never confused with "the tool doesn't return that"); `updateCompany`/`updateContact` re-read the record after PATCH so the response matches a fresh read (HubSpot's PATCH echo omits populated fields); `getCompanyActivity` emits ISO-8601 (engagement timestamps are epoch millis upstream). `getTickets` filters datetime props (`closedate`/`hs_lastmodifieddate`) with **epoch millis** — the search API 400s on ISO. Empty `{}` update payloads are rejected by the Zod schema before any API call. Email bodies in `getCompanyActivity` need the `sales-email-read` scope (in the OAuth scope list).
- **Slack files need `files:read` + a reconnect:** attachments are surfaced as `📎 <name> — <mime>, <size> — file ID: F…` lines under each message (`formatFileRef`/`formatFiles` in `src/slack/helpers.ts`, reached through `formatMessage`, so both the bot and user servers get it from one place), and `downloadFile(fileId, channelId, format)` retrieves the content. `files:read` is in the OAuth scope seed and the dashboard's bot-scope copy, but **already-connected users must reconnect/re-consent** — without it Slack returns file stubs with `file_access: 'check_file_info'` (rendered as "file hidden") and `files.info` 403s. **Formats:** `url` (default) re-hosts images through `store()` (`src/images/imageBlobStore.ts`) and returns a `/images/<hash>.webp` link — that link is **public and unauthenticated**, so a screenshot from a private DM becomes publicly fetchable at an unguessable URL — which is why Slack stores it as **ephemeral** (`store(..., { ephemeral: true })`), making it eligible for removal after `IMAGE_RETENTION_DAYS` (default 30, `0` disables) so exposure is bounded rather than permanent. **That is a ceiling, not a guarantee:** blobs are content-addressed, so if the same bytes are also stored for a permanent use (a ClickUp Doc image) the shared row is promoted to permanent and the Slack URL keeps working — `fetch()` enforces expiry at read time so a lapsed row is never served, but a *shared* row simply hasn't lapsed; this is what makes `insertImageFromUrl` work (Google fetches it server-side), and it needs `DATABASE_URL` + `IMAGE_PUBLIC_BASE_URL`. `inline` returns a FastMCP `imageContent` block instead (capped at 1.5 MB, no image host needed) — the **only** tool in this repo that returns anything but a string. Text-like files come back as text; other types return metadata + permalink rather than an error. **Security:** `src/slack/fileDownload.ts` attaches the bearer token **per redirect hop and only for `*.slack.com`**, so Slack's redirect to signed S3 URLs can't leak the workspace token; a token missing `files:read` gets `200 OK` with an **HTML sign-in page** (not a 401), which is rejected explicitly so a login page is never stored as a screenshot. `downloadFile` requires `channelId` and verifies the file is really shared there (`fileShareTargets` unions `channels`/`groups`/`ims` **and** the newer `shares.public`/`shares.private` maps) — on the user server `enforceAccess` runs first, and the share check is what stops a file in a denied channel being laundered through an allowed one.
- **`listChannels` surfaces org-blocked channels rather than hiding them — and says when it could not check:** a channel blocked *only* by the organisation rule is listed with a `⚠ Not readable: shared with <Org Name> (ID)` warning, so the user can see which org to tick instead of watching the channel vanish. This is guarded by `passesNonOrgRules`: the row is surfaced **only if the user's own whitelist/blacklist/public-only rules would have allowed it**, otherwise a channel their patterns exclude would leak into the output on an org technicality. It applies on **both** paths now — previously only `verifyBackfilledChannel` (the org-unknown path) flagged, while a channel whose `shared_team_ids` were already in the `conversations.list` payload was silently dropped, which is exactly what made the tool description's promise false and made the two paths blame different rules (`whitelist-empty` vs `org-not-allowed`) for the same channel. Shared channels past `CHANNEL_INFO_BACKFILL_MAX` (25) are now marked `caution` (`⚠ Organisation unverified`) instead of rendering as ordinary readable rows — the trailing note alone was too easy to miss, and an agent planned work against channels every read then refused. **`warning` and `caution` are deliberately different:** `warning` means *we know this is blocked* and withholds topic/purpose; `caution` means *we could not check*, so nothing has denied it and its free text stays. The summary counts all three buckets separately.
- **Slack search is user-token-only and post-filtered:** `searchMessages`/`searchFiles` are registered on the **slack-user** server alone — `search.messages`/`search.files` reject bot tokens with `not_allowed_token_type`, so there is deliberately no stub on `slack-bot` (same reasoning as the omitted HubSpot `searchData`). They need **`search:read`**, added to the OAuth seed in `mcpCatalogStore.ts`, so **already-connected users must reconnect/re-consent** — which the dashboard only started allowing once `renderInstanceRow` grew a `showReauthorize` branch: `needsReconnect()` returns false for every non-Google provider (their tokens never expire), so a Slack row rendered *Copy URL* and no Reconnect button at all, and the tools' "reconnect from the dashboard" instruction pointed at an affordance that did not exist. Scope changes, not expiry, are what make re-consent necessary for these providers. Until they do, `callSearch` rewrites Slack's `missing_scope` into a "reconnect from the dashboard" message — carrying through Slack's own `needed`/`provided` fields (`formatScopeDetail` in `apiHelpers.ts`), because `provided` is the authoritative list of what the stored token actually holds and is the only way to tell a reconnect that never happened from one that happened and still didn't grant the scope. **Access control is the subtle part:** `enforceAccess` can't run (it takes one `channelId`; a search has none), and Slack's query DSL has no channel deny-list, so results are over-fetched and dropped client-side — `buildChannelFilter` (`src/slack-user/server.ts`) runs `fetchChannelMeta` + `assertAccess` + `assertDmMemberAccess` per distinct channel — the DM/group-DM check matters because without it a result from a DM with a non-allowed org, or a group DM holding a blacklisted member, would pass a filter a direct read rejects — memoised per call on top of the 5-minute meta cache, and **fails closed** on any error. A file is shown if *any* channel it's shared into is allowed. Because filtering happens after Slack pages, **page numbers are Slack's, not the filtered list's** — a page can come back empty while more matches exist, and the response says so plus how many results the rules hid (a silent drop would read as "Slack found nothing"). `search.*` pages by `page`/`count`, **not** by `cursor` like every other Slack call here. No REST sibling: the REST plane is hard-gated on `slackBotToken` precisely because access rules can't be applied there.
- **Slack list/read parity is one rule engine with one deliberate seam:** `listChannels` used to run a *second*, hand-written copy of the access rules that skipped the org check whenever `conversations.list` returned no team IDs — so a Slack Connect channel was advertised as available and then failed every read with an opaque team ID. `filterChannelList` is now a thin wrapper over `classifyChannelList`, which calls the same `assertAccess` a read calls; keep it that way. The one surviving difference is intentional and tested: a shared channel whose *list* payload names no org is `needsOrgBackfill`, not denied — "unknown" is not "denied", and resolving it costs a `conversations.info`. `listChannels` spends that call for up to `CHANNEL_INFO_BACKFILL_MAX` (25) channels, which is half the tier-3 minute budget because the same handler already pays for DM and group-DM member lookups; channels past the cap are reported, never silently unchecked. **`assertAccess` checks orgs before channel patterns**, so an org denial says nothing about whether the whitelist would have allowed it — anything that treats an org denial specially must call `assertNonOrgAccess` first, or a channel the user's own whitelist excludes leaks out on an org technicality. Denials are typed (`SlackAccessDenied`, with `reason`/`orgIds`/`patterns`) so the message text is no longer the API; the text itself is unchanged so callers that only print it are unaffected. Org-denied rows are **listed but flagged** (with `topic`/`purpose` withheld — structural facts about a channel the rules refuse to read are fine, its free text is not); rows denied by the user's own channel patterns are **hidden but counted**, because listing them would dump the names of channels they deliberately excluded. `diagnoseChannelAccess` is the generic answer to "why can't I see #x" — it was chosen over hardcoding an exemption for the support channel, which would have been spoofable by any workspace creating a channel with that name. Error messages name the org via `resolveTeamNames` (`src/slack-user/teamNames.ts`), whose cache is **keyed by token and bypassed entirely without one**: whether `team.info` succeeds depends on the calling token, so a bare team-ID key would serve one tenant's names to another. Expect the name to be missing — `team.info` on a foreign org usually fails even with `team:read`, and every org in a denial is by definition foreign — which is why the raw `T0…` ID is always kept alongside it: that ID is what the dashboard's Organizations checkbox is labelled with, and matching the two is how the user actually applies the fix.
- **Google Docs text is sanitised before it reaches the transport:** `src/google-docs/textSafety.ts` is on every `readGoogleDoc` return path, `parseDocStructure`'s `textPreview`, and the REST twin at `/api/v1/docs/:documentId`. Three defects lived here. (1) `format: 'json'` sliced *already-serialised* JSON and returned the fragment, so anything that parsed it failed with `EOF while parsing a string` — a truncation bug that reads exactly like a transport bug; the partial now travels as a **string field inside a valid envelope**, the same contract `truncateJsonByLength` uses for REST. (2) Every truncation used `substring`, which cuts on UTF-16 code units and leaves a lone surrogate when it lands inside a surrogate pair — use `sliceSafe`, never `substring`, on anything headed for a tool result. (3) `textRun.content` was copied verbatim, including the `U+000B` Docs emits for shift-enter soft breaks (converted to `\n`, **not dropped** — it is a real line break) and the private-use chars it uses as inline-object placeholders. `assertTransportSafe` is the backstop: after sanitising it should never fire, and that is the point — if anything ever reaches the wire unencodable, the caller gets an error naming the offset and code point instead of a JSON parse failure inside their client, which is undiagnosable from the outside. Also note `format: 'text'` **used to drop all table text**: its `fields` projection named only paragraphs, so the table-walking branch was dead code; the projection now names tables too.

- **Slack channel events are a store you poll, not a push:** `subscribeToChannelEvents`/`listChannelEventSubscriptions`/`getChannelEventHistory`/`debugChannelEventSubscription`/`unsubscribeFromChannelEvents` (slack-user only) mirror the ClickUp task-event quartet, including its delivery model — the webhook writes rows and the caller asks later. **Nothing in this repo pushes to an LLM session**; what this removes is paging a channel and keeping your own watermark. **Slack has no per-user subscription API:** event delivery is configured once on the app (Request URL + `SLACK_SIGNING_SECRET`, both operator-set), so subscribing makes *no Slack call* — it inserts a local interest filter. Unlike ClickUp, `[slack-ingest]` log lines **never include message text** — envelope shape only, since a private DM's body has no business in stderr. Because stderr is invisible to an MCP tool, every delivery also leaves a durable breadcrumb in **`slack_ingest_health`** (`recordIngestDelivery`/`readIngestHealth`): one row **per outcome branch**, not append-only, because the ingest URL is public and unauthenticated — keying by branch bounds the table at ~13 rows forever and needs no pruner. `debugChannelEventSubscription` reads it back, which is the only thing that separates *"Slack has never POSTed here"* (Request URL unset/wrong) from *"handshake only"* (no event types enabled on the app) from *"rejected"* (signing-secret mismatch) from *"delivered but unmatched"* (wrong channel, or `matchPattern` filtered it). The health write is **best-effort and never changes the status Slack sees** — a non-2xx to protect a diagnostic counter would disable the workspace's Request URL, which is exactly backwards.

- **PeopleForce probation + the `status` filter (verified live 2026-08-18):** `probation_ends_on` is a **first-class, HR-set date** on the employee record — report it, never derive it from `hired_on` + 90 days (observed spans run 3 to 17 months, and it is extendable). Both `formatEmployee` and `formatEmployeeList` render it plus a **derived** `Probation:` state via `probationStatus()`. The 4-row result seen at probe time fit one page only because that tenant had 4 people on probation. - **Redmine is self-hosted, so the instance URL is per-connection data — not an env default:** every other connector here falls back `providerTokens.baseUrl → process.env.X_BASE_URL → a public default`; Redmine **drops the third term**, because there is no `api.redmine.com` and guessing a host would send the credential somewhere the user never named. `getRedmineClient` therefore throws on a missing base URL rather than papering over it, the dashboard's URL field is mandatory (the `isOutline || isRedmine` gate in `connectWithToken`), and the connect route is shaped like **Outline's**, not like the two-line `connectPasteToken` helper peopleforce/hubspot share — that helper stores only `{ access_token }`, which would produce a connection no tool can use. The URL is attacker-controllable input we send a credential to, so it runs through `checkBaseUrl` (`src/util/baseUrlGuard.ts`, hoisted out of `outline/connectToken.ts` so the two connectors cannot drift); there is still **no DNS-rebinding defence**, same documented gap as Outline.
- **Redmine auth is dual-mode, and the mode is inferred from the stored refresh token:** a pasted personal API key goes in `X-Redmine-API-Key` and works on every Redmine; an OAuth 2.0 access token goes in `Authorization: Bearer` and exists **only on Redmine 6.1+** (the Doorkeeper provider, feature #24808). Nothing stores the mode — `getRedmineClient` reads `session.redmineRefreshToken` and picks the header, and **`connectionHealth.ts` must pass the matching `authMode`**, or a perfectly healthy OAuth connection is re-probed as an API key and reported as a bad credential. The catalog is **env-gated like Outline**: `REDMINE_CLIENT_ID` + `REDMINE_CLIENT_SECRET` + `REDMINE_BASE_URL` turn on "Connect with Redmine", and without them the dashboard falls back to the paste form. That fallback is load-bearing, not garnish: the OAuth *application* is registered per instance at `<base>/oauth/applications` **by an administrator**, so one `client_id` serves exactly one Redmine — every other instance, and everything older than 6.1, can only paste a key. Doorkeeper expires access tokens (~2h) **and rotates the refresh token on use**, so `performRedmineRefresh` persists whatever comes back; keeping the old refresh token after a rotation is what silently kills the connection on the call after next.
- **Redmine OAuth scopes are permission names, and are not a security boundary:** the scope strings are Redmine's own permissions (`view_issues`, `add_issues`, …) plus `admin`, not OAuth-style verbs, and they must exist on the instance *and* be ticked on the registered application or the authorize request errors instead of rendering a consent screen. More importantly, Redmine defect **#44271** reports that issue edit, notes and delete are authorised from the resource owner's roles alone — Doorkeeper's `oauth_scope` filter does not apply on those paths — so a narrowly-scoped token can still write. Do not rely on the scope list to prevent a mutation.
- **A Redmine 401 and a Redmine 403 mean opposite things:** `403` means an administrator has the REST API switched **off** (`Administration → Settings → API → Enable REST API`) and the key is irrelevant; `401` means the credential itself was rejected. Redmine only split these in **4.1.0** (defect #30086) — before that a disabled REST API also answered 401, byte-identical to a bad key — so the 401 text names **both** causes. `validateRedmineToken` passes a *function* as `rejectedMessage` (the shared `validatePasteToken` accepts `string | (status) => string` for exactly this) rather than one message for both. - **Most of the Redmine API is officially Alpha, and lists cap at 100:** Redmine marks only **Issues, Projects, Users, Time Entries and News** as Stable; Attachments are Beta, and Wiki, Versions, Memberships, Relations, Categories, Enumerations, Custom Fields and Search are all **Alpha** and may change between releases — roughly 20 of the 46 tools sit on Alpha endpoints. - **Redmine deletes are permanent and `deleteProject` cascades:** there is no recycle bin for any Redmine delete. `deleteProject` destroys every issue, wiki page, version and time entry in the project *and its subprojects*; `archiveProject` is the reversible option and the tool description says so. - **Two Redmine guards that are easy to undo by accident:** (1) `RedmineClient.request` sets `redirect: 'error'`. Node's fetch strips `Authorization` across an origin change but **keeps custom headers**, so following a redirect would hand `X-Redmine-API-Key` to the `Location` host; `validatePasteToken` takes the same stance at connect time, which is also why a redirecting base URL never gets stored. (2) `checkBaseUrl` now requires **https://** by default (`requireHttps`), because every caller goes on to send a credential to that URL. - **Redmine's session cache identity is the token AND the base URL AND the auth mode**, not the token alone. ## Parameter Patterns

- **Document ID:** Extract from URL: `docs.google.com/document/d/DOCUMENT_ID/edit`
- **Text targeting:** Use `textToFind` + `matchInstance` OR `startIndex`/`endIndex`
- **Colors:** Hex format `#RRGGBB` or `#RGB`
- **Alignment:** `START`, `END`, `CENTER`, `JUSTIFIED` (not LEFT/RIGHT)
- **Indices:** 1-based, ranges are [start, end)
- **Tabs:** Optional `tabId` parameter (defaults to first tab)
