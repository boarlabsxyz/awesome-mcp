## Known Limitations

- **Comment anchoring:** Programmatically created comments appear in "All Comments" but aren't visibly anchored to text in the UI
- **Resolved status:** May not persist in Google Docs UI (Drive API limitation)
- **editTableCell:** Not implemented (complex cell index calculation)
- **fixListFormatting:** Experimental, may not work reliably
- **ClickUp Docs search is entirely client-side:** `GET /api/v3/workspaces/{id}/docs` has **no text-search parameter and no sort parameter**, and `limit` defaults to **50** (max 100, min 10) with opaque `cursor`/`next_cursor` paging. `listDocs` and `searchDocs` hit the *same* endpoint — `listDocs` is just the unfiltered call — so matching, paging, and ordering all live in `ClickUpClient` (`matchesDocQuery`, `sortDocsNewestFirst`, `searchAllDocs`) and both the MCP tools and the REST handlers share them; do not re-add a per-caller filter. `searchDocs` **auto-pages** the whole workspace (cap `DOCS_MAX_PAGES = 20` → 2000 docs) then sorts newest-first, and **always reports the scan extent** — a bare "No docs found" reads as "that doc doesn't exist" and is the bug this replaced (ticket 86cb5r680). Title matching is **token-AND, not substring**: every whitespace-separated word must appear, in any order, because titles are punctuation-heavy (`"AWESOME Sync"` must match `[AWESOME] Sync - 08/15/2026`). `parentType: 'EVERYTHING'` is **dropped rather than forwarded** — ClickUp accepts it but matches nothing, whereas omitting the filter returns the whole workspace; `SPACE`/`FOLDER`/`LIST` require `parentId` (Zod-enforced). `request()` has no 429 backoff, so a mid-scan rate limit returns partial results flagged `rateLimited` instead of throwing away the pages already fetched. Note `createDoc.parentType` is a **different** parameter (numeric 4/5/6 in the POST body) — do not unify it with `searchDocs.parentType`.
- **ClickUp returns the 25 newest task comments and NOTHING that says so, so `getTaskComments` pages to the end (ticket 1245xaweyh4):** `GET /task/{task_id}/comment` has no `limit`, no page number, and its response carries **no total and no cursor** — older comments are reached only by repeating the request with `start` (the `date` of the **last**, i.e. oldest, comment of the previous page) and `start_id` (that comment's `id`), until a page holds fewer than 25 ([ClickUp's own pagination doc](https://developer.clickup.com/docs/task-comments-pagination), which is the authority here — read it raw). The wrapper sent the first request only, so a 40-comment grilling log read back as its newest 25 and an agent summarising it wrote from the second half of the discussion as if it were all of it. **The reporter's "ClickUp's own paging parameters change nothing" was not evidence:** they tested through `GET /api/v1/clickup/tasks/{taskId}/comments`, whose handler passed `taskId` and nothing else — `start`/`start_id` were dropped before they ever reached ClickUp (the same "control that wasn't one" as the Sheets `batchUpdate` body). Whether ClickUp honours the cursor is therefore **still unverified live** from this repo, which is exactly why `stalled` exists: paging lives in `ClickUpClient.getAllTaskComments` (so the tool and the REST route share one implementation, as `searchAllDocs` does), it **deduplicates by comment id**, and a full page that adds nothing new is reported as *ClickUp returned the same page again* rather than looped on — without that, an ignored cursor would re-read the same 25 for all 40 pages and hand back a plausible-looking array of duplicates. **`complete` is the only field that means "this is the whole history", and it is set by exactly one thing: a short page.** Every other stop is named separately (`hitLimit`, `hitCap`, `stalled`, `rateLimited`, `cursorUnavailable`) with the resume cursor when one could be built, because "25 comments" and "25 comments and that is all of them" are the two cases this exists to separate — and an empty result from a *failed* scan is rendered as "NOT evidence that the task has no comments", never as `No comments on this task.` A task with **exactly 25** comments costs a second request and must not report `hitCap` for it: 25 is indistinguishable from a full page with more behind it without asking. A `limit` that lands on the last comment of a short page reports `complete`, **not** a cursor pointing at comments that do not exist. Both halves of the cursor are **refused in `execute`, not in Zod** — a Zod rejection surfaces as FastMCP's generic `InvalidParams`, and ClickUp ignores one half without the other and answers with the newest 25 again, the silent no-op that produced this bug report (identical reasoning to `resolveDueDateUpdate`). The REST route pages to completion **by default** (`?allPages=false` for just the newest 25, `?limit=N`, `?start=&start_id=`, `startId` accepted as an alias and refused when the two spellings disagree); it keeps the `comments` key and element shape it has always had and adds `scan` alongside, and it **refuses `page` and `cursor` by name** rather than ignoring them, since ignoring them is how a caller concludes paging does nothing. Order is ClickUp's **newest-first** and is now stated in the output, with `oldestFirst` to read a thread as it was written — flipping the default was rejected as a silent change to an existing contract, but an unlabelled reverse-chronological dump is what makes an LLM invert a Q&A narrative. **Threaded replies remain unreachable and that is a ceiling, not an oversight:** `GET /comment/{comment_id}/reply` is not exposed here and ClickUp gives it **no paging parameters at all** (verified in its OpenAPI: `comment_id` is the only parameter), so a tool for it would carry a first-page cap nothing could work around; `formatComment` prints `[N threaded replies, not included]` so a threaded discussion is merely *unread* rather than *invisible*. Note the route still reports an upstream 404 as a 500 — the pre-existing symbol-tagged-status defect below, deliberately left for the one pass that fixes all ~24 ClickUp GETs together.
- **ClickUp Doc images are self-hosted:** ClickUp has no image-upload API for Docs, and its SPA `/v1/attachment` route needs a browser session JWT this server doesn't have (ClickUp auth here is a per-user OAuth token). So `insertImageIntoPage`/`uploadClickUpDocImage` re-host the image themselves: fetch a public image URL (SSRF-guarded, 20 MB cap), store the bytes in Postgres (`clickup_doc_images`, `src/clickup/docImageStore.ts`), and embed `![](BASE_URL/images/clickup-doc/<id>)` via the existing markdown `editPage`. The serve route (`registerClickUpDocImageRoutes` in `webServer.ts`) is public/unauthenticated (ClickUp's renderer must fetch it; ids are unguessable UUIDs). Requires `DATABASE_URL` + `BASE_URL`; without Postgres the tools return a clear error. Input is a remote URL only (no base64 yet). **These images must never be stored `ephemeral`:** ClickUp's renderer re-fetches the URL on every page view, so an expiring blob would 404 the day it lapses — retention in `image_blobs` is opt-in per call site precisely so a global TTL can't break this path.
- **ClickUp task types are a bare number, and `listTaskTypes` exists because two of them are invisible:** `createTask`/`updateTask` take `taskTypeId` and send it as `custom_item_id`; `0` is the default "Task" (and is what resets a task back to one), `1` is Milestone. `GET /team/{id}/custom_item` returns **only the workspace's *custom* types** — the two built-ins are absent — so rendering that payload as-is reads as "this workspace has no Task type"; `listTaskTypes` prepends them and labels the counts (`2 built-in + N custom`). `formatTask` shows `Task type:` only when the value is a real type: `0` is the default and a line saying so on every row of a 100-task list carries no information (same rule as `Archived:` and `Top-level parent:`). It renders the **number**, not a name — ClickUp's task payload carries no type name, exactly like `parent` — so the description points at `listTaskTypes` rather than paying an N+1 lookup per row. Note ClickUp's own docs warn that **changing the type changes which custom fields apply**, so a `getTask` after a type change can return a different `custom_fields` set.
- **Re-parenting a ClickUp task goes through `updateTask.parentTaskId`, and the wrapper is most of the feature:** ClickUp's `PUT /task/{id}` has always accepted `parent`, and `ClickUpClient.updateTask` has always declared it — it was simply never populated, and FastMCP's `additionalProperties: false` meant an LLM could not pass it at all, so restructuring a hierarchy meant recreating tasks and losing their comments, history and custom fields (ticket 1245xawcebz). `parentTaskId` is **`.nullable()` and deliberately not `.min(1)`**: a Zod-level rejection surfaces as FastMCP's generic `InvalidParams` ("Expected string, received null"), which is the unexplained failure the parameter exists to replace — letting `null`, `''` and self-reference reach the body is what buys one clear voice for all of them. **ClickUp cannot clear a parent**, so null is refused rather than sent: a subtask can be moved between parents but never promoted back to top level. The re-parent path costs **three calls; a plain update still costs exactly one** and returns the byte-identical string it always did (there is a test on that). The **pre-flight `getTask(parent)` is the only source of the parent's name** — ClickUp's payload carries `parent` as a bare ID and no name anywhere — and it also yields the parent's list and turns an unknown ID into a message naming it instead of the raw 400 body `request()` would surface (it has no 400/404 special-casing). It is a **hard gate because nothing has been mutated yet**; the post-write re-read is the opposite, **best-effort**, because failing a move that did happen is worse than not confirming it. The re-read exists because **a stale PUT echo would let a silent no-op read as success** — the exact bug the ticket is about — so a mismatch is reported as `⚠ Re-parent did NOT take effect`, never as "updated successfully". The cycle check only sees the candidate's immediate parent and its root, so **a deeper cycle still relies on ClickUp's own rejection** (wrapped with the parent's name and list). The PUT is **atomic**, so a rejected parent loses the other fields in the same call — hence the tool description telling the model to re-parent standalone. **ClickUp emits no webhook event for a parent change at all** (`taskMoved` is a LIST move), so `getTaskEventHistory` can never show one and an empty result there never means "nothing was re-parented"; do **not** synthesise a row for it — it would capture only moves made through this MCP, leaving a ClickUp-UI drag invisible, so the history would be partial in a way that reads as complete (and `ClickUpTaskEvent` requires a `subscriptionId` FK a user without a subscription does not have). `formatTask` renders `Parent:`/`Top-level parent:` for **all five** task tools and the REST `Accept: text/plain` twin from one place; `Top-level parent` is suppressed when it merely repeats `parent` or the task's own id, so it only appears when nesting is deeper than one level. Finally, the uncatalogued **`PATCH /api/v1/clickup/tasks/:taskId` forwards `parent` raw and bypasses every guard above — on purpose**: those guards are error-message quality for an LLM, not integrity checks (ClickUp itself rejects null parents and cycles), and that route's caller is a dashboard API key holder. **Cross-list parents: unverified.** The tool reports the parent's list and the task's list after the move rather than asserting a rule; fold the observed answer into this bullet and the tool description once a real cross-list move has been run.
- **Clearing a ClickUp task due date needs `clearDueDate: true`, because `dueDate` CANNOT express it:** `dueDate` is a string and every path funnels it through `toClickUpTimestamp`, which refuses anything that does not parse — so `""` answers *"dueDate is not a valid date"* and there was no value at all that meant *remove the date* (reported bug: task 1245xawdeqp). That refusal is **correct and must stay**: an unparseable date yields `NaN`, `JSON.stringify` serialises `NaN` as **`null`**, and ClickUp reads a null `due_date` as *clear the date* and answers 200 — so accepting `""` or a typo'd ISO string would wipe the date and report success. Which is also why the field is a **separate boolean rather than making `dueDate` `.nullable()`**: a client sending null by accident would then destroy data in the other direction, and an explicit flag cannot be arrived at by accident. Passing **both** `dueDate` and `clearDueDate` is **refused with nothing written** rather than resolved by precedence — which one was meant is unknowable — while `clearDueDate: false` means *no change*, since that is what a templated body sends. The resolution lives **once**, in `resolveDueDateUpdate` (`src/clickup/restWrites.ts`), because the MCP tool builds its update body **inline** rather than through `buildTaskUpdateBody`, so the refusal and the null would otherwise exist in two copies that could disagree. **The clear is verified, like the re-parent above:** ClickUp answers an update it ignored with 200, and `formatTask` renders `Due:` only when a date is present, so a clear that did nothing differs from one that worked only by an absent line — and an absent line is not evidence. The PUT echo is trusted when it **agrees** with the request (so a clear costs exactly one call, and a plain update is byte-identical to before); only a **disagreeing** echo buys a `getTask`, because a stale echo and a silent no-op are indistinguishable from the echo alone and reporting a successful clear as a failure is as wrong as the reverse. REST reports it as three-valued `dueDateCleared` (true / false / **null = unconfirmed**), the same contract as `reparentConfirmed` and `addTaskToList`'s `confirmed`. Two things to know about the evidence base: ClickUp honouring an explicit JSON `null` to clear a task field is **verified live** (2026-10-12, `priority: null` on `PUT /task/{id}`), but **`due_date: null` specifically has not been exercised end-to-end** — which is exactly why the runtime verification exists rather than a comment asserting it. And **`start_date` has the identical gap**, deliberately left alone: the same flag would fix it and nobody has asked. Finally, the bug report's other two routes were **not** this bug — see the REST body-parser entry: the dev deployment predated that fix, so `{"dueDate": null}` on `/update` and native `{"due_date": null}` on the legacy PATCH both failed because **`req.body` never arrived**, not because null was dropped or ignored (a plain `{"name": "x"}` failed identically, which is the control that proves it).
- **Every ClickUp date must travel with its `*_date_time` boolean, and omitting it SILENTLY MOVES THE DATE (verified live 2026-10-13):** ClickUp pairs `due_date`/`start_date` with `due_date_time`/`start_date_time`, and the boolean defaults to **false** — which does not mean "no opinion", it means *discard the time of day*: ClickUp converts the instant to the **workspace's** timezone, keeps the **local calendar date**, and pins the result to **04:00 local**. `grep -rn due_date_time src/` returned **zero** before this, so every date this server had ever written was normalised that way. Proof: `2026-10-20T09:00:00Z` and `2026-10-20T18:30:00Z` both stored as `2026-10-20T01:00:00Z` (= 04:00 in a UTC+3 workspace), and the older probe's `2026-12-01T00:00:00Z` stored as `02:00Z` (= 04:00 at UTC+2 — same rule, different DST offset). **The severe half is not the lost time, it is that the date kept is the LOCAL one:** `2026-10-20T23:30:00Z` is 02:30 on the 21st in that workspace and came back as `2026-10-21T01:00:00Z` — a task due **a day later** than asked, with nothing in the 200 to say so. So any caller passing a UTC instant late in the UTC day got the wrong date. The flag is derived from the **input's shape**, never a new parameter (`inputCarriesTimeOfDay` in `src/clickup/restWrites.ts`): an ISO value with at least `HH:MM` sends `true`, a bare `2026-10-20` sends `false`, and a **Unix-ms value sends `true`** because it designates an instant — the caller chose millisecond precision and deciding they meant a whole day would be deciding for them. A separate parameter was rejected precisely because it could contradict the value beside it. `toClickUpDateValue` wraps `toClickUpTimestamp` (keeping all of its NaN/Infinity/range refusals) and returns `{ ts, hasTime }`; the two flags are **independent**, so one date may carry a time while the other does not. A **clear sends no `due_date_time` at all** — there is no date left for it to qualify and a flag beside a `null` is a contradiction ClickUp need not resolve (see [[clearDueDate]] above). Fixed on `createTask`, `updateTask`, `buildTaskUpdateBody`, `updateList` and `performUpdateList`; **`getTimeEntries`' `start_date`/`end_date` are deliberately untouched** — they are query filters on a read, not stored values, and the boolean has no meaning there. The **legacy native passthrough routes are also untouched by design**: their caller sends ClickUp's own snake_case body and can pass `due_date_time` itself. Two things this does NOT fix: a date-only value is parsed as **UTC midnight**, so in a workspace at a *negative* UTC offset its local date is the day before — fixing that needs the workspace timezone, which this layer does not have — and the behaviour change is **intentional and visible**: a caller who passed `09:00Z` and had been getting 04:00 local will now get 09:00Z.
- **ClickUp's Tasks in Multiple Lists answers a disabled ClickApp with 401, and the pre-flight is the feature:** `addTaskToList`/`removeTaskFromList` wrap `POST`/`DELETE /list/{listId}/task/{taskId}`, which ClickUp gates on the **"Tasks in Multiple Lists" ClickApp** — and when it is switched off the endpoints answer **401**, the *same* status ClickUp uses for a revoked token and for an ID it cannot resolve (`OAUTH_027` "Team not authorized", the same collision `updateTask`'s re-parent pre-flight documents). Nothing in the body separates the four causes, so the raw `ClickUp API error (401)` sends the user off to re-issue a credential that works perfectly — the reported bug. Since the response cannot be read to tell which it is, both tools **rule the others out first**: they `getTask` then `getList`, and only a 401 *after* both reads succeeded is attributed to the ClickApp (a non-401 rejection never is). Those reads are not garnish — they are also the only source of the two **names** the confirmation quotes, because both endpoints answer **200 with an empty body**. That empty body is also why every path re-reads the task afterwards, and why the verdict is **four-way, not two**: a failed re-read reports the *requested* state, a payload carrying no `locations` array reports *unconfirmed* (that absence is what a disabled ClickApp looks like), and only a payload that actually disagrees is reported as `⚠ did NOT take effect` — collapsing those would turn a share that did happen into an error. **`locations` is read as evidence only when present**, never as proof of absence, which is why the "already in that list" / "not in that list" shortcuts fall through to the API when the key is missing instead of fabricating a no-op. Two refusals are local and cost no write: ClickUp **cannot remove a task from its home list** (documented), and adding a task to its own home list is a no-op ClickUp accepts with 200, which would read as a successful share. `formatTask` renders `Also in lists:` for all five task tools and the REST `Accept: text/plain` twin from one place — without it these writes would be **unobservable** through this server — and it subtracts `task.list` rather than echoing `locations`, because ClickUp's schema ("Lists where the task has been added") never says whether the home list is among them and the subtraction is correct either way. Sharing a **subtask** needs the separate **"Subtasks in Multiple Lists"** ClickApp, so the 401 message names both. Custom task IDs are unsupported here (no `custom_task_ids`/`team_id` forwarding), and the two writes now DO have REST siblings (`POST /api/v1/clickup/tasks/{taskId}/lists/{listId}` and `.../remove`) which deliberately skip the `getTask`/`getList` pre-flight: a REST 401 is therefore **never** attributed to the ClickApp, because without those two reads there is nothing to rule out a revoked token or an unresolvable ID. They do keep the empty-body re-read, so `confirmed` stays three-valued. **Every ID is `encodeURIComponent`d before it enters a path** — a `?` or `#` would truncate it, so the pre-flight could validate one task while the write hit the prefix, with the tool reporting the ID it was handed either way. Finally, a failed write is only reported as "the task was not changed" when ClickUp **answered that it refused**: `request()` tags each error with whether ClickUp answered and with the status, and only a **4xx** is a refusal — an answered **5xx** joins timeouts and dropped connections in the "outcome UNKNOWN" branch, because a 500 can be raised after the write committed and a 502/504 is usually a proxy that never learned either. Claiming otherwise would be the same lie as reporting a silent no-op as success.
- **A task shared into a second ClickUp list is INVISIBLE when you browse by list unless `include_timl=true` (verified live 2026-09-29):** this is the half of Tasks in Multiple Lists that has nothing to do with the write path — `addTaskToList` can succeed and the task still reads back as absent. `GET /list/{list_id}/task` **excludes** tasks whose home list is elsewhere by default, so `listTasks` answered `No tasks found` for a list that demonstrably contained the task. `listTasks` therefore sends `include_timl` **on by default** (`includeMultiListTasks=false` opts out), on the plain and close-window paths and on the REST twin `GET /api/v1/clickup/lists/{listId}/tasks?includeMultiListTasks=false`. The default is read as **`args.includeMultiListTasks !== false`, not from Zod's `.default(true)`** — if the schema layer is ever bypassed, `undefined` must still mean ON, because the off direction fails by silently omitting tasks that are really there. Turning it on creates a second-order confusion the tool has to answer for: `formatTask` renders each task's **home** list, so a shared row's `List:` line names a list you did not ask about — `sharedTaskNote` counts those rows and names their home lists rather than leaving them looking like a bug. **The sibling endpoint has no such parameter and cannot be fixed:** `GET /team/{team_id}/task` (`filterTeamTasks`, and `searchTasks` on top of it) accepts **no `include_timl`**, so its `list_ids` filter matches a task's **home list only** — both the client method and the `listIds` description say so, and point at `listTasks` for a list's complete membership. Do not "fix" that by adding the parameter: ClickUp ignores unknown query keys, so it would read as support while changing nothing.
- **ClickUp cannot create or edit custom FIELD DEFINITIONS, and no amount of tooling here changes that:** the public API exposes only reads (`GET /list|space|folder|team/{id}/field`) and per-task value writes (`POST`/`DELETE /task/{taskId}/field/{fieldId}`) — which is what `getAccessibleCustomFields` / `setCustomFieldValue` / `removeCustomFieldValue` already cover. There is **no create-field, update-field, or edit-dropdown-options endpoint on v2 or v3**; a field (and every option on a drop_down) has to be created in the ClickUp UI first, and ClickUp's own feature request for it has been **open since September 2019** with an explicit staff confirmation that only get/set/remove of *values* is available. So a workspace cannot be provisioned or migrated field-schema-and-all through this server, and a tool claiming to do it could only be a throwing stub — the same reason HubSpot's `searchData` is omitted rather than advertised. Do not add one; re-check the feature request before assuming the ceiling has moved. The check to run is **`curl -s https://developer.clickup.com/llms.txt | grep -i field`** — ClickUp's own machine-readable endpoint index, which lists exactly the four reads plus set/remove value and nothing else. Read it raw: a summarised fetch of that file is how you end up trusting a paraphrase of an API surface. Because the request that reaches for this arrives as "create a field", the ceiling is stated **in the tool descriptions** of `getAccessibleCustomFields` and `removeCustomFieldValue`, not only here — a model that cannot see this file still has to stop offering it. Values themselves are confirmed working live (2026-09-29) for `drop_down`, `number`, `labels` and `url`, including re-setting a drop-down and clearing it.
- **`setCustomFieldValue` normalises the value before it writes, and `value` is a typed union rather than `z.any()` (ticket 86cba13av):** ClickUp stores every array-valued field type (`labels`, `users`, `tasks`, `list_relationship`, `attachment`) as a JSON array and answers a scalar with `{"err":"Value must be an array","ECODE":"FIELD_144"}` — and `z.any()` renders as the **empty JSON Schema `{}`**, which gives a client nothing to keep an array *as* an array, so the array arrived as its own JSON text and **every labels and users field in the workspace was unwritable from an agent** while text/number/drop_down wrote cleanly through the same call. The schema is now an explicit union (string | number | boolean | array | object) **and** `src/clickup/customFieldValue.ts` revives what still arrives serialised — both fixes, because neither alone covers a client that ignores the schema. **Reviving a string is only unambiguously safe once the field TYPE is known**: `["a"]` in a `text` field is a legitimate literal, so the tool looks the definition up first (`getTask` → its list → `getAccessibleCustomFields`) and the type decides. That lookup is spent **only when the value could still need it** (`needsFieldLookup`): an array of UUIDs, a number or a boolean is already in ClickUp's shape and still costs exactly one request, the same rule the re-parent pre-flight follows. It is **best-effort, not a gate** — a failed lookup degrades to reviving only a string that parses as a JSON array/object (never a scalar: `"12"` stays the string) and the response says option names were not resolved. Unknown label/drop-down options are **refused before the write**, naming the options that do exist, because the raw 400 names neither the field nor its options — and ClickUp has no API to create one, so an unknown option can only be a mistake. **A drop-down has two working value forms and the tool never downgrades one:** ClickUp documents the value as the option **UUID**, while this tool has always sent the **orderindex** — and that form is verified live (2026-09-29), so a UUID passes through unchanged, a number or numeric string stays an orderindex (the contract every existing caller was written against), and only a *name* is resolved, to the documented UUID. **A numeric string is an orderindex, never an option name**: the live `Triage Score` field has options *named* `1`..`10` whose orderindexes are `0`..`9`, so name-matching would write 2 where the caller asked for 3 — the collision is reported with the option's UUID instead of being resolved silently, and an orderindex **no option has** is refused rather than sent, since it can only set the wrong option or nothing. **`users` and relationship fields have two legal shapes, and the second is an OBJECT:** ClickUp documents an incremental `{"add": [...], "rem": [...]}` (either key alone) for People and `tasks`/`list_relationship` fields, which says something an array cannot — change membership without replacing it — so it passes through untouched in both the object and the serialised-string form. Wrapping it in an array, which is what array-valued handling does to any other object, would break a call that worked before any of this existed; an object that is neither shape is refused instead of wrapped. `attachment` is deliberately **not** in the array-valued set — its value shape here is unverified. Finally there is **no post-write re-read**: ClickUp answers this POST 200 with an empty body and omits a field from a task's payload entirely when it does not apply to that task's type, so a confirming `getTask` would report a successful write as a failed one (see the `applied_objects` bullet above).
- **A ClickUp task payload carries only the custom fields that apply to its task TYPE, and an omitted field is not an empty one (verified live 2026-09-29, task `1245xawcvnn`):** six fields were set on a task and `getTask` rendered exactly **one**. It was not an endpoint difference (`getTask` and `searchTasks` returned the identical set), not field type (two `drop_down`s, only one shown), and **not this repo's formatter** — the raw payload from `GET /api/v1/clickup/tasks/{taskId}` contained a `custom_fields` array of **length 1**. The cause is `applied_objects` on each field definition: it lists the task-type IDs the field applies to, and ClickUp drops from a task's payload every field whose list excludes that task's `custom_item_id`. Here the task was type `0` and only "Mode" listed `object_id: 0`; the other five were scoped to Project (1005), Tactic (1006), Operation (1007) and LI Snapshot (1011) — real types from `listTaskTypes`, which is what confirms `object_id` is a task-type ID. **The stored values are untouched and still match the `searchTasks` `custom_fields` filter**, because filtering runs server-side against the stored value and ignores applicability — so the filter matching while the render shows nothing is the signature of this, not a contradiction. That asymmetry is why the omission is so misleading: a field you can successfully filter on reads as unset. `getAccessibleCustomFields` is the **only** place this is diagnosable (the task payload has no trace of the missing field at all), so it now renders `Applies to task types:` per field — `all` when `applied_objects` is absent, since the scoping is opt-in — plus a trailing note, emitted only when something really is type-scoped, stating that an omitted field may still hold a value. `getTask`'s description says the same, because a model reading one task never sees the field list. - **Email sign-up is verify-first — the account does not exist until the link is clicked:** `POST /api/auth/register` creates **nothing** in `users`. It bcrypt-hashes the password, parks it in `pendingRegistrationStore.ts` (Redis `pending_registration:<sha256(token)>`, 24h TTL, memory fallback bounded at 10k with oldest-first eviction), and mails a link; `GET /auth/verify?token=…` is **inert** — it only serves `public/verify.html`; the `POST /auth/verify` that page submits is what calls `createPasswordUser` and opens the session. **That split is load-bearing, not ceremony:** when a single GET both consumed the token and created the account, a mail scanner following the link (Outlook SafeLinks and friends do) completed the sign-up on the recipient's behalf and burned their link, so the human then clicked it and was told it was invalid. Single-use does *not* prevent that on its own — it only stops a second account — which is why the redemption had to move to a request a prefetch will not make. Consequences worth knowing: **the token is stored only as a SHA-256** (it is a bearer credential that can bring an account into existence, so a Redis dump must not yield a usable one — no work factor needed, the input is 32 CSPRNG bytes); it is **single-use, deleted before the record is returned**, so one link can never create two accounts; and unknown/used/expired all answer the **same** `/login?verify=invalid`, because distinguishing them tells a probe which tokens once existed. `/auth/verify` sets `Referrer-Policy: no-referrer` — the token rides in the query string and would otherwise leak in the Referer of anything the next page loads. **Registration answers 202 identically whether or not the address is taken** (`REGISTRATION_ACCEPTED`), replacing the old 409: the owner of a taken address gets a "someone tried to sign up" mail carrying **no link**, and the password is hashed on *both* paths so the ~190ms bcrypt cost cannot be used as a timing oracle for what the identical body refuses to say. Two sign-ups for one address mint two valid tokens (nothing exists yet to reject the second); whichever link is clicked first wins and the other gets `?verify=exists` — `DuplicateEmailError` is caught rather than 500ing, and the loser is **not** signed in, since that request never proved its password. **Mail goes through Resend over plain `fetch`** (`mailer.ts`, no new dependency; `RESEND_API_KEY` + `MAIL_FROM`). Without a key: outside production the message body — including the link — is logged so local sign-up works with no provider; in production `register` throws `MailNotConfiguredError` → **503, nothing created**, because reporting "check your email" for a mail that was never sent strands the user. `isMailConfigured()` requires **`MAIL_FROM` as well as the key in production** — the fallback sender is Resend's sandbox address, so a key-only deployment would otherwise pass preflight, build pending state, and fail at the provider (or send from an identity nobody chose). **Pending records are cleaned up when we fail, not when the user does:** an undelivered link's record is deleted (it is unreachable — the token existed only inside that request), and a redemption that fails for a non-duplicate reason *restores* the record, so a database outage does not spend a valid link. A `DuplicateEmailError` keeps it consumed, since an account now exists. Registration logs one **branch-independent line with no address**, so the logs cannot answer what the identical 202 refuses to. The per-email rate-limit bucket is what stops this endpoint being used to mail-bomb an arbitrary address.

- **Slack `editMessage` is gated by authorship, not by scope:** `chat.update` needs only `chat:write` — already in the seed and already held by every Slack connection — so **no reconnect is required**, unlike `files:read`/`search:read` above. What it *is* gated on is who wrote the message: a user token edits only that user's own messages, a bot token only the bot's, and Slack refuses anything else with a bare `cant_update_message` that reads as a malfunction when passed through. `handleEditMessage` (`src/slack/helpers.ts`) maps that plus `edit_window_closed` (an **admin-set workspace limit**, not bypassable via the API — the message must be deleted and reposted), `message_not_found` (**timestamps are per-channel**, so a `ts` from channel A with channel B named fails this way) and `msg_too_long`. On **slack-user** `enforceAccess` wraps it exactly as it wraps `postMessage` — without that, a channel denied for reads and writes would still be editable; **slack-bot has no `enforceAccess` on any tool**, access rules being a slack-user mechanism. **The previous text is unrecoverable:** `chat.update` replaces it and the API offers no way to read the old version back (Slack still shows humans an "edited" marker), which is why the confirmation echoes what the message now says — it is the caller's only record, and an edit that hit the wrong `ts` would otherwise be indistinguishable from a correct one. **That echo is now the plain-text path only:** an edit carrying `markdownText`/`blocks` may leave no `text` at all, so it reports the block types Slack stored instead of quoting a body that is absent — see the **"Slack mrkdwn has NO list syntax"** entry. Annotated `readOnlyHint: false` **without** `destructiveHint`, matching every other in-place update in the repo (`updateCompany`, `editPage`, `writeSpreadsheet`); `destructiveHint` is reserved for deletes. The handler lives in the shared `helpers.ts` so `slack-bot` could register it in one `addTool` block, and **it now does** — it was left unregistered while "a bot editing its own status message" was a workflow nobody had asked for, and what changed is that it was asked for, as the way to fix a message's formatting after posting. **Everything about the content parameters, the combination refusals and the rich-content confirmation lives in the "Slack mrkdwn has NO list syntax" entry**, which is also where the newer error mappings (`invalid_blocks`, `msg_blocks_too_long`, `markdown_text_conflict`, shared with the two post paths) are recorded.
- **Slack link previews are per-message and post-time only, and `omitted` must stay distinguishable from `false`:** `postMessage`/`replyInThread` on **both** Slack servers take `unfurlLinks`/`unfurlMedia`, forwarded to `chat.postMessage` as `unfurl_links`/`unfurl_media`. Like `editMessage` this needs only `chat:write`, so **no reconnect is required**. The load-bearing detail is that a flag the caller did not set is **left out of the form body entirely rather than sent as `false`** — Slack's default is not one value: a **bot-token** post does not unfurl primarily text-based links by default but *does* unfurl media, while a **user-token** post behaves like a human's and unfurls both. So `false` for a flag nobody set would silently change behaviour on the bot path, and suppressing *every* preview takes both flags. `request()` already drops `undefined` from the body, but the spread in `chatPostMessage` is written out so that invariant does not depend on a filter several hundred lines away. No REST sibling, since the Slack write plane is hard-gated.
- **Slack mrkdwn has NO list syntax, so `- item` was arriving as a literal hyphen — `markdownText` is the fix and `blocks` the escape hatch:** `grep -rn "blocks\|rich_text" src/slack src/slack-user` returned **zero** before this, so `postMessage`/`replyInThread` could only send `text`, which Slack renders as mrkdwn — and mrkdwn has bold, italic, strike, code and blockquote but **no bullets and no numbered lists**. A reporter confirmed the rendered message contained no list elements at all. It refuses `markdownText` + `text` and `markdownText` + `blocks` — Slack's own `markdown_text_conflict` names neither argument — refuses an all-empty call rather than letting Slack answer `no_text`, and refuses **`blocks: []`**, which is not an omitted array: `chat.update` reads it as *remove every block*, so it would read back as a successful no-op. `blocks` **+** `text` is deliberately allowed and encouraged, `text` being Slack's notification and screen-reader fallback. Every refusal runs before the API call, so nothing is written. **Unlike the unfurl flags there IS a readback, and it answers the reporter's actual question:** both methods echo a `message` carrying the blocks Slack stored, so `renderNote` reports `Rendered as: rich_text (rich_text_list ×2)` — i.e. *did my list really become a list* — instead of reporting what was requested. An echo with no blocks is reported as the message *may* have been stored as plain text, never as a flat assertion: an absent `blocks` key is absence of evidence. The note is emitted only when one of the new parameters was passed, so all three confirmation strings stay **byte-identical** for pre-existing callers (there is a test on that). **`broadcast` → `reply_broadcast` is on `replyInThread` only** — the "Also send to channel" checkbox, previously unreachable — and is confirmed from `message.subtype === 'thread_broadcast'`, else reported as requested-but-unconfirmed. Slack's `chat.update` reference **does** list `reply_broadcast` ("Broadcast an existing thread reply"), contradicting the usual assumption that it is post-time only, but that is **unverified end-to-end and deliberately not forwarded**: the response does not echo it, so a no-op would be indistinguishable from success (the declined Browserbase `timeoutSeconds` call). Add it once someone has run it live. **`chat.update` strips blocks on a text-only edit** — Slack's documented rule is that omitting `blocks` while providing `text` *removes* them — so the `editMessage` descriptions warn about it; passing `markdownText`/`blocks` is also how a message already posted as plain text is converted into a list, which is what makes "fix the formatting afterwards" work. **`editMessage` is now registered on `slack-bot` too**, reversing only the "nobody has asked for it" half of the older note: the handler had always been in `helpers.ts` for exactly this, and `src/__tests__/slack/tools.test.ts` is a **new** registry guard for that server, which until now imported nothing and so checked no registration at all. The unfurl flags stay off `editMessage` — that refusal turned on there being no readback, which is precisely what `blocks` does have. All of this needs only `chat:write`, so **no reconnect**, unlike `files:read`/`search:read`; and there is no REST sibling, since the Slack write plane is hard-gated.
- **Slack channel events are a store you poll, not a push:** `subscribeToChannelEvents`/`listChannelEventSubscriptions`/`getChannelEventHistory`/`debugChannelEventSubscription`/`unsubscribeFromChannelEvents` (slack-user only) mirror the ClickUp task-event quartet, including its delivery model — the webhook writes rows and the caller asks later. **Nothing in this repo pushes to an LLM session**; what this removes is paging a channel and keeping your own watermark. **Slack has no per-user subscription API:** event delivery is configured once on the app (Request URL + `SLACK_SIGNING_SECRET`, both operator-set), so subscribing makes *no Slack call* — it inserts a local interest filter. Unlike ClickUp, `[slack-ingest]` log lines **never include message text** — envelope shape only, since a private DM's body has no business in stderr. Because stderr is invisible to an MCP tool, every delivery also leaves a durable breadcrumb in **`slack_ingest_health`** (`recordIngestDelivery`/`readIngestHealth`): one row **per outcome branch**, not append-only, because the ingest URL is public and unauthenticated — keying by branch bounds the table at ~13 rows forever and needs no pruner. `debugChannelEventSubscription` reads it back, which is the only thing that separates *"Slack has never POSTed here"* (Request URL unset/wrong) from *"handshake only"* (no event types enabled on the app) from *"rejected"* (signing-secret mismatch) from *"delivered but unmatched"* (wrong channel, or `matchPattern` filtered it). The health write is **best-effort and never changes the status Slack sees** — a non-2xx to protect a diagnostic counter would disable the workspace's Request URL, which is exactly backwards.

- **Answering a Google Calendar invitation means rewriting the whole guest list, which is why it rides `performUpdateEvent`:** Google has **no "set my response" endpoint** — an RSVP is an `events.update` whose `attendees` array carries your own entry with a new `responseStatus`. And a body with a *partial* `attendees` array **REPLACES** the list, uninviting everyone absent from it, so this could only be built on the existing read-modify-write: `myResponseStatus` maps the array `events.get` just returned and swaps one row, leaving every other guest *and their answers* untouched (there is a test pinning all three rows plus the `recurrence`). **An RSVP on its own is sent as an `events.patch` carrying only that array, not as the full-resource update** — because the common case is a meeting *somebody else* organised, where this account is merely an attendee and `guestsCanModify` is false, and handing Google back the organiser's `summary`/`start`/`recurrence` may be refused as a 403 that surfaces as "make sure you have write access": the feature failing opaquely in exactly its main use case. A patch touching only the guest list asks for nothing an attendee is not entitled to change; a call that *also* edits other fields keeps the merge, since such a caller is editing the event anyway. **This split is reasoned, not measured** — there is no Calendar connection on hand to observe the 403, so the lower-risk shape was chosen rather than asserting Google's behaviour. **The caller's own row is found by Google's `self: true` flag, never by comparing emails** — the connected account may be invited through an alias or a group, so an email comparison finds nobody and silently changes nothing, or worse reports a colleague's answer as the user's. When there is **no** `self` row the call is **refused with nothing written** rather than adding the user to the guest list: that is inviting yourself to someone else's meeting, a different act from replying, and Google would accept it silently. It is a normal state, not a malfunction — an organizer frequently does not appear in `attendees` at all. Only **three** of Google's four `responseStatus` values are offered: `needsAction` is the *absence* of an answer, so writing it back would be an un-answer nobody asked for. - **Browserbase is a PROXY to someone else's MCP server, and the `sessionId` contract is the whole design:** the six browser tools (`start`/`end`/`navigate`/`act`/`observe`/`extract`) forward to the hosted server at `https://mcp.browserbase.com/mcp` rather than reimplementing Stagehand — which is also why this connector needs **no model key**: Gemini runs on Browserbase's side and they pay for it. That is not a shortcut: Browserbase's own docs name this exact client shape — "Some MCP clients open a new transport on every tool call … which means the server has no active session to fall back to and calls fail with `No active session`" — and prescribe passing the id every time, noting "an explicit `sessionId` always takes priority over the transport's current session" and that a stale id **errors rather than silently redirecting**. Caching a transport would be actively worse here, because this server runs multiple replicas and a cached id a sibling replica does not hold is precisely that failure. The cost is three round-trips on an operation that already takes seconds in a real browser; the payoff is that any replica can serve any call. `No active session` is rewritten into an instruction naming `start`, because the raw string says nothing about what to do. **Hosted-only means the CLI flags do not exist**: `--contextId`, `--persist`, `--proxies`, `--verified`, `--browserWidth/Height` and `--experimental` work only in the self-hosted server, so do not add parameters for them. **A session bills until it is released or hits the project timeout**, which is why `listBrowserSessions`/`getBrowserSession`/`forceEndBrowserSession` exist over REST and are not garnish — without them a session whose id outlived its conversation is **invisible through this server while still costing money**, and `end` falls back to REST `REQUEST_RELEASE` precisely because reporting a close that did not happen leaves a browser billing. The real backstop is the project's `defaultTimeout` in Browserbase settings (an ops step, not code); creating sessions ourselves via `POST /v1/sessions` with a bounded `timeout` would give a per-call cap but **it is unverified** whether hosted `start({sessionId})` adopts a REST-created session nothing has connected to over CDP — do not ship a `timeoutSeconds` parameter until that is tested, since one that silently does nothing is worse than none. **Domain rules bind `navigate` only** (`providerTokens.accessRules`, dashboard → Domain Rules): it is the one tool that declares a destination, so `act` can click through to anywhere and `start` can reattach to a session already navigated off-list — it is a guardrail against an agent wandering, **not a security boundary**, and the `act` description says so rather than letting a model infer containment. Absent rules mean **unrestricted** (the opposite of Slack's fail-closed `getRules`) and are deliberately **never written back as empty defaults**: an empty object is a non-empty value that would survive every reconnect merge and reset the user's rules — the trap `PRESERVED_ON_RECONNECT` documents. Matching is **label-boundary hostname suffix, never glob**: `example.com` covers `app.example.com` but not `notexample.com`, because glob semantics on a hostname are ambiguous in the widening direction. Note the paste-token re-auth path (`persistPasteConnectionFor`) now preserves `accessRules` for the same reason the OAuth path does — it used to replace `providerTokens` wholesale, which would have silently widened access on every reconnect. Finally, **`BROWSERBASE_API_KEY` and `BROWSERBASE_PROJECT_ID` are already taken** by the unrelated e2e cloud-browser transport in `.github/workflows/e2e-smoke.yml`; this connector reads neither (the key is per-connection) and the only env var it owns is `BROWSERBASE_MCP_URL` and `BROWSERBASE_ENABLED`. **The connector is seeded but HIDDEN by default (`BROWSERBASE_ENABLED`)**, exactly as `peopleforce-v4` is: the row is written on every boot with `isActive: false`, both catalog backends filter on it, so it drops out of `/api/v1/catalogs` and therefore out of the dashboard's Add Tool list and the public integrations page. `BROWSERBASE_ENABLED=true` restores it — a **restart, not a deploy**, since the seed upserts — and the comparison is strict `=== 'true'`, so `yes`/`TRUE` leave it hidden (verified). It is seeded rather than skipped so the flag can flip both ways without orphaning an existing connection, but be clear on what hiding costs one: `getMcpCatalog` filters on `isActive` too, so the entry reads as **missing**, `renderInstanceRow` degrades to the raw slug and a fallback icon, and `getMcpUrl` returns `''` so Copy URL silently yields nothing. The connection keeps working — `mcp:browserbase` stays in `scopeMap.ts` either way — it is only the dashboard affordances that degrade. On the REST plane, **`act` is deliberately absent**: it submits forms on third-party systems, that plane accepts the permanent dashboard API key, and a curl has no confirmation affordance.
- **A REST POST on a per-service subdomain had NO body parser, and the symptom named the wrong layer (fixed, ticket 1245xawe935):** `createMcpOnlyApp` — the factory `MCP_MODE=mcp` boots for every per-service Railway domain (`google-sheets.awesome-mcp.xyz`, …) — called `registerRestApiRoutes` but mounted **no `express.json()` at all**, so `req.body` was `undefined` on every REST POST it served. Every handler does `safeParse({ ...req.body, id: req.params.id })`, and spreading `undefined` yields `{}`, so the route answered **400 `"range": Required, "values": Required`** to a request that carried both — a message that accuses the caller and sends them to re-read the schema, when the schema was never the problem. GET routes worked throughout, which is what made it read as a proxy dropping bodies. The parsers are now one function (`registerRestBodyParsers` + `registerRestBodyParseErrorHandler`), and **every factory that calls `registerRestApiRoutes` must call it first** — that is the invariant to preserve, since the third factory was added without it and nothing failed until a POST was tried on a subdomain. The mount in `createMcpOnlyApp` is **scoped to `/api/v1`, not global**, and that difference is load-bearing: this app also proxies `/mcp` and `/sse`, and a global `express.json()` would consume those request streams before `http-proxy-middleware` could forward them — fixing the REST POSTs by breaking every MCP call on the same subdomain. `src/__tests__/restRoutes.mcpOnlyApp.test.ts` pins both halves; the parser assertion is the load-bearing one, because the auth gate answers 401 before a body is ever parsed, so a POST reaching 401 proves nothing on its own.
- **A Google Sheets tab is 1000 rows and `writeSpreadsheet` will not grow it, which is what made "the REST write rejects every body" look like two bugs (ticket 1245xaweemn):** the reported half — `POST /api/v1/sheets/{id}/write` and `/append` answering `"range": Required, "values": Required` to a body that carried both — **was** the missing body parser in the entry above, fixed on main 2026-10-12 (PR #195) one day after the report and pinned by `restRoutes.mcpOnlyApp.test.ts`. The report's own control was **not** one: `batchUpdate` answering `"operations": Required` to a `{"requests": [...]}` body is the *same* empty-body signature, since that body has no `operations` key either — so "parsing works for batchUpdate and fails only for write/append" was two different bodies each missing the field its schema names, not evidence of a per-route difference. What remained is the real ceiling. **`values.update` — what `writeSpreadsheet` and `POST .../write` call — never grows a grid, while `values.append` (`appendSpreadsheetRows`, `insertDataOption: INSERT_ROWS`) does**, so the same 3,196 rows succeed or fail on nothing but which tool was reached for, and the fixed-range path died on Google's `Range (...) exceeds grid limits. Max rows: 1000` with nothing on this surface able to make room. **All of it verified live on the dev deployment 2026-10-14:** the ticket's own `/write` repro now answers `{"updatedCells":1,...}` (the parser fix is deployed), `POST .../write` at `Sheet1!A1500` on a fresh 1000-row tab answers `exceeds grid limits. Max rows: 1000, max columns: 26` — **as HTTP 500**, which is the status half of this fix — a 1,500-row `POST .../append` onto that same tab answers **200** and grew `rowCount` from 1000 to **2500** (Google over-allocates; it is not 1501), and the byte-identical `/write` that had just failed then succeeded. `batchUpdateSpreadsheet` now carries **`appendDimension`** (rows/columns at the end) and **`insertDimension`** (room in the middle) — indices there are **1-based inclusive**, like `columnWidth`/`rowHeight`, converted to Google's 0-based half-open range, and `inheritFromBefore` is refused at index 1, where Google answers a bare "invalid request" because nothing precedes the first row. Both `addSpreadsheetSheet` and the `addSheet` operation take **`rowCount`/`columnCount`**, and that sizing is **not a convenience**: `performBatchUpdateSpreadsheet` reads the spreadsheet metadata **once, before any operation runs**, so a tab created by `addSheet` has no sheetId yet and **cannot be named by a later operation in the same batch** — an `appendDimension` after it is not a working alternative (the openapi description asserting that same-batch sheets resolve was wrong, and is corrected along with the comment above the op). `gridProperties` is sent **only when asked for**, because an explicit `{}` is itself a request to size the tab and every pre-existing caller has been getting Google's 1000x26; the confirmation reports **the grid Google replied with**, not the one requested, since a clamped `rowCount` reported as created is what the next write would be sized against. `writeRange` keeps Google's own text (it names the real limits) and appends the part it never says — which of the three routes grows a grid — matched on the message because Google sends no machine-readable reason for it; and the REST `/write` route maps an upstream **400 to 400** instead of through `sendUpstreamError`, which knows only 404 and 403 and would report the caller's own range as a 500 "server problem, retry". Two gaps the ticket names are **deliberately left open**: `pasteData` (the `/write` + `/append` pair is the bulk path now, and at 5 MB it takes the whole 360 KB export in one request) and Drive **upload** — that plane is GET-only, so a CSV still cannot be imported as a sheet without passing through the model's context. The second is a multipart-upload feature, not a parameter, and is not in this change.
- **Redmine redirects are now read, and sometimes followed, because `redirect: 'error'` made one broken route undiagnosable (ticket 1245xawe935):** `/time_entries.json` on one instance was redirected while `/issues.json`, `/projects.json` and `/users/current` all answered fine — so `listTimeEntries` was the only unusable tool, and the error said merely "the request was redirected away from <host> and was refused", which cannot distinguish **a proxy rewrite, an SSO hop to another host, a login bounce on one route, and a redirect loop**. Those four have four different fixes, so a message naming none of them left the endpoint broken indefinitely. `jsonApiRequest` now uses **`redirect: 'manual'`, never `'error'`** — the credential still never follows a redirect, but the `Location` is read *before* the call is refused. Four rules bound what gets followed: same-origin only, compared against the **original** request rather than the previous hop (hop-to-hop comparison lets a chain walk off-origin one innocent step at a time); **GET/HEAD only**, since a 301/302 replays a POST as a GET by spec and 307/308 replays it verbatim, and no diagnostic is worth a duplicate write; a **login path is never followed** (it answers 200 with HTML, which has no JSON content type and so resolves to `undefined` — a sign-in page reported as an empty result); and hops are capped at 3. **`RedirectRefusedError.status` is deliberately 502, not the 3xx** — `sendUpstreamError` passes `.status` straight to `res.status()`, so echoing a 302 would make our own REST client try to follow a `Location` we stripped the credential precisely to avoid; the real status stays on `.redirect.status`. On top of that, `RedmineClient` retries a **same-host login bounce** with the two other ways Redmine accepts a personal key (`?key=` then HTTP Basic `key:x`), because a reverse proxy stripping unknown `X-*` headers on one route breaks only `X-Redmine-API-Key` and looks exactly like this; it is GET-only, API-key-mode only, never cross-origin, and a **non-redirect failure on a retry stops the chain** (a 403 is Redmine having answered, which is better information than "it bounced"). The `?key=` form puts the credential in a query string a proxy may log — a real cost, accepted only because the header form has already failed on that exact route — and Redmine's bounce echoes the whole original URL back in `back_url`, which is why `jsonApiRequest` takes a `secrets` list and redacts it out of the message, the log and `.redirect`. **That redaction has to cover `target`, not just the body and the Location** — `target` prefixes every message this layer throws (redirect, timeout, non-2xx) and callers build it from the request path, so a 403 or a timeout on the `?key=` attempt would otherwise put the credential in the log and in the text shown to the model. `RedirectRefusal.resolved` is redacted for the same reason (it is reachable as `.redirect.resolved` from every caller), which is why the raw URL a follow needs is returned **beside** the record rather than read back off it. One more message trap: `sameOrigin` is false for a **scheme** change as well as a host change, so an `http://` base URL answered with a 301 to `https://` lands in the cross-host branch and would name the *same* host as "a DIFFERENT host" and blame an SSO proxy — it is split out and told to reconnect over https, and a prose `baseUrlHint` ("the Redmine instance", which several call paths pass) falls back to the generic wording rather than guessing.
- **A Redmine hours total from one page is wrong, so `listTimeEntries` grew `allPages` and a per-project fallback:** `limit` caps at 100, so "billable vs non-billable per person for nine months" computed from one response is short by whatever did not fit, with nothing in the output saying so — the old line said `Hours on this page`, which is honest but was being summed anyway. `allPages=true` (MCP and `?allPages=true` on the REST twin) pages to the end and labels the sum `Hours across all N entries`; it is **opt-in** so the single-page contract stays byte-identical for existing callers, and the single-page output now *points at the flag* so the complete answer is discoverable. The scan is bounded at **5000 entries** and says when it hit that, and it stops on a short page as well as on `total_count`, because a plugin omitting `total_count` would otherwise spend 50 requests re-reading nothing. The REST mode answers **`{ items, scan }` with no `page`** — there is no window to report and echoing one would invite paging an exhausted set — and `scan` is what tells a client whether the number is a total or a floor. Separately, `/time_entries.json` is a *single route* and can break alone, so when the workspace-wide list fails `allPages` falls back to `/projects/{id}/time_entries.json` **per project**; that is attempted only for a **route-level** failure (a refused redirect, 404, 405, 501, 5xx) and never for a 401/403/422, because those are Redmine having evaluated the request and scanning 100 projects to be told so 100 more times is a slower path to the same message. **It must use `listProjectTimeEntries`, never `listTimeEntries({ project_id })`** — the latter still requests `/time_entries.json` and scopes with a query parameter, so it re-runs the exact failure once per project, each one also paying the login-bounce retries (~300 requests to produce an empty result); the first version of this shipped that way and its test passed only because the stub keyed on `project_id` rather than the request path, so the test asserts the **path** now. Entries are **deduplicated by id**, because Redmine scopes a project query to the project *and its subprojects* when `display_subprojects_issues` is on (the default) — the same entry comes back under parent and child, and summing the concatenation reports hours **higher** than reality, which is worse than a floor; skipping child projects would be wrong in the other direction when that setting is off, and it is not readable through the API, so deduplication is the only form correct either way. If **no** project answers, the original error is rethrown rather than returned as an empty floor, which would read as "this workspace logged no hours". Its total is a **floor twice over** — one page of projects, and any project that failed individually — so it is labelled `FLOOR, not a total`, names the unreadable projects (a project contributing 0 because it could not be read must not look like one that logged no hours) and carries the reason the global list failed. `activityId` was added in the same pass because billable/non-billable is modelled as the activity on most instances, and Redmine **drops a filter key it does not recognise and answers with MORE rows**, so a mis-mapped name fails open — the caller gets every entry and reads it as the billable subset.
- **A Redmine 403 on `/time_entries.json` is FOUR causes wearing one status, and "the account lacks `view_time_entries`" was the one we asserted (ticket: redmine.gluzdov.com, non-admin account, 2026-10-15):** the reported instance 403s every time-entry call — workspace-wide, `userId=me`, per project, `allPages` — while the same account opens `/projects/329/time_entries` in the browser and sees every entry, and `listIssues`/`listProjects`/`listMemberships`/`getCurrentUser` all answer. **That report contains the evidence that disproves our own message.** Redmine authorises its HTML and JSON routes through the *identical* path — `find_optional_project` → `authorize_global` → `User#allowed_to?` (read raw from `app/controllers/application_controller.rb`; `timelog_controller.rb` has no separate check on `index`) — so for a GET the only differences are the credential (session cookie vs API key) and the response format. A page that renders for an account whose API call 403s therefore rules out **both** the permission and the project module, conclusively. A third cause is ruled out by Redmine's source too: `require_login` answers an unauthenticated `.json` request **401**, not 403, whenever the REST API is enabled and the action declares `accept_api_auth` (`timelog#index` does) — so this is not an anonymous request, and a disabled REST API would fail every call rather than one. What is left is a plugin or a proxy rule in front of this route, which is consistent with the instance running time-lock plugins and with its pre-v0.11.1 symptom (a bounce to `/login` on this route alone). `describeRedmineDenial` therefore **lists all four causes and names the browser test instead of picking one** — the same correction as the PeopleForce service-account-key wording, where the old message sent someone to re-issue a credential that was never the problem. **The regression that made it unusable was a class change, not a new block:** v0.11.1 turned the refused redirect into a 403 (the `?key=` retry gets a real answer), and `isRouteLevelFailure` listed 404/405/501/5xx and a refused redirect but **not 403** — so the per-project fallback built for exactly this instance stopped firing the moment its symptom changed shape. 403 is now in `isGlobalRouteWorthRetrying`, bounded rather than trusted: a **named project costs one extra request** (`/projects/{id}/time_entries.json`, which is also now reached on the **single-page** path, not just `allPages` — the default call had no fallback at all), and a workspace-wide scan abandons the sweep after `DENIAL_PROBE_LIMIT = 3` consecutive refusals with nothing collected, which keeps the old reasoning (being told no a hundred times is a slower route to the same message) while letting the one request that could prove it wrong happen. Three further details. The old guard skipped the fallback whenever `projectId` was set, reasoning that "naming one already uses a project-scoped query" — it does **not**: it adds `project_id` to `/time_entries.json`, the same route that just failed, so the one case with the cheapest way out was the one case with no way out. Evidence now travels **on** the error (`noteRedmineEvidence`, a Symbol read only by `mapRedmineError`, so this is not the ClickUp mistake of hiding a *status* where generic handlers cannot see it): the retry chain records that the `X-Redmine-API-Key` form was bounced to a sign-in page and the **same key** as a `?key=` parameter then got the 403 — a pair that says something about the route and nothing about a role, and which used to be discarded at the point it mattered. And `projectRoute` is deliberately **not** part of the floor condition that `perProject` sets: one project was asked for and that project answered in full, so its total is a total — what it changes is that the answer came from a different path, which is worth saying because it means the instance has a route someone should fix.
- **Nothing the hosted Browserbase server returns is forwarded verbatim, and that rule was learned the hard way (live run, 2026-10-08):** `navigate` answers with a serialized Page/CDP object — ~15 KB carrying the internal connect websocket URL, its `signingKey` JWT repeated several times, internal `*.svc.cluster.local` hostnames and a flow-logger session id — and the first version handed all of it to the model, the transcript and, over REST, any API-key holder. So `navigate` is now projected to an **allowlist** (`url`, `status`, `title`) rather than redacted: the payload's shape is Browserbase's to change, and redaction can only remove secrets someone already thought of. The URL is echoed from what was **requested**, never read back out of the payload. Redaction (`src/browserbase/responseSafety.ts`) is the backstop for `extract`/`observe`, whose payload *is* the point and therefore cannot be allowlisted. Separately, `extract` with an instruction can make the extraction model emit thousands of newlines until its JSON is cut off, and the upstream `AI_NoObjectGeneratedError` echoed **~214 KB** of raw text — enough to overflow a 25 K-token client on its own, so the error that most needed reading was the one that could not be read. Error text is capped at 1 KB, and degenerate character runs are **collapsed before** truncating: truncating 214 K newlines at 4 KB still yields 4 KB of nothing and hides whatever real content followed. There is **no hosted parameter to cap the upstream model's output** (`modelName`/`modelApiKey` are the only model knobs), so detection-and-collapse is the only half available here. Sanitising runs at **both** the proxy and the op layer on purpose — one choke point is one new call site away from being bypassed, which is exactly how this shipped. The `{"success":true,"data":…}` envelope is unwrapped so every tool renders the same way, instead of act/observe/extract handing back a raw wrapper while start/end/getBrowserSession returned text.

## Parameter Patterns

- **Document ID:** Extract from URL: `docs.google.com/document/d/DOCUMENT_ID/edit`
- **Text targeting:** Use `textToFind` + `matchInstance` OR `startIndex`/`endIndex`
- **Colors:** Hex format `#RRGGBB` or `#RGB`
- **Alignment:** `START`, `END`, `CENTER`, `JUSTIFIED` (not LEFT/RIGHT)
- **Indices:** 1-based, ranges are [start, end)
- **Tabs:** Optional `tabId` parameter (defaults to first tab)
