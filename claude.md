## Known Limitations

- **Comment anchoring:** Programmatically created comments appear in "All Comments" but aren't visibly anchored to text in the UI
- **Resolved status:** May not persist in Google Docs UI (Drive API limitation)
- **editTableCell:** Not implemented (complex cell index calculation)
- **fixListFormatting:** Experimental, may not work reliably
- **ClickUp Docs search is entirely client-side:** `GET /api/v3/workspaces/{id}/docs` has **no text-search parameter and no sort parameter**, and `limit` defaults to **50** (max 100, min 10) with opaque `cursor`/`next_cursor` paging. `listDocs` and `searchDocs` hit the *same* endpoint — `listDocs` is just the unfiltered call — so matching, paging, and ordering all live in `ClickUpClient` (`matchesDocQuery`, `sortDocsNewestFirst`, `searchAllDocs`) and both the MCP tools and the REST handlers share them; do not re-add a per-caller filter. `searchDocs` **auto-pages** the whole workspace (cap `DOCS_MAX_PAGES = 20` → 2000 docs) then sorts newest-first, and **always reports the scan extent** — a bare "No docs found" reads as "that doc doesn't exist" and is the bug this replaced (ticket 86cb5r680). Title matching is **token-AND, not substring**: every whitespace-separated word must appear, in any order, because titles are punctuation-heavy (`"AWESOME Sync"` must match `[AWESOME] Sync - 08/15/2026`). `parentType: 'EVERYTHING'` is **dropped rather than forwarded** — ClickUp accepts it but matches nothing, whereas omitting the filter returns the whole workspace; `SPACE`/`FOLDER`/`LIST` require `parentId` (Zod-enforced). `request()` has no 429 backoff, so a mid-scan rate limit returns partial results flagged `rateLimited` instead of throwing away the pages already fetched. Note `createDoc.parentType` is a **different** parameter (numeric 4/5/6 in the POST body) — do not unify it with `searchDocs.parentType`.
- **ClickUp Doc images are self-hosted:** ClickUp has no image-upload API for Docs, and its SPA `/v1/attachment` route needs a browser session JWT this server doesn't have (ClickUp auth here is a per-user OAuth token). So `insertImageIntoPage`/`uploadClickUpDocImage` re-host the image themselves: fetch a public image URL (SSRF-guarded, 20 MB cap), store the bytes in Postgres (`clickup_doc_images`, `src/clickup/docImageStore.ts`), and embed `![](BASE_URL/images/clickup-doc/<id>)` via the existing markdown `editPage`. The serve route (`registerClickUpDocImageRoutes` in `webServer.ts`) is public/unauthenticated (ClickUp's renderer must fetch it; ids are unguessable UUIDs). Requires `DATABASE_URL` + `BASE_URL`; without Postgres the tools return a clear error. Input is a remote URL only (no base64 yet). **These images must never be stored `ephemeral`:** ClickUp's renderer re-fetches the URL on every page view, so an expiring blob would 404 the day it lapses — retention in `image_blobs` is opt-in per call site precisely so a global TTL can't break this path.
- **Dashboard login is Google OAuth *or* email+password:** `/login` serves `public/login.html` (both methods side by side) — it used to 302 straight to `/auth/google`, which is why `/connect/:mcpSlug`'s park-and-login now also targets `/login`. `POST /api/auth/register` + `POST /api/auth/login` (`webServer.ts`) back the email path; hashing lives in `src/auth/password.ts` (bcrypt cost 12). **Passwords over 72 bytes are rejected, not truncated** — bcrypt silently discards past that, so accepting them would claim a passphrase protects the account when only its first 72 bytes do. Login runs `verifyPassword` **unconditionally**, including for unknown emails and Google-only accounts (hash `null` → compared against a dummy hash of the same cost), so response time is not an account-existence oracle; registration's 409 discloses existence on purpose, because a generic error there would leave the user unable to tell "taken" from "broken". `src/website/loginRateLimit.ts` caps attempts per **IP and per email** (8 / 15 min, Redis-backed, in-memory fallback that is per-process); it counts **every** attempt, not just failures — counting failures alone lets one valid login reset the window — and the **email bucket is the load-bearing half**, since `trust proxy: true` makes `req.ip` spoofable via `X-Forwarded-For`. **The load-bearing change is that sessions are keyed by `userId`, not `googleId`:** ~13 dashboard routes did `getUserByGoogleId(req.session.googleId)` inline, which 401s for an account whose `google_id` is NULL, so all of them now go through `resolveSessionUser` (userId first, googleId fallback so pre-existing sessions survive their 7-day TTL). The `/connect/:mcpSlug` OAuth state carries `userId` for the same reason — without it a password user consents at the provider and gets "User not found" on the way back. `regenerateApiKey(googleId)` was **deleted rather than kept**: its `WHERE google_id = $1` matched zero rows for these accounts and reported "user not found" on a valid one; `regenerateApiKeyByUserId` is the only version. Linking Google to an existing password account (same email) **updates that row and keeps the password + `auth_method='password'`** — both the DB `ON CONFLICT (email)` path and its file-store sibling — because the dashboard renders `authMethod` verbatim and relabelling would announce the loss of a credential that still works. `password_hash` is deliberately absent from `DB_USER_COLUMNS` and from `UserProfile`, so nothing that serializes a user can leak a hash it never selected. **There is no password reset:** no email infrastructure exists in this repo (no SMTP/Resend/SendGrid anywhere), so a forgotten password currently has no self-service path — adding one means adding a mail provider first.
- **HubSpot auth is OAuth 2.0 by default:** the catalog always advertises the OAuth endpoints, so the dashboard always shows "Connect with HubSpot" (the paste-token form is not shown). The client_id/secret come from `HUBSPOT_CLIENT_ID`/`HUBSPOT_CLIENT_SECRET` (a registered HubSpot app) and MUST be set on both the web service and the hubspot MCP service, or the connect flow has no client and fails. OAuth access tokens expire (~30 min) and are refreshed at tool-call time via `maybeRefreshHubSpotToken`. The paste-token path (`connectToken.ts`, the `/api/connect-token` hubspot branch) still exists server-side as an API-level escape hatch and skips refresh, but the dashboard no longer surfaces it.
- **HubSpot `searchData` not registered:** the reference's 16th tool did semantic search over a local FAISS vector index; this codebase has no vector store, so the tool is intentionally omitted rather than advertised as a throwing stub. The 29 registered HubSpot tools are implemented against the official HubSpot REST API. (`searchCompanies`/`searchContacts` cover the CRM search endpoint — the free-text/property lookup the omitted FAISS tool was reaching for.)
- **`getDeal` needs an ID only `getCompanyDeals`/`searchDeals` can produce:** a company record carries `num_associated_deals` — a plain **company** property, no deals scope — so a caller could see *that* a company had deals while having no route to their IDs. `getCompanyActivity` reads `/associations/engagements` (notes/calls/meetings, never deals) and `getActiveDeals` is a global recent-N with no company filter, so "show me this company's deals" dead-ended and the model reported it as **a permissions problem it was not**. `getCompanyDeals` closes it: associations v4 for the IDs, then `readDealsByIds` for the records. **Both sides page, at different sizes, and neither may truncate silently** — the association read follows `paging.next.after` 500 at a time (bounded at `ASSOCIATION_MAX_PAGES` = 10, i.e. 5,000 IDs) while the batch read chunks at HubSpot's **100-input cap**. Hitting the page bound returns `truncated`, which the op renders as "of N**+**": a bounded scan is a floor, not a count, and a truncated "Found 25 deals" would read as the company's whole pipeline. `searchDeals` is the by-name route, and widening `opSearchObjects` to a third label is why deals now share one search implementation with companies/contacts. **Do not diagnose a deal failure as missing scopes when other deal tools work:** `getActiveDeals` (`POST /crm/v3/objects/deals/search`) and `getDeal` (`GET /crm/v3/objects/deals/{id}`) gate on the *same* `crm.objects.deals.read`, so no scope grants one and denies the other.
- **HubSpot deals need the deals scopes + a reconnect:** deal tools (`getActiveDeals`, `getDeal`, `searchDeals`, `getCompanyDeals`, `createDeal`, `updateDeal`, `listPipelines`) and deal support in `getProperty`/`createProperty`/`updateProperty` require the `crm.objects.deals.*` + `crm.schemas.deals.*` scopes now in the catalog seed (`mcpCatalogStore.ts`). `seedDefaultCatalogs` re-seeds on boot and the upsert overwrites `oauth_scopes`, so the *catalog* is current after any deploy — but a **token is frozen at the scopes it was minted with**, so **already-connected users must reconnect/re-consent** before deal calls work; until then they 403. HubSpot tokens never expire in a way the dashboard flags, so such a connection looks perfectly healthy while failing every deal call — which is why the 403 is no longer reported as a bare "check your scopes". `parseHubSpotMissingScopes` (`hubspot/apiHelpers.ts`) detects it (`category`/`errorType` = `MISSING_SCOPES`, scope list from `context.requiredScopes` *or* the prose `requires any of [...]` — HubSpot sends one or the other, not both), and `withHubSpotClient` then spends one round-trip on `fetchHubSpotGrantedScopes` (`GET /oauth/v1/access-tokens/{token}`) so the message names **needed *and* granted** and points at the dashboard's Reconnect button — the Slack `formatScopeDetail` contract. Granted is the load-bearing half: it is the only way to tell *"the reconnect never happened"* from *"it happened and still didn't grant it"*, and in the latter case the message **stops telling the user to reconnect** (the HubSpot app config or the portal is the problem, not consent). The lookup is best-effort — a failed lookup degrades to the needed-only message, never to a second error. `listPipelines` returns each pipeline with its ordered stages (covering both list-pipelines and list-stages); use it to resolve `dealstage` IDs to names.
- **HubSpot engagement writes (`createNote`/`createTask`/`logCall`/`logMeeting`):** create the engagement standalone then attach it via a v4 **default** association (`PUT /crm/v4/objects/{type}/{id}/associations/default/{toType}/{toId}`), avoiding the direction-sensitive association-type-ID table. `hs_timestamp` defaults to now when omitted (the #1 documented create failure). `deleteEngagement(engagementType, engagementId)` is the cleanup counterpart — HubSpot's DELETE archives the engagement (off every timeline, recoverable from the recycling bin), which is what makes the create tools safely testable against a real portal; it needs the same contacts scopes as the writes. Success only claims a timeline attachment once the association call returns 2xx; a failed association is reported as an orphaned engagement, not a silent success. **Scopes:** these need no extra scope — HubSpot documents the notes, tasks, calls, and meetings APIs as requiring `crm.objects.contacts.read` + `crm.objects.contacts.write`, both already in the catalog seed. **Do not add `crm.objects.{notes,tasks,calls,meetings}.*`**: no such scope exists in HubSpot's public scope list, and an unknown scope makes the entire consent flow fail (every HubSpot connection, not just these tools). If an engagement write 401/403s, inspect the scopes actually granted on the token (`GET /oauth/v1/access-tokens/{token}`) instead of guessing a scope string.
- **HubSpot read/write contract:** reads that request explicit `properties` flag unknown keys HubSpot silently drops (`getCompany`/`getContact`, and `searchCompanies`/`searchContacts` via `formatObjectList`, which renders every requested property — unset ones as `(empty)` — and appends a ⚠ note listing keys HubSpot never returned, so "no value on this record" is never confused with "the tool doesn't return that"); `updateCompany`/`updateContact` re-read the record after PATCH so the response matches a fresh read (HubSpot's PATCH echo omits populated fields); `getCompanyActivity` emits ISO-8601 (engagement timestamps are epoch millis upstream). `getTickets` filters datetime props (`closedate`/`hs_lastmodifieddate`) with **epoch millis** — the search API 400s on ISO. Empty `{}` update payloads are rejected by the Zod schema before any API call. Email bodies in `getCompanyActivity` need the `sales-email-read` scope (in the OAuth scope list).
- **Slack files need `files:read` + a reconnect:** attachments are surfaced as `📎 <name> — <mime>, <size> — file ID: F…` lines under each message (`formatFileRef`/`formatFiles` in `src/slack/helpers.ts`, reached through `formatMessage`, so both the bot and user servers get it from one place), and `downloadFile(fileId, channelId, format)` retrieves the content. `files:read` is in the OAuth scope seed and the dashboard's bot-scope copy, but **already-connected users must reconnect/re-consent** — without it Slack returns file stubs with `file_access: 'check_file_info'` (rendered as "file hidden") and `files.info` 403s. **Formats:** `url` (default) re-hosts images through `store()` (`src/images/imageBlobStore.ts`) and returns a `/images/<hash>.webp` link — that link is **public and unauthenticated**, so a screenshot from a private DM becomes publicly fetchable at an unguessable URL — which is why Slack stores it as **ephemeral** (`store(..., { ephemeral: true })`), making it eligible for removal after `IMAGE_RETENTION_DAYS` (default 30, `0` disables) so exposure is bounded rather than permanent. **That is a ceiling, not a guarantee:** blobs are content-addressed, so if the same bytes are also stored for a permanent use (a ClickUp Doc image) the shared row is promoted to permanent and the Slack URL keeps working — `fetch()` enforces expiry at read time so a lapsed row is never served, but a *shared* row simply hasn't lapsed; this is what makes `insertImageFromUrl` work (Google fetches it server-side), and it needs `DATABASE_URL` + `IMAGE_PUBLIC_BASE_URL`. `inline` returns a FastMCP `imageContent` block instead (capped at 1.5 MB, no image host needed) — the **only** tool in this repo that returns anything but a string. Text-like files come back as text; other types return metadata + permalink rather than an error. **Security:** `src/slack/fileDownload.ts` attaches the bearer token **per redirect hop and only for `*.slack.com`**, so Slack's redirect to signed S3 URLs can't leak the workspace token; a token missing `files:read` gets `200 OK` with an **HTML sign-in page** (not a 401), which is rejected explicitly so a login page is never stored as a screenshot. `downloadFile` requires `channelId` and verifies the file is really shared there (`fileShareTargets` unions `channels`/`groups`/`ims` **and** the newer `shares.public`/`shares.private` maps) — on the user server `enforceAccess` runs first, and the share check is what stops a file in a denied channel being laundered through an allowed one.
- **Slack search is user-token-only and post-filtered:** `searchMessages`/`searchFiles` are registered on the **slack-user** server alone — `search.messages`/`search.files` reject bot tokens with `not_allowed_token_type`, so there is deliberately no stub on `slack-bot` (same reasoning as the omitted HubSpot `searchData`). They need **`search:read`**, added to the OAuth seed in `mcpCatalogStore.ts`, so **already-connected users must reconnect/re-consent** — which the dashboard only started allowing once `renderInstanceRow` grew a `showReauthorize` branch: `needsReconnect()` returns false for every non-Google provider (their tokens never expire), so a Slack row rendered *Copy URL* and no Reconnect button at all, and the tools' "reconnect from the dashboard" instruction pointed at an affordance that did not exist. Scope changes, not expiry, are what make re-consent necessary for these providers. Until they do, `callSearch` rewrites Slack's `missing_scope` into a "reconnect from the dashboard" message — carrying through Slack's own `needed`/`provided` fields (`formatScopeDetail` in `apiHelpers.ts`), because `provided` is the authoritative list of what the stored token actually holds and is the only way to tell a reconnect that never happened from one that happened and still didn't grant the scope. **Access control is the subtle part:** `enforceAccess` can't run (it takes one `channelId`; a search has none), and Slack's query DSL has no channel deny-list, so results are over-fetched and dropped client-side — `buildChannelFilter` (`src/slack-user/server.ts`) runs `fetchChannelMeta` + `assertAccess` + `assertDmMemberAccess` per distinct channel — the DM/group-DM check matters because without it a result from a DM with a non-allowed org, or a group DM holding a blacklisted member, would pass a filter a direct read rejects — memoised per call on top of the 5-minute meta cache, and **fails closed** on any error. A file is shown if *any* channel it's shared into is allowed. Because filtering happens after Slack pages, **page numbers are Slack's, not the filtered list's** — a page can come back empty while more matches exist, and the response says so plus how many results the rules hid (a silent drop would read as "Slack found nothing"). `search.*` pages by `page`/`count`, **not** by `cursor` like every other Slack call here. No REST sibling: the REST plane is hard-gated on `slackBotToken` precisely because access rules can't be applied there.
- **Slack list/read parity is one rule engine with one deliberate seam:** `listChannels` used to run a *second*, hand-written copy of the access rules that skipped the org check whenever `conversations.list` returned no team IDs — so a Slack Connect channel was advertised as available and then failed every read with an opaque team ID. `filterChannelList` is now a thin wrapper over `classifyChannelList`, which calls the same `assertAccess` a read calls; keep it that way. The one surviving difference is intentional and tested: a shared channel whose *list* payload names no org is `needsOrgBackfill`, not denied — "unknown" is not "denied", and resolving it costs a `conversations.info`. `listChannels` spends that call for up to `CHANNEL_INFO_BACKFILL_MAX` (25) channels, which is half the tier-3 minute budget because the same handler already pays for DM and group-DM member lookups; channels past the cap are reported, never silently unchecked. **`assertAccess` checks orgs before channel patterns**, so an org denial says nothing about whether the whitelist would have allowed it — anything that treats an org denial specially must call `assertNonOrgAccess` first, or a channel the user's own whitelist excludes leaks out on an org technicality. Denials are typed (`SlackAccessDenied`, with `reason`/`orgIds`/`patterns`) so the message text is no longer the API; the text itself is unchanged so callers that only print it are unaffected. Org-denied rows are **listed but flagged** (with `topic`/`purpose` withheld — structural facts about a channel the rules refuse to read are fine, its free text is not); rows denied by the user's own channel patterns are **hidden but counted**, because listing them would dump the names of channels they deliberately excluded. `diagnoseChannelAccess` is the generic answer to "why can't I see #x" — it was chosen over hardcoding an exemption for the support channel, which would have been spoofable by any workspace creating a channel with that name. Error messages name the org via `resolveTeamNames` (`src/slack-user/teamNames.ts`), whose cache is **keyed by token and bypassed entirely without one**: whether `team.info` succeeds depends on the calling token, so a bare team-ID key would serve one tenant's names to another. Expect the name to be missing — `team.info` on a foreign org usually fails even with `team:read`, and every org in a denial is by definition foreign — which is why the raw `T0…` ID is always kept alongside it: that ID is what the dashboard's Organizations checkbox is labelled with, and matching the two is how the user actually applies the fix.
- **Google Docs text is sanitised before it reaches the transport:** `src/google-docs/textSafety.ts` is on every `readGoogleDoc` return path, `parseDocStructure`'s `textPreview`, and the REST twin at `/api/v1/docs/:documentId`. Three defects lived here. (1) `format: 'json'` sliced *already-serialised* JSON and returned the fragment, so anything that parsed it failed with `EOF while parsing a string` — a truncation bug that reads exactly like a transport bug; the partial now travels as a **string field inside a valid envelope**, the same contract `truncateJsonByLength` uses for REST. (2) Every truncation used `substring`, which cuts on UTF-16 code units and leaves a lone surrogate when it lands inside a surrogate pair — use `sliceSafe`, never `substring`, on anything headed for a tool result. (3) `textRun.content` was copied verbatim, including the `U+000B` Docs emits for shift-enter soft breaks (converted to `\n`, **not dropped** — it is a real line break) and the private-use chars it uses as inline-object placeholders. `assertTransportSafe` is the backstop: after sanitising it should never fire, and that is the point — if anything ever reaches the wire unencodable, the caller gets an error naming the offset and code point instead of a JSON parse failure inside their client, which is undiagnosable from the outside. Also note `format: 'text'` **used to drop all table text**: its `fields` projection named only paragraphs, so the table-walking branch was dead code; the projection now names tables too.
- **Slack `allowedOrgs` is an allowlist you can only tick what the dashboard found:** the Organizations checkboxes in Access Rules come from `discoverConnectedOrgs` (`src/slack-user/orgDiscovery.ts`), and an org missing from that list has no checkbox, so it can never be allowed, so its channels and Slack Connect DMs stay invisible with no way for the user to say otherwise — **under-reporting here is a silent access failure, not a cosmetic one**, which is why every cap in the module is reported back as `orgDiscovery.truncated` + notes and rendered as a warning instead of quietly shortening the list. Discovery sweeps four sources because no single one is sufficient: `conversations.list` (public+private), `users.conversations` for `im,mpim` (**conversations.list never returns DMs**, so an org you only Slack-Connect-DM was previously undiscoverable while `filterDmsByOrg`/`assertDmMemberAccess` still enforced `allowedOrgs` on it), `users.list` (every visible user carries its own `team_id`, including external counterparts), and `conversations.info` only for shared channels whose list payload named no team — the old code called `conversations.info` on **the first 10 shared channels and nothing else**. **Never read `shared_team_ids` directly:** Slack Connect puts the partner org in `connected_team_ids` (and `pending_connected_team_ids` before the invite is accepted) while `shared_team_ids` stays internal-only, so both discovery and enforcement go through `channelTeamIds()` (`src/slack/apiHelpers.ts`), which unions them — `includePending: true` for discovery (the org should be tickable early), **false** for enforcement (an unaccepted invite must not deny a channel that org cannot read yet). Enforcement is **all** the channel's orgs must be allowed, not `some`: `some` passed any channel that included your own workspace, which is always in `allowedOrgs`. Saved orgs are always returned even when nothing rediscovers them, because the dashboard rebuilds `allowedOrgs` from rendered checkboxes — a missing row used to mean opening the modal and pressing Save revoked an org nobody asked to revoke (the client now merges unrendered saved orgs too). Results are cached 5 min per `(instance, saved allowlist)`; `team.info` on a **foreign** team usually fails even with `team:read`, so an org shown as a raw `T0…` ID with `nameResolved: false` is expected, not a bug.
- **Slack channel events are a store you poll, not a push:** `subscribeToChannelEvents`/`listChannelEventSubscriptions`/`getChannelEventHistory`/`debugChannelEventSubscription`/`unsubscribeFromChannelEvents` (slack-user only) mirror the ClickUp task-event quartet, including its delivery model — the webhook writes rows and the caller asks later. **Nothing in this repo pushes to an LLM session**; what this removes is paging a channel and keeping your own watermark. **Slack has no per-user subscription API:** event delivery is configured once on the app (Request URL + `SLACK_SIGNING_SECRET`, both operator-set), so subscribing makes *no Slack call* — it inserts a local interest filter. Consequently there's no remote id, no per-row secret and no orphan-rollback, and **one Request URL serves the whole workspace**, so `handleSlackEventIngest` looks subscriptions up by `(team, channel)` and **fans out one delivery to N subscriber rows** (`findSubscriptionsForChannel` returns an array — the ClickUp analogue returned one row). **Dedup is mandatory here and absent in ClickUp:** Slack retries any non-prompt-2xx (flagging `X-Slack-Retry-Num`), so `UNIQUE(subscription_id, event_id)` + `ON CONFLICT DO NOTHING` is load-bearing; Slack's `event_id` is the key ClickUp never provided. **Status contract differs from ClickUp's on purpose** — a non-2xx gets the *whole workspace's* URL disabled, not one user's webhook, so no-subscription/no-match/DB-blip all return 200 and only signature failures 401. Signature is `v0=` HMAC over `v0:{ts}:{body}` with a ±5-min replay window (ClickUp: bare-body HMAC, no window), checked **before** the `url_verification` challenge is echoed. Parsing gotchas: `reaction_added` carries its channel and message ts under **`event.item`**, not `event.channel`, so a naive read drops every reaction; `event.type` is `message` for **all four** of `message.channels`, `message.groups`, `message.im` and `message.mpim` (the tool enum uses *event* names, not subscription names) — and those four are **separate toggles on the Slack app**, so a workspace with only `message.channels` enabled records **nothing** for a DM while every local check reports healthy. `requiredMessageEventSubscription()` maps a channel to the one toggle it needs (from `conversations.info`'s `is_im`/`is_mpim`/`is_private`, falling back to the ID prefix — a `C` prefix no longer implies public), and both `subscribeToChannelEvents` and `debugChannelEventSubscription` name it; join/leave/topic subtypes are dropped as churn but `bot_message` is kept. `matchPattern` is a **literal case-insensitive substring**, never a regex (an LLM-supplied `.*` must not match everything). `enforceAccess` runs on **subscribe and on every history read** — rules are re-read per call, so stored history stops being readable if the channel is later denied. `reactions:read` was added to the scope seed for `reaction_added` (batched with `search:read`, one reconnect). Unlike ClickUp, `[slack-ingest]` log lines **never include message text** — envelope shape only, since a private DM's body has no business in stderr. Because stderr is invisible to an MCP tool, every delivery also leaves a durable breadcrumb in **`slack_ingest_health`** (`recordIngestDelivery`/`readIngestHealth`): one row **per outcome branch**, not append-only, because the ingest URL is public and unauthenticated — keying by branch bounds the table at ~13 rows forever and needs no pruner. `debugChannelEventSubscription` reads it back, which is the only thing that separates *"Slack has never POSTed here"* (Request URL unset/wrong) from *"handshake only"* (no event types enabled on the app) from *"rejected"* (signing-secret mismatch) from *"delivered but unmatched"* (wrong channel, or `matchPattern` filtered it). The health write is **best-effort and never changes the status Slack sees** — a non-2xx to protect a diagnostic counter would disable the workspace's Request URL, which is exactly backwards.
- **PeopleForce employee custom tables ARE exposed (v3):** repeating-row profile sections like "Dev Sprint participation" are readable via `listEmployeeTables` (definitions + each table's `internal_name`) and `getEmployeeTable(employeeId, internalName)` (a specific employee's rows). This partially lifts the "no participation" ceiling below — attendance/participation data a tenant models as an employee table (not a flat custom field) is now reachable per employee. Cells are typed (text/date/single_select `{id,value}`/multi_select `[]`/number/`hr_manager`/boolean); `formatEmployeeTable` renders them. Gotchas: the row-data GET is wrapped in `{ data: {...} }` (docs omit it — `getEmployeeTable` unwraps, else every table reads as empty); a table's `internal_name` is a **system slug**, often unrelated to the display name (e.g. "Dev Sprint participation" → `timeline`), so always get it from `listEmployeeTables` — never guess. `formatEmployeeTable` **dumps the raw payload** if it finds no `rows` array rather than falsely reporting "no rows" (a silent 0 would read as 0 participants downstream).
- **PeopleForce probation + the `status` filter (verified live 2026-08-18):** `probation_ends_on` is a **first-class, HR-set date** on the employee record — report it, never derive it from `hired_on` + 90 days (observed spans run 3 to 17 months, and it is extendable). Both `formatEmployee` and `formatEmployeeList` render it plus a **derived** `Probation:` state via `probationStatus()`. There is **no probation_status field** on the record — `active`/`inactive` is the only status the payload carries — and **no termination/dismissal date anywhere**, so "failed probation" is **not computable**: a departed employee reports `inactive`, never passed/failed, because terminated-during-probation cannot be told from terminated-years-later. `probation_failed` exists in `PROBATION_STATUS_VALUES` as a **reserved, never-emitted** slot; `probation_ends_on` survives offboarding, so if a termination date ever surfaces this becomes computable retroactively over existing rows. A null date reports `unknown`, never "passed" (a null is ambiguous — no probation configured vs cleared vs unfilled). **The `status` filter is an allowlist for a reason** (`EMPLOYEE_STATUS_VALUES`): only `active`, `probation`, and `inactive` behave. **Omitting `status` returns active-only, not everyone** — there is no "all", so full headcount = active + inactive in two passes. `status=probation` is a genuine server-side segment (returns just that cohort rather than the whole directory) — but it is **still paginated**: follow `metadata.pagination` and fetch further pages when reported. The 4-row result seen at probe time fit one page only because that tenant had 4 people on probation. Two values are rejected at the Zod schema: `on_probation` is **silently ignored** upstream and returns the byte-identical default directory (fails **open** — a typo yields plausible-looking wrong data instead of a 400), and `terminated` resolves to a **mixed active+inactive union**, not a termination cohort — use `inactive` for departed employees.
- **PeopleForce L&D analytics ceiling (verified live 2026-08-08):** the public API has **no** first-class entities for courses, enrollments, participation/attendance, completions, or L&D cost/hours — so "course completions", "participation counts", and "overall L&D investment" are **not answerable** from the connector *as dedicated objects* (but see employee custom tables above — a tenant may model participation there). In practice these live only as free text: Dev Sprints and courses show up as *objective titles / key-result prose* (e.g. "Dev Sprint complete…", "Professional Scrum Master course"), countable only by fragile string-matching. `listSkills`/`listEmployeeSkills` carry **no timestamps**, so skills-over-time needs you to snapshot into your own time-series store on a schedule (no retroactive history). `listObjectives`/`listKeyPerformanceIndicators` have **no date filter** (only `page`) — filter by `Period` client-side. There is **no bulk employee-skills endpoint** — a company-wide skills portfolio is one `listEmployeeSkills` call per employee (cache aggressively). Employee **custom fields are tenant-dependent** — do not promise specific field names (e.g. "Dev Sprint") in tool descriptions; many tenants have none. Objective/KPI `owner` may arrive name-only — `formatObjectiveList`/`formatKpiList` surface owner `id`+`email` when present to give a stable join key. KB article `body` can be a structured object, not a string (`formatKnowledgeArticle` serializes it); custom-field values can contain raw HTML (`formatCustomFields` strips tags/entities).
- **PeopleForce is the first service with REST writes:** all 41 read tools have a `GET` sibling under `/api/v1/peopleforce/*`, and four `POST` endpoints now cover the write tools (`createLeaveRequest`, `addCandidateNote`, `moveVacancyApplication`, `disqualifyVacancyApplication`). This widened `src/restCatalog.ts` from `method: 'GET'` to `'GET' | 'POST'` — the first catalogued write in the repo. **The consequence to know:** `createServiceAuth` accepts the *permanent dashboard API key* alongside the 5-minute `mintRestBearerForCurl` bearer, so that long-lived key can now mutate PeopleForce leave and recruitment state, where before it could only read. Bodies are validated with the MCP tools' own exported Zod schemas (`createLeaveRequestSchema`, `moveVacancyApplicationSchema`, `disqualifyVacancyApplicationSchema`, `addCandidateNoteSchema` in `src/peopleforce/server.ts`) via `safeParse` → 400 with `flatten()` issues; that reuse is the only thing stopping the REST and MCP surfaces drifting, so never hand-roll `if (!field)` checks here. **Path params override same-named body keys**, so a URL and a mismatched body can't disagree about which record is written. The move/disqualify routes re-read the application afterwards so the response is the record as it now stands. `disqualifyVacancyApplication` is consequential and **not idempotent** — repeating the call re-disqualifies, and a curl has no confirmation affordance. Every PeopleForce route (read and write) first resolves its token through `peopleForceToken()`, which 403s when the account has no PeopleForce connection: `createServiceAuth` otherwise falls back to a plain Google session and the client would go out with an undefined bearer. `peopleForceBaseUrl` is deliberately **not** required — it is optional and `PeopleForceClient` falls back to the default tenant base.
- **PeopleForce trend dashboards → snapshot collector, not the MCP:** because the API has no history/date-filtering, time-series analytics (Grafana) are built by the **snapshot collector** (`src/peopleforce/snapshot/`, `npm run snapshot:peopleforce`), which periodically writes the current state into append-only `pf_*_snapshot` Postgres tables stamped with `captured_at`. Querying across stamps reconstructs trends. It needs `PEOPLEFORCE_API_KEY` + `DATABASE_URL`, is single-tenant (one API key), and history is **forward-only** — start it early. Grafana reads the Postgres tables directly (see `src/peopleforce/snapshot/README.md` for schema, scheduling, and per-dashboard SQL). The MCP tools remain the path for ad-hoc/LLM queries. The collector also captures **employee custom-table cells** into `pf_employee_table_cell_snapshot` (participation — e.g. Dev Sprint attendance, multi-select expanded to one row per value), which powers participation counts + team trends over time; set `PEOPLEFORCE_SNAPSHOT_TABLES` (comma-separated `internal_name`s) to scope which tables, else all discovered tables are captured (`employees × tables` calls).

## Parameter Patterns

- **Document ID:** Extract from URL: `docs.google.com/document/d/DOCUMENT_ID/edit`
- **Text targeting:** Use `textToFind` + `matchInstance` OR `startIndex`/`endIndex`
- **Colors:** Hex format `#RRGGBB` or `#RGB`
- **Alignment:** `START`, `END`, `CENTER`, `JUSTIFIED` (not LEFT/RIGHT)
- **Indices:** 1-based, ranges are [start, end)
- **Tabs:** Optional `tabId` parameter (defaults to first tab)
