# Redmine — notes for Claude

## Known Limitations

- **Redmine is self-hosted, so the instance URL is per-connection data — not an env default:** every other connector here falls back `providerTokens.baseUrl → process.env.X_BASE_URL → a public default`; Redmine **drops the third term**, because there is no `api.redmine.com` and guessing a host would send the credential somewhere the user never named. `getRedmineClient` therefore throws on a missing base URL rather than papering over it, the dashboard's URL field is mandatory (the `isOutline || isRedmine` gate in `connectWithToken`), and the connect route is shaped like **Outline's**, not like the two-line `connectPasteToken` helper peopleforce/hubspot share — that helper stores only `{ access_token }`, which would produce a connection no tool can use. The URL is attacker-controllable input we send a credential to, so it runs through `checkBaseUrl` (`src/util/baseUrlGuard.ts`, hoisted out of `outline/connectToken.ts` so the two connectors cannot drift); there is still **no DNS-rebinding defence**, same documented gap as Outline.
- **Redmine auth is dual-mode, and the mode is inferred from the stored refresh token:** a pasted personal API key goes in `X-Redmine-API-Key` and works on every Redmine; an OAuth 2.0 access token goes in `Authorization: Bearer` and exists **only on Redmine 6.1+** (the Doorkeeper provider, feature #24808). Nothing stores the mode — `getRedmineClient` reads `session.redmineRefreshToken` and picks the header, and **`connectionHealth.ts` must pass the matching `authMode`**, or a perfectly healthy OAuth connection is re-probed as an API key and reported as a bad credential. The catalog is **env-gated like Outline**: `REDMINE_CLIENT_ID` + `REDMINE_CLIENT_SECRET` + `REDMINE_BASE_URL` turn on "Connect with Redmine", and without them the dashboard falls back to the paste form. That fallback is load-bearing, not garnish: the OAuth *application* is registered per instance at `<base>/oauth/applications` **by an administrator**, so one `client_id` serves exactly one Redmine — every other instance, and everything older than 6.1, can only paste a key. Doorkeeper expires access tokens (~2h) **and rotates the refresh token on use**, so `performRedmineRefresh` persists whatever comes back; keeping the old refresh token after a rotation is what silently kills the connection on the call after next.
- **Redmine OAuth scopes are permission names, and are not a security boundary:** the scope strings are Redmine's own permissions (`view_issues`, `add_issues`, …) plus `admin`, not OAuth-style verbs, and they must exist on the instance *and* be ticked on the registered application or the authorize request errors instead of rendering a consent screen. More importantly, Redmine defect **#44271** reports that issue edit, notes and delete are authorised from the resource owner's roles alone — Doorkeeper's `oauth_scope` filter does not apply on those paths — so a narrowly-scoped token can still write. Do not rely on the scope list to prevent a mutation.
- **A Redmine 401 and a Redmine 403 mean opposite things:** `403` means an administrator has the REST API switched **off** (`Administration → Settings → API → Enable REST API`) and the key is irrelevant; `401` means the credential itself was rejected. Redmine only split these in **4.1.0** (defect #30086) — before that a disabled REST API also answered 401, byte-identical to a bad key — so the 401 text names **both** causes. `validateRedmineToken` passes a *function* as `rejectedMessage` (the shared `validatePasteToken` accepts `string | (status) => string` for exactly this) rather than one message for both. Sending someone to re-issue a key that was never the problem is the failure this avoids — same class as the PeopleForce service-account-key wording.
- **Most of the Redmine API is officially Alpha, and lists cap at 100:** Redmine marks only **Issues, Projects, Users, Time Entries and News** as Stable; Attachments are Beta, and Wiki, Versions, Memberships, Relations, Categories, Enumerations, Custom Fields and Search are all **Alpha** and may change between releases — roughly 20 of the 46 tools sit on Alpha endpoints. Collections page with `offset`/`limit` (default 25, **hard cap 100**) and answer with `total_count`, so every list formatter prints `Showing N-M of TOTAL` plus the exact `offset` for the next page: a truncated list that does not say it is truncated reads as "that is everything". `formatTimeEntryList`'s hours sum is deliberately labelled **"Hours on this page"** for the same reason. Multi-valued filters are **one comma-joined parameter** (`issue_id=1,2,3`) — repeated keys are silently ignored, which reads as "the filter matched everything" — and unknown filter keys are dropped upstream rather than erroring, which is why `mergeCustomFieldFilters` refuses anything that is not `cf_<digits>`.
- **Redmine deletes are permanent and `deleteProject` cascades:** there is no recycle bin for any Redmine delete. `deleteProject` destroys every issue, wiki page, version and time entry in the project *and its subprojects*; `archiveProject` is the reversible option and the tool description says so. All seven delete tools carry `destructiveHint: true`. Note `listUsers` and `listCustomFields` are **admin-only** and 403 for ordinary accounts — use `listMemberships` to resolve user IDs without administrator rights.
- **Two Redmine guards that are easy to undo by accident:** (1) `RedmineClient.request` sets `redirect: 'error'`. Node's fetch strips `Authorization` across an origin change but **keeps custom headers**, so following a redirect would hand `X-Redmine-API-Key` to the `Location` host; `validatePasteToken` takes the same stance at connect time, which is also why a redirecting base URL never gets stored. (2) `checkBaseUrl` now requires **https://** by default (`requireHttps`), because every caller goes on to send a credential to that URL. The HTTPS check runs *after* the private-host check, so a loopback or RFC1918 address still reports the more specific "must point to a public host" — and that ordering is what keeps Outline's existing tests meaningful. This also tightened Outline: a plain-`http://` public instance URL is now refused at connect time.
- **Redmine's session cache identity is the token AND the base URL AND the auth mode**, not the token alone. A reconnect can persist a new `providerTokens.baseUrl` without the API key changing, and a token-only cache key would then keep handing back a session still pointed at the old instance. Same reasoning for `authMode`: it decides which header goes out.
- **Redmine redirects are now read, and sometimes followed, because `redirect: 'error'` made one broken route undiagnosable (ticket 1245xawe935):** `/time_entries.json` on one instance was redirected while `/issues.json`, `/projects.json` and `/users/current` all answered fine — so `listTimeEntries` was the only unusable tool, and the error said merely "the request was redirected away from <host> and was refused", which cannot distinguish **a proxy rewrite, an SSO hop to another host, a login bounce on one route, and a redirect loop**. Those four have four different fixes, so a message naming none of them left the endpoint broken indefinitely. `jsonApiRequest` now uses **`redirect: 'manual'`, never `'error'`** — the credential still never follows a redirect, but the `Location` is read *before* the call is refused. Four rules bound what gets followed: same-origin only, compared against the **original** request rather than the previous hop (hop-to-hop comparison lets a chain walk off-origin one innocent step at a time); **GET/HEAD only**, since a 301/302 replays a POST as a GET by spec and 307/308 replays it verbatim, and no diagnostic is worth a duplicate write; a **login path is never followed** (it answers 200 with HTML, which has no JSON content type and so resolves to `undefined` — a sign-in page reported as an empty result); and hops are capped at 3. **`RedirectRefusedError.status` is deliberately 502, not the 3xx** — `sendUpstreamError` passes `.status` straight to `res.status()`, so echoing a 302 would make our own REST client try to follow a `Location` we stripped the credential precisely to avoid; the real status stays on `.redirect.status`. On top of that, `RedmineClient` retries a **same-host login bounce** with the two other ways Redmine accepts a personal key (`?key=` then HTTP Basic `key:x`), because a reverse proxy stripping unknown `X-*` headers on one route breaks only `X-Redmine-API-Key` and looks exactly like this; it is GET-only, API-key-mode only, never cross-origin, and a **non-redirect failure on a retry stops the chain** (a 403 is Redmine having answered, which is better information than "it bounced"). The `?key=` form puts the credential in a query string a proxy may log — a real cost, accepted only because the header form has already failed on that exact route — and Redmine's bounce echoes the whole original URL back in `back_url`, which is why `jsonApiRequest` takes a `secrets` list and redacts it out of the message, the log and `.redirect`. **That redaction has to cover `target`, not just the body and the Location** — `target` prefixes every message this layer throws (redirect, timeout, non-2xx) and callers build it from the request path, so a 403 or a timeout on the `?key=` attempt would otherwise put the credential in the log and in the text shown to the model. `RedirectRefusal.resolved` is redacted for the same reason (it is reachable as `.redirect.resolved` from every caller), which is why the raw URL a follow needs is returned **beside** the record rather than read back off it. One more message trap: `sameOrigin` is false for a **scheme** change as well as a host change, so an `http://` base URL answered with a 301 to `https://` lands in the cross-host branch and would name the *same* host as "a DIFFERENT host" and blame an SSO proxy — it is split out and told to reconnect over https, and a prose `baseUrlHint` ("the Redmine instance", which several call paths pass) falls back to the generic wording rather than guessing.
- **A Redmine hours total from one page is wrong, so `listTimeEntries` grew `allPages` and a per-project fallback:** `limit` caps at 100, so "billable vs non-billable per person for nine months" computed from one response is short by whatever did not fit, with nothing in the output saying so — the old line said `Hours on this page`, which is honest but was being summed anyway. `allPages=true` (MCP and `?allPages=true` on the REST twin) pages to the end and labels the sum `Hours across all N entries`; it is **opt-in** so the single-page contract stays byte-identical for existing callers, and the single-page output now *points at the flag* so the complete answer is discoverable. The scan is bounded at **5000 entries** and says when it hit that, and it stops on a short page as well as on `total_count`, because a plugin omitting `total_count` would otherwise spend 50 requests re-reading nothing. The REST mode answers **`{ items, scan }` with no `page`** — there is no window to report and echoing one would invite paging an exhausted set — and `scan` is what tells a client whether the number is a total or a floor. Separately, `/time_entries.json` is a *single route* and can break alone, so when the workspace-wide list fails `allPages` falls back to `/projects/{id}/time_entries.json` **per project**; that is attempted only for a **route-level** failure (a refused redirect, 404, 405, 501, 5xx) and never for a 401/403/422, because those are Redmine having evaluated the request and scanning 100 projects to be told so 100 more times is a slower path to the same message. **It must use `listProjectTimeEntries`, never `listTimeEntries({ project_id })`** — the latter still requests `/time_entries.json` and scopes with a query parameter, so it re-runs the exact failure once per project, each one also paying the login-bounce retries (~300 requests to produce an empty result); the first version of this shipped that way and its test passed only because the stub keyed on `project_id` rather than the request path, so the test asserts the **path** now. Entries are **deduplicated by id**, because Redmine scopes a project query to the project *and its subprojects* when `display_subprojects_issues` is on (the default) — the same entry comes back under parent and child, and summing the concatenation reports hours **higher** than reality, which is worse than a floor; skipping child projects would be wrong in the other direction when that setting is off, and it is not readable through the API, so deduplication is the only form correct either way. If **no** project answers, the original error is rethrown rather than returned as an empty floor, which would read as "this workspace logged no hours". Its total is a **floor twice over** — one page of projects, and any project that failed individually — so it is labelled `FLOOR, not a total`, names the unreadable projects (a project contributing 0 because it could not be read must not look like one that logged no hours) and carries the reason the global list failed. `activityId` was added in the same pass because billable/non-billable is modelled as the activity on most instances, and Redmine **drops a filter key it does not recognise and answers with MORE rows**, so a mis-mapped name fails open — the caller gets every entry and reads it as the billable subset.
- **A Redmine 403 on `/time_entries.json` is FOUR causes wearing one status, and "the account lacks `view_time_entries`" was the one we asserted (ticket: redmine.gluzdov.com, non-admin account, 2026-10-15):** the reported instance 403s every time-entry call — workspace-wide, `userId=me`, per project, `allPages` — while the same account opens `/projects/329/time_entries` in the browser and sees every entry, and `listIssues`/`listProjects`/`listMemberships`/`getCurrentUser` all answer. **That report contains the evidence that disproves our own message.** Redmine authorises its HTML and JSON routes through the *identical* path — `find_optional_project` → `authorize_global` → `User#allowed_to?` (read raw from `app/controllers/application_controller.rb`; `timelog_controller.rb` has no separate check on `index`) — so for a GET the only differences are the credential (session cookie vs API key) and the response format. A page that renders for an account whose API call 403s therefore rules out **both** the permission and the project module, conclusively. A third cause is ruled out by Redmine's source too: `require_login` answers an unauthenticated `.json` request **401**, not 403, whenever the REST API is enabled and the action declares `accept_api_auth` (`timelog#index` does) — so this is not an anonymous request, and a disabled REST API would fail every call rather than one. What is left is a plugin or a proxy rule in front of this route, which is consistent with the instance running time-lock plugins and with its pre-v0.11.1 symptom (a bounce to `/login` on this route alone). `describeRedmineDenial` therefore **lists all four causes and names the browser test instead of picking one** — the same correction as the PeopleForce service-account-key wording, where the old message sent someone to re-issue a credential that was never the problem. **The regression that made it unusable was a class change, not a new block:** v0.11.1 turned the refused redirect into a 403 (the `?key=` retry gets a real answer), and `isRouteLevelFailure` listed 404/405/501/5xx and a refused redirect but **not 403** — so the per-project fallback built for exactly this instance stopped firing the moment its symptom changed shape. 403 is now in `isGlobalRouteWorthRetrying`, bounded rather than trusted: a **named project costs one extra request** (`/projects/{id}/time_entries.json`, which is also now reached on the **single-page** path, not just `allPages` — the default call had no fallback at all), and a workspace-wide scan abandons the sweep after `DENIAL_PROBE_LIMIT = 3` consecutive refusals with nothing collected, which keeps the old reasoning (being told no a hundred times is a slower route to the same message) while letting the one request that could prove it wrong happen. Three further details. The old guard skipped the fallback whenever `projectId` was set, reasoning that "naming one already uses a project-scoped query" — it does **not**: it adds `project_id` to `/time_entries.json`, the same route that just failed, so the one case with the cheapest way out was the one case with no way out. Evidence now travels **on** the error (`noteRedmineEvidence`, a Symbol read only by `mapRedmineError`, so this is not the ClickUp mistake of hiding a *status* where generic handlers cannot see it): the retry chain records that the `X-Redmine-API-Key` form was bounced to a sign-in page and the **same key** as a `?key=` parameter then got the 403 — a pair that says something about the route and nothing about a role, and which used to be discarded at the point it mattered. And `projectRoute` is deliberately **not** part of the floor condition that `perProject` sets: one project was asked for and that project answered in full, so its total is a total — what it changes is that the answer came from a different path, which is worth saying because it means the instance has a route someone should fix.

## Source Files

| File | Contains |
|------|----------|
| `src/redmine/server.ts` | Redmine tool definitions (46 tools: issues, projects, users, time entries, wiki, versions, categories, memberships, relations, lookups, search) |
| `src/redmine/apiHelpers.ts` | `RedmineClient` — API-key/Bearer HTTP client for the Redmine REST API, plus every formatter and the OAuth token-refresh plumbing |
| `src/redmine/ops.ts` | One exported `op*` function per tool body, so they can be driven against a stubbed client in tests (same split as HubSpot's `op*`) |
| `src/redmine/schemas.ts` | Zod parameter schemas for every Redmine tool; kept out of `server.ts` so `ops.ts` can type its args from them without an import cycle |
| `src/redmine/authMode.ts` | `resolveRedmineAuthMode` — which credential a connection holds, read by both the client and the health probe |
| `src/redmine/connectToken.ts` | Paste-token validation (`validateRedmineToken`) against `GET <base>/users/current.json` |
| `src/redmine/oauthCallback.ts` | Redmine (Doorkeeper) OAuth 2.0 code exchange + refresh grant |
