# Google Docs — notes for Claude

## Known Limitations

- **Comments and suggestions moved off the Drive API onto the Docs API, and the commentId changed id space with them (GA 2026-09-30, NOT yet exercised live):** the two limitations that used to head this list — comments arriving unanchored, and a resolved flag that did not persist — were **Drive API** ceilings, and `documents.batchUpdate` now has its own comment requests: `insertComment` (with a first-class `range`), `addCommentReply`, `updateCommentPost`, `deleteComment`, `deleteCommentReply`, plus `acceptSuggestion`/`rejectSuggestion`/`deleteSuggestion` and `writeControl.writeMode: 'SUGGEST'`. All ten comment tools and the four suggestion tools run on it; `drive.comments.*` is gone from this server. **Setting Drive's `anchor` was never a workaround and is actively worse** — Google's guide states the editors "treat these comments as unanchored comments", and a Drive anchor on a Doc renders the thread as *"Original content deleted"* — which is why the old `addComment` quoted the range by hand instead. **Resolving is a reply ACTION, not a field** (`post.commentAction: 'RESOLVE'`, or `REOPEN`), so there is no update-thread-status request and `content` is optional only for those two actions. **The readback is the other half of the win:** Drive answered a resolve it had dropped with 200, so the old op resolved-then-re-read; batchUpdate returns **`commentUpdateState`**, where `ALL_SAVED` is the only value meaning it happened — `ALL_FAILED_UNKNOWN_REASON` **throws** (a 200 that applied nothing is the silent no-op this repo refuses to report as success) and anything else is `confirmed: false`, never a claim either way. **Suggestion verdicts do NOT use that field** — they report through `suggestionResponses[].accepted/rejected/deletedSuggestionIds`, so confirmation is the id turning up in the matching list. Three things are not guessable. **Reading is one `documents.get` with three parameters that only work together** (`commentsViewMode: COMMENTS_VIEW_MODE_INCLUDED` + `suggestionsViewMode: SUGGESTIONS_INLINE` + `includeTabsContent: true`); omitting the first returns a document with no `comments` key at all, which reads as *this document has no comments*. **There is no per-comment GET** — `documents` exposes only `get`/`create`/`batchUpdate` — so `getComment` is `listComments` plus a find, both surfaces share `commentReads.ts`, and its 404 is **ours**, not Google's. And **the anchorId → range map lives on `DocumentTab.commentAnchors`, not on the Document**, which is the real reason tabs content is mandatory; `collectCommentAnchors` walks **child tabs recursively**, because a top-level-only walk loses the range of every comment in a nested tab and renders it as unanchored — the exact failure the migration exists to end. **The recursion is only half of it, and the other half was caught in review: a `fields` mask CANNOT recurse.** `tabs/documentTab/commentAnchors` selects that sub-path and nothing else, so `tabs[].childTabs` comes back **absent** and the recursive walk has nothing to walk — a green unit test proves nothing here, because a stub returns the whole payload and ignores `fields`. The mask is therefore built by `tabAnchorFields` in Google's grouped `tabs(...)` form with each level written out, to **4** levels against Google's documented limit of **3** nesting levels (and 100 tabs per document); one spare level is free and makes a raised limit degrade to a reported missing range rather than a silent one. **Assignment is create-only in one direction:** `insertComment.assigneeEmailAddress` assigns a new thread, while `assigneeEmail` on a reply 400s when "the parent thread is a CommentThread whose headPost does not have an assignee" — so `assignComment` can only REASSIGN, a thread created unassigned can never be assigned, and the 400 is rewritten to list all four documented causes rather than asserting one (same rule as `describeRedmineDenial`). Bodies cap at **2048 UTF-8 BYTES**, refused locally before the request and measured in bytes, not `String.length` — 600 emoji are 2400 bytes and 1200 UTF-16 units, so a length check would send what Google rejects. **No reconnect is needed** (`batchUpdate` takes `auth/documents` + `auth/drive`, both already in the seed), but **`googleapis` had to go 148 → 186**, which in turn forced `google-auth-library` **9 → 11**: googleapis-common requires `^11`, and leaving the direct dependency at `^9` installs two copies whose `OAuth2Client` types are structurally incompatible, which fails the build repo-wide rather than in the Docs files. Two deliberate asymmetries: `rejectSuggestion`/`deleteSuggestion` have **no REST sibling** (both discard proposed text irrecoverably and only `deleteCommentReply`/`updateCommentPost` were signed off for that plane), and a **suggestion thread's posts cannot be edited or deleted over REST** — path params are merged over the body, so one path can only mean one thread kind. **What is NOT verified: any of it, end to end.** Every claim above is read off Google's reference, the release notes and the published client types; there is no Google credential in this checkout, so the live run that would confirm anchoring, `commentUpdateState` and the `fields` mask (which keeps a one-comment read from dragging the whole body along) has not happened. Treat a 400 on the mask, a nested-tab comment still reporting no range, or an absent `plainTextQuote` as the first things to check. One asymmetry that IS deliberate: `addComment` reports `assigneeEmail` as **only what Google recorded** and the asked-for address separately as `requestedAssigneeEmail` — Google is not documented to echo an assignee on the insert response, and reporting the request as the stored state would be the same overclaim `confirmed` exists to prevent.
- **Google Docs text is sanitised before it reaches the transport:** `src/google-docs/textSafety.ts` is on every `readGoogleDoc` return path, `parseDocStructure`'s `textPreview`, and the REST twin at `/api/v1/docs/:documentId`. Three defects lived here. (1) `format: 'json'` sliced *already-serialised* JSON and returned the fragment, so anything that parsed it failed with `EOF while parsing a string` — a truncation bug that reads exactly like a transport bug; the partial now travels as a **string field inside a valid envelope**, the same contract `truncateJsonByLength` uses for REST. (2) Every truncation used `substring`, which cuts on UTF-16 code units and leaves a lone surrogate when it lands inside a surrogate pair — use `sliceSafe`, never `substring`, on anything headed for a tool result. (3) `textRun.content` was copied verbatim, including the `U+000B` Docs emits for shift-enter soft breaks (converted to `\n`, **not dropped** — it is a real line break) and the private-use chars it uses as inline-object placeholders. `assertTransportSafe` is the backstop: after sanitising it should never fire, and that is the point — if anything ever reaches the wire unencodable, the caller gets an error naming the offset and code point instead of a JSON parse failure inside their client, which is undiagnosable from the outside. Also note `format: 'text'` **used to drop all table text**: its `fields` projection named only paragraphs, so the table-walking branch was dead code; the projection now names tables too.
- **Every Google Docs write tool now has a REST sibling (19 POSTs), and the shape of that change was forced by one fact: `src/google-docs/server.ts` is the application entry point.** It imports `createWebApp`, so `webServer.ts` can never import it — not statically, and not with the `await import('../<provider>/server.js')` trick the Calendar and Sheets routes use, because in web-only mode that would boot an entire MCP server from inside a REST handler. So the schemas and ops live in **`writeSchemas.ts` and `writeOps.ts`**, which both surfaces import, and that is the pattern to copy for anything else the entry point owns. The ops exist for the usual reason — `webServer` would otherwise hold a second copy of the request building, which is the drift that bit Calendar — and each returns **data**, with the tool rendering the string and the route emitting JSON. Three things about the set are worth knowing. (1) **`editTableCell`, `fixListFormatting` and `findElement` are deliberately absent**: they are in `NOT_IMPLEMENTED` in `e2e/tools.ts` and throw, so an endpoint would advertise a 500. Every other read was already live, which is why this pass is writes-only. (2) **`batchUpdateDoc` subsumes nine of the individual endpoints** (`insert_text`, `delete_text`, `replace_text`, `format_text`, `update_paragraph_style`, `insert_table`, `insert_page_break`, `find_replace`, `create_bullet_list`), and they were shipped individually anyway, on purpose: generated clients and ChatGPT Actions drive named single-purpose operations far better than a discriminated-union batch body. (3) **`deleteRange` and `deleteComment` are `destructiveHint` and were exposed with explicit sign-off**, as POSTs to action paths (`/ranges/delete`, `/comments/{commentId}/delete`) with the sign-off in the catalog `notes`; `batchUpdateDoc` reaches `delete_text` regardless, which is why reading what a schema can express matters more than reading its annotation. **The entry point now boots only when not under the test runner** (`NODE_TEST_CONTEXT`), which is what let it be imported and tested at all — it had **773 executable lines at 0% coverage**, the worst file in the repo, because importing it started a server. The guard is phrased as *start unless testing* rather than *start if entry point* because the failure directions are opposite: a wrong argv check silently stops production from booting, while a wrong test check merely boots a server inside a test. Two contracts the responses keep that a naive passthrough would lose: `findAndReplace` reports **`occurrencesChanged: 0`** as a successful call that matched nothing, and the comment routes report confirmation from Google's `commentUpdateState`, not from the request (see the Docs-API comments entry at the top of this list). `POST /api/v1/docs/{id}/comments` was already served uncatalogued as ChatGPT-compat with three hand-rolled presence checks; its path and response keys are unchanged. `/api/v1/docs` joins `REST_LARGE_BODY_PREFIXES` for the append, import, batch and base64-image bodies. Note two **pre-existing** duplicate `operationId`s in the merged spec, left alone because renaming a published id breaks the clients that reference it: `readGoogleDoc` (the legacy `POST /docs/read` and the catalogued `GET /docs/{documentId}`) and `createFolder`.
