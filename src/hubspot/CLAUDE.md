# HubSpot — notes for Claude

## Known Limitations

- **HubSpot auth is OAuth 2.0 by default:** the catalog always advertises the OAuth endpoints, so the dashboard always shows "Connect with HubSpot" (the paste-token form is not shown). The client_id/secret come from `HUBSPOT_CLIENT_ID`/`HUBSPOT_CLIENT_SECRET` (a registered HubSpot app) and MUST be set on both the web service and the hubspot MCP service, or the connect flow has no client and fails. OAuth access tokens expire (~30 min) and are refreshed at tool-call time via `maybeRefreshHubSpotToken`. The paste-token path (`connectToken.ts`, the `/api/connect-token` hubspot branch) still exists server-side as an API-level escape hatch and skips refresh, but the dashboard no longer surfaces it.
- **HubSpot `searchData` not registered:** the reference's 16th tool did semantic search over a local FAISS vector index; this codebase has no vector store, so the tool is intentionally omitted rather than advertised as a throwing stub. The 29 registered HubSpot tools are implemented against the official HubSpot REST API. (`searchCompanies`/`searchContacts` cover the CRM search endpoint — the free-text/property lookup the omitted FAISS tool was reaching for.)
- **`getDeal` needs an ID only `getCompanyDeals`/`searchDeals` can produce:** a company record carries `num_associated_deals` — a plain **company** property, no deals scope — so a caller could see *that* a company had deals while having no route to their IDs. `getCompanyActivity` reads `/associations/engagements` (notes/calls/meetings, never deals) and `getActiveDeals` is a global recent-N with no company filter, so "show me this company's deals" dead-ended and the model reported it as **a permissions problem it was not**. `getCompanyDeals` closes it: associations v4 for the IDs, then `readDealsByIds` for the records. **Both sides page, at different sizes, and neither may truncate silently** — the association read follows `paging.next.after` 500 at a time (bounded at `ASSOCIATION_MAX_PAGES` = 10, i.e. 5,000 IDs) while the batch read chunks at HubSpot's **100-input cap**. Hitting the page bound returns `truncated`, which the op renders as "of N**+**": a bounded scan is a floor, not a count, and a truncated "Found 25 deals" would read as the company's whole pipeline. `searchDeals` is the by-name route, and widening `opSearchObjects` to a third label is why deals now share one search implementation with companies/contacts. **Do not diagnose a deal failure as missing scopes when other deal tools work:** `getActiveDeals` (`POST /crm/v3/objects/deals/search`) and `getDeal` (`GET /crm/v3/objects/deals/{id}`) gate on the *same* `crm.objects.deals.read`, so no scope grants one and denies the other.
- **HubSpot deals need the deals scopes + a reconnect:** deal tools (`getActiveDeals`, `getDeal`, `searchDeals`, `getCompanyDeals`, `createDeal`, `updateDeal`, `listPipelines`) and deal support in `getProperty`/`createProperty`/`updateProperty` require the `crm.objects.deals.*` + `crm.schemas.deals.*` scopes now in the catalog seed (`mcpCatalogStore.ts`). `seedDefaultCatalogs` re-seeds on boot and the upsert overwrites `oauth_scopes`, so the *catalog* is current after any deploy — but a **token is frozen at the scopes it was minted with**, so **already-connected users must reconnect/re-consent** before deal calls work; until then they 403. HubSpot tokens never expire in a way the dashboard flags, so such a connection looks perfectly healthy while failing every deal call — which is why the 403 is no longer reported as a bare "check your scopes". `parseHubSpotMissingScopes` (`hubspot/apiHelpers.ts`) detects it (`category`/`errorType` = `MISSING_SCOPES`, scope list from `context.requiredScopes` *or* the prose `requires any of [...]` — HubSpot sends one or the other, not both), and `withHubSpotClient` then spends one round-trip on `fetchHubSpotGrantedScopes` (`GET /oauth/v1/access-tokens/{token}`) so the message names **needed *and* granted** and points at the dashboard's Reconnect button — the Slack `formatScopeDetail` contract. Granted is the load-bearing half: it is the only way to tell *"the reconnect never happened"* from *"it happened and still didn't grant it"*, and in the latter case the message **stops telling the user to reconnect** (the HubSpot app config or the portal is the problem, not consent). The lookup is best-effort — a failed lookup degrades to the needed-only message, never to a second error. `listPipelines` returns each pipeline with its ordered stages (covering both list-pipelines and list-stages); use it to resolve `dealstage` IDs to names.
- **HubSpot engagement writes (`createNote`/`createTask`/`logCall`/`logMeeting`):** create the engagement standalone then attach it via a v4 **default** association (`PUT /crm/v4/objects/{type}/{id}/associations/default/{toType}/{toId}`), avoiding the direction-sensitive association-type-ID table. `hs_timestamp` defaults to now when omitted (the #1 documented create failure). `deleteEngagement(engagementType, engagementId)` is the cleanup counterpart — HubSpot's DELETE archives the engagement (off every timeline, recoverable from the recycling bin), which is what makes the create tools safely testable against a real portal; it needs the same contacts scopes as the writes. Success only claims a timeline attachment once the association call returns 2xx; a failed association is reported as an orphaned engagement, not a silent success. **Scopes:** these need no extra scope — HubSpot documents the notes, tasks, calls, and meetings APIs as requiring `crm.objects.contacts.read` + `crm.objects.contacts.write`, both already in the catalog seed. **Do not add `crm.objects.{notes,tasks,calls,meetings}.*`**: no such scope exists in HubSpot's public scope list, and an unknown scope makes the entire consent flow fail (every HubSpot connection, not just these tools). If an engagement write 401/403s, inspect the scopes actually granted on the token (`GET /oauth/v1/access-tokens/{token}`) instead of guessing a scope string.
- **HubSpot read/write contract:** reads that request explicit `properties` flag unknown keys HubSpot silently drops (`getCompany`/`getContact`, and `searchCompanies`/`searchContacts` via `formatObjectList`, which renders every requested property — unset ones as `(empty)` — and appends a ⚠ note listing keys HubSpot never returned, so "no value on this record" is never confused with "the tool doesn't return that"); `updateCompany`/`updateContact` re-read the record after PATCH so the response matches a fresh read (HubSpot's PATCH echo omits populated fields); `getCompanyActivity` emits ISO-8601 (engagement timestamps are epoch millis upstream). `getTickets` filters datetime props (`closedate`/`hs_lastmodifieddate`) with **epoch millis** — the search API 400s on ISO. Empty `{}` update payloads are rejected by the Zod schema before any API call. Email bodies in `getCompanyActivity` need the `sales-email-read` scope (in the OAuth scope list).

## Source Files

| File | Contains |
|------|----------|
| `src/hubspot/server.ts` | HubSpot CRM tool definitions (base URL via `HUBSPOT_BASE_URL`, defaults to api.hubapi.com) |
| `src/hubspot/apiHelpers.ts` | `HubSpotClient` — bearer-token HTTP client for the HubSpot CRM v3 REST API; OAuth token-refresh plumbing |
| `src/hubspot/connectToken.ts` | Paste-token validation (`validateHubSpotToken`) for the private-app access-token connect flow |
| `src/hubspot/oauthCallback.ts` | HubSpot OAuth 2.0 code exchange + refresh grant (`exchangeHubSpotOauthCode`, `refreshHubSpotToken`) |
