# GitHub — notes for Claude

## Known Limitations

- **GitHub is a port of the ARCHIVED reference server, and seven of its behaviours were bugs that read as successes — do not "restore parity" with it:** the 26 tools come from `modelcontextprotocol/servers-archived` (`src/github`, TypeScript, deprecated upstream) because the maintained `github/github-mcp-server` is Go and not portable; the Go server was used to cross-check behaviour. Departures, each listed in the `src/github/ops.ts` header: `pushFiles` moved the branch with **`force: true`**, discarding any commit pushed between our read and our write — it now fast-forwards only and reports the race (the Go server agrees: `Force: false`); it wrote every file as **mode 100644**, silently stripping the executable bit — existing modes are now read from the base tree, and a directory, submodule or symlink at a target path is refused; `createBranch` **guessed `main` then `master`** for the default branch — it is read from the repo now; branch lookups used **`git/refs/heads/<name>` (plural), a PREFIX match** that returns an array when other branches share the prefix — reads use the exact `git/ref/` form (the PATCH stays plural, GitHub's documented write path); `createOrUpdateFile` treated **any** failure of its existence check (401, rate limit, 5xx) as "file absent" — only a 404 means that now; `createRepository` sent `autoInit` verbatim where GitHub reads **`auto_init`**, so "initialize with a README" never worked; and `getPullRequestStatus` read only legacy commit statuses, **which GitHub Actions never writes**, so an Actions-only repo read as `pending` forever (the combined `state` is literally `pending` when `total_count` is 0) — check runs are read too, **best-effort**, because a fine-grained PAT reaches them only with the **Checks (read)** repository permission (GitHub's check-runs reference, read raw 2026-10-15 — an earlier note here claimed no such permission existed, which was wrong), so a token without it degrades to statuses with a note instead of failing the tool. **The verdict is `PASSING` only when every check was read:** a check-run read that failed, or a list longer than the one page fetched (100), answers `UNKNOWN` instead (`verdict: "unknown"` plus `unread` on the REST twin), because PASSING is what a model merges on and a failure it never saw would read as green. **GitHub answers several different failures with the same 403, and only a response HEADER tells them apart**, which is why `jsonApiRequest` grew `jsonApiRequestWithMeta` (headers on success, a non-enumerable `.headers` on a thrown error) and why `mapGitHubError` reads `x-ratelimit-remaining` (rate limit — wait), `retry-after` (secondary limit — slow down), `x-github-sso` (SAML — authorize the token for the org; URL quoted), `x-accepted-github-permissions` (fine-grained token missing a permission — named) and `x-accepted-oauth-scopes` vs `x-oauth-scopes` (needed **and** granted, with implied scopes such as `repo` ⊃ `public_repo` honoured; a token with no `x-oauth-scopes` header — fine-grained or GitHub App — is never told it holds no scopes). A **404 is worded "does not exist OR you cannot see it"** because GitHub never answers 403 for a private resource. GitHub **silently drops labels/assignees/milestone** on issue writes from accounts without push access (2xx, fields absent), so `createIssue`/`updateIssue` diff the response against the request and say what was not applied. Auth is env-gated dual mode like Outline/Redmine but with **no base URL** (github.com only — GHES would need a per-connection guarded base URL, not an env override that sends every token to one configurable host): `GITHUB_CLIENT_ID` + `GITHUB_CLIENT_SECRET` enable "Connect with GitHub", otherwise a PAT is pasted. The OAuth scope list is **`repo` + `read:org`** — `repo` is the only OAuth-App scope that reaches private repos, and coarse (write access to everything the user can write); `read:org` is read-only and exists solely so `/user/orgs` can list the account's organizations for Access Rules and `listOrganizations` (it reaches no organization DATA; it was added after launch, so connections made before it need a Reconnect to list private memberships) — and **`workflow` is deliberately NOT requested**, so `.github/workflows/` cannot be written through this connector (otherwise a prompt-injected model could rewrite CI to exfiltrate secrets); GitHub's refusal is rewritten to say so. The same callback serves a **GitHub App**, whose user tokens expire in 8h with a refresh token that **rotates on every use** — so `maybeRefreshGitHubToken` is single-flight per connection and persists the whole record (`updateMcpInstanceProviderTokens` replaces, it does not merge); for an OAuth App token or a PAT there is no expiry and it is a no-op. The token endpoint answers a failed exchange with **200 and `{"error": ...}`**, which `postTokenGrant` reports as "no access token" with the real reason in the log. **REST plane** (`/api/v1/github/*`, registered from the tables in `src/github/restRoutes.ts`): 14 GETs plus 5 POSTs — `createIssue`, `addIssueComment`, `pushFiles`, `createOrUpdateFile`, `mergePullRequest` — exposed with **explicit sign-off**, which matters because `createServiceAuth` accepts the permanent dashboard API key: that key can now commit code and merge pull requests on every repository the connected account can write to. Every route validates with the tool's own schema and calls the same `READS` builder or `perform*` function the tool uses. It does **not** use `sendUpstreamError`, which maps every 403 to "Permission denied": `githubRestError` answers a used-up rate limit **429 with Retry-After**, a rejected *stored* credential **502, never 401** (on this plane 401 means the caller's bearer), and an op's own refusal 400 unless it carries the upstream status it stands for (missing branch 404, lost push race 409). `mergePullRequest` answers **409 for GitHub's `merged: false`** so a pipeline checking only the status cannot read it as merged. `public/openapi-github.json` was generated from the same schemas and route tables. **Three behaviours found in live testing (2026-10-21):** `mergePullRequest` reads the pull request first, because GitHub answers a merge of an ALREADY-merged PR with success and the original merge commit — a repeated call reported "Merged #2 (merge)" for a PR squash-merged earlier, i.e. a merge that did not happen under a method never used; it now says it was already merged (REST: 200, `alreadyMerged: true`, `merged: false`) and refuses a closed-unmerged PR with 409. Writes under **`.github/workflows/` are refused before any call** (`assertNoWorkflowPaths`, 403), because without the `workflow` scope GitHub refuses the push with a **404 at the ref update**, which reads as "repository not found". And `parseLinkHeader` drops a `next` past GitHub's own `last`: `/commits` sent `next=2, last=1` when results exactly filled the page, so the footer said "Page 1 of 1. More results exist" and page 2 was empty. Known gaps, from the tool set chosen: **no tool reads issue/PR conversation comments** (`getIssue` reports the count only; `getPullRequestComments` is inline diff comments only) and nothing deletes a file.
- **GitHub Access Rules make one GitHub account usable for several workspaces — and they are a guardrail, not a boundary:** an OAuth or classic token reaches every organization the account granted, so "one connector per workspace" cannot come from the token; it comes from `providerTokens.accessRules.allowedOwners`, set in the dashboard's Access Rules dialog (Slack-style "Allowed Organisations" checkboxes, the connected account always included). **Absent rules mean unrestricted** (the Browserbase default, not Slack's fail-closed one), so every connector made before this kept working; null from the dialog **deletes** the key rather than storing `{}`, because the reconnect merge keeps any non-empty `accessRules`. Enforcement lives in **`GitHubClient.request`, the one place every MCP tool and REST route passes**: a `/repos/<owner>/…` path into an excluded owner is refused before anything is sent (`GitHubAccessDenied`, 403 on REST), a fork's destination is checked from the **body** (`organization`), search hits from `/search/{repositories,code,issues}` are dropped after the fact with `hiddenByAccessRules` reported (GitHub's query language has no "not these orgs", and a silent drop reads as "found nothing" — `total_count` stays GitHub's, so a page can come back short), and a hit whose owner cannot be read is dropped too. **Rename redirects are not followed under rules**: `/repositories/<id>` names no owner, so a repository transferred out of an allowed org would otherwise be readable through its old name. Rules are **re-read from storage on every call** (`loadGitHubOwnerPolicy`) because the stateful transport keeps a `UserSession` for its whole life, and a failed read **fails CLOSED** (503 on REST) — the opposite of Browserbase, because a user who saved rules asked for other workspaces to be unreachable. Two traps found building it: `performGitHubRefresh` used to write `{access_token, refresh_token, expiry_date}` as the WHOLE record, which would have wiped the rules on every 8-hour GitHub App refresh — it now reads the record and swaps only the token fields; and `githubRestError` matched `error.name === 'UserError'`, which a **subclass** fails (FastMCP names errors after their class), so an access denial was re-described as GitHub's own 403 — it uses `instanceof` now. Discovery (`src/github/ownerDiscovery.ts`) combines three sources because none is complete: `/user/orgs` (every membership, but **403 without `read:org`** and an **empty 200 for a fine-grained token**), `/users/{login}/orgs` (PUBLIC memberships only, no scope — the fallback that keeps a pre-`read:org` connection from listing nothing), and the owners of `/user/repos`, counted per owner. **That count is the diagnostic:** an organization the account is a member of that exposes **zero** repositories is almost always one that **restricts OAuth Apps and has not approved this one** — GitHub hides its private resources from the token, so allowing it in the rules changes nothing, and both the dialog and `listOrganizations` say so with GitHub's approval page (`/settings/connections/applications/<client_id>`, `oauthAppApprovalUrl`). The same restriction surfaced from a call (a 403 whose message names "OAuth App access restrictions") is rewritten by `forbiddenMessage` to name the organization and that page instead of "an organization policy may block it". Every discovery note is shown in the dialog, not only a truncated scan's — "private memberships are not listed" is precisely what explains an organization missing there. A capped scan is reported, saved owners keep their row even when unseen (so Save cannot silently revoke one), and an org can be added by name. **Switching the dialog from "All organizations" to "Only the ticked ones" — by the radio or by adding a name — starts with every reachable owner TICKED** (`restrictGithubRules`): it used to start empty, so adding a second organization by name unticked the first and Save cut the connector off from it, which read as "add by name does not work". **The connected account is added to the rules at SAVE time** (`includeConnectedAccount`, one `/user` call; a 502 and nothing written if GitHub cannot say who it is): the dashboard always ticks it, but the route is reachable without the dashboard, and a policy without it is incoherent — an organization-less fork and `POST /user/repos` go to that account with no owner to check, while an explicit read of its repositories would be refused. The OAuth callback no longer answers `already_exists` for a second connect of the same account — that is now the supported setup — and suffixes the name instead (`uniqueGitHubInstanceName`: "GitHub (me) 2"). For a limit GitHub itself enforces, a fine-grained PAT scoped to one owner remains the answer, and the dialog says so. **Deleting or reconnecting a GitHub connector revokes it on GitHub** (`src/github/revoke.ts`, called from `DELETE /api/instances/:id` and from `/connect/github?reconnect=` before the redirect), because GitHub otherwise remembers the authorization and skips its consent screen — the only place a user picks organization access — on every later connect. Two different revocations, and choosing between them is the design: `DELETE /applications/{client_id}/grant` is the only one that brings the consent screen back, and it **deletes every token the GitHub account holds for the app**; `.../token` revokes one token and leaves the consent skipped. Since several connectors per account is supported, the grant is revoked only when **no other connector of the same user belongs to the same GitHub account** (logins compared via `/user`; an account that cannot be identified counts as shared, because a wrong guess breaks a connector while the cautious one merely skips a screen), otherwise only the token, and the delete response says which (`githubRevoke`, shown in the dashboard). Other dashboard users connecting the same GitHub account are NOT checked — a revoked grant disconnects them too. Only OAuth tokens (`gho_`, `ghu_`) are revocable this way; a pasted PAT is not this app's, so the response tells the user to delete it on GitHub. Revocation is best-effort and never blocks the delete or the reconnect. Note GitHub's consent screen controls organization access **per app, not per connector**, and an organization owner's approval survives a revoked user grant — per-connector scoping is still the access rules' job. **REST does not choose a connector:** the dashboard API key and a `mintRestBearerForCurl` bearer both resolve to the USER, and `createServiceAuth` then takes `getMcpConnection(user, 'github')` — `ORDER BY connected_at ASC LIMIT 1` — so with several GitHub connectors every REST call uses the **oldest** one's token and rules, even when the bearer was minted from a narrower connector. This is documented (the catalog's per-service `REST_SERVICE_NOTES`, shown once in `docs/REST_ENDPOINTS.md` and by `listRestEndpoints` — not repeated on all 19 entries, which Sonar counted as duplicated new code and failed the gate on — plus the spec description and the dialog) rather than changed; making REST connector-aware would mean an instance-bound bearer, which every other service would need too.

## Source Files

| File | Contains |
|------|----------|
| `src/github/server.ts` | GitHub tool definitions (26 ported tools — repositories, files, branches, commits, issues, pull requests, search — plus `listOrganizations`), ported from the archived reference server |
| `src/github/apiHelpers.ts` | `GitHubClient` (over `jsonApiRequestWithMeta`, Link-header paging), the header-driven `mapGitHubError`, and call-time GitHub App token refresh |
| `src/github/ops.ts` / `schemas.ts` | One `op*` per tool (testable against a stubbed client) and the Zod schemas; the `ops.ts` header lists every deliberate departure from the reference |
| `src/github/accessRules.ts` / `ownerDiscovery.ts` | Per-connector owner allowlist (parsing, `GitHubAccessDenied`, the fail-closed per-call loader) and the dashboard's owner discovery; enforcement itself is in `GitHubClient.request` |
| `src/github/connectToken.ts` / `oauthCallback.ts` | PAT validation (`GET /user`), instance naming, and the OAuth code exchange + rotating refresh grant |
