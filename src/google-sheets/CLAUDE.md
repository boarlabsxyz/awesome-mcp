# Google Sheets — notes for Claude

## Known Limitations

- **Google Sheets and Calendar writes are on the REST plane now (8 POSTs), and three of them were already there uncatalogued — which is the interesting part:** `POST /api/v1/sheets/{id}/write`, `/append` and `POST /api/v1/calendars/{id}/events` have existed all along as **ChatGPT Custom Actions compat** routes, absent from `restCatalog.ts` and validating with hand-rolled `if (!range || !values)` checks. Presence-only checks are the whole problem: `values: "a,b"` — a string, not the 2D array the API needs — passed them and failed upstream as an opaque Google 400, and `attendees: "a@b.com"` reached Google as a string. Those paths are **unchanged and now catalogued**, validating with the MCP tools' own exported schemas (`writeSpreadsheetSchema`, `appendSpreadsheetRowsSchema`, `createSpreadsheetSchema`, `clearSpreadsheetRangeSchema`, `batchUpdateSpreadsheetSchema` in `src/google-sheets/server.ts`; `createEventSchema`, `updateEventSchema`, `deleteEventSchema` in `src/google-calendar/server.ts`). **The ops moved out with the schemas** — `performCreateEvent`/`performUpdateEvent`/`projectEvent` and `performCreateSpreadsheet`/`performBatchUpdateSpreadsheet` — because webServer held a *second* copy of each event body and projection, and the copies had drifted. `performUpdateEvent` keeps its pre-flight `events.get`: Google's `events.update` **replaces** the resource, so merging is what stops an omitted field being cleared. **Verb choices are forced by the catalog, not by taste:** the method union is `GET | POST`, so the event update is a **POST on the event path** (`updateCalendarEvent`) sharing one handler with the legacy **PATCH** that keeps its own uncatalogued id, and the two destructive writes are POSTs to **action paths** — `/ranges/clear` and `/events/{eventId}/cancel`. Those two (`clearSpreadsheetRange`, `deleteEvent`, both `destructiveHint`) plus `batchUpdateSpreadsheet` — whose operation list reaches **`deleteSheet`**, destroying a tab and every value on it — were **exposed with explicit sign-off**, recorded in the catalog `notes` so `docs/REST_ENDPOINTS.md` carries the warning. Operation types are **not** filtered on the REST side: narrowing them would make this surface diverge from the schema the MCP tool validates against, which is the drift the shared schema exists to prevent. `/api/v1/sheets` joins `REST_LARGE_BODY_PREFIXES` (5 MB) because bulk rows are the entire reason a spreadsheet write belongs on this plane and the global 100 kb would 413 the use case. Two response contracts worth keeping: `createSpreadsheet` answers **201 with `initialDataWritten: false`** when the seed write fails, since the file exists by then and an error status would invite a retry that makes a second spreadsheet; and `clearSpreadsheetRange` reports the range **Google says it cleared**, which can be wider than the one requested. The batch handler maps a per-operation rejection to **400, not 502**, matching on `err.name === 'UserError'` rather than `instanceof` — `webServer.ts` imports no part of FastMCP and pulling the framework in to narrow one error was not worth it (`FastMCPError` sets `name = new.target.name`, so the name is reliable). Finally, the catalog's `openapiOperationId`s were **aligned to the ids the published per-service specs already use** (`writeRange`, `appendRows`, `createEvent`), not to fresh names: a client generated from `public/openapi-sheets.json` calls those, and the merge in `buildRootOpenapi.mjs` prefers the per-service spec over its own stub, so a mismatch would have left the catalog naming an operation nothing answers to. Patched while there: those specs typed spreadsheet cells as `string`, while the Zod schema has always taken numbers, booleans and nulls.
- **A Google Sheets tab is 1000 rows and `writeSpreadsheet` will not grow it, which is what made "the REST write rejects every body" look like two bugs (ticket 1245xaweemn):** the reported half — `POST /api/v1/sheets/{id}/write` and `/append` answering `"range": Required, "values": Required` to a body that carried both — **was** the missing body parser in the entry above, fixed on main 2026-10-12 (PR #195) one day after the report and pinned by `restRoutes.mcpOnlyApp.test.ts`. The report's own control was **not** one: `batchUpdate` answering `"operations": Required` to a `{"requests": [...]}` body is the *same* empty-body signature, since that body has no `operations` key either — so "parsing works for batchUpdate and fails only for write/append" was two different bodies each missing the field its schema names, not evidence of a per-route difference. What remained is the real ceiling. **`values.update` — what `writeSpreadsheet` and `POST .../write` call — never grows a grid, while `values.append` (`appendSpreadsheetRows`, `insertDataOption: INSERT_ROWS`) does**, so the same 3,196 rows succeed or fail on nothing but which tool was reached for, and the fixed-range path died on Google's `Range (...) exceeds grid limits. Max rows: 1000` with nothing on this surface able to make room. **All of it verified live on the dev deployment 2026-10-14:** the ticket's own `/write` repro now answers `{"updatedCells":1,...}` (the parser fix is deployed), `POST .../write` at `Sheet1!A1500` on a fresh 1000-row tab answers `exceeds grid limits. Max rows: 1000, max columns: 26` — **as HTTP 500**, which is the status half of this fix — a 1,500-row `POST .../append` onto that same tab answers **200** and grew `rowCount` from 1000 to **2500** (Google over-allocates; it is not 1501), and the byte-identical `/write` that had just failed then succeeded. `batchUpdateSpreadsheet` now carries **`appendDimension`** (rows/columns at the end) and **`insertDimension`** (room in the middle) — indices there are **1-based inclusive**, like `columnWidth`/`rowHeight`, converted to Google's 0-based half-open range, and `inheritFromBefore` is refused at index 1, where Google answers a bare "invalid request" because nothing precedes the first row. Both `addSpreadsheetSheet` and the `addSheet` operation take **`rowCount`/`columnCount`**, and that sizing is **not a convenience**: `performBatchUpdateSpreadsheet` reads the spreadsheet metadata **once, before any operation runs**, so a tab created by `addSheet` has no sheetId yet and **cannot be named by a later operation in the same batch** — an `appendDimension` after it is not a working alternative (the openapi description asserting that same-batch sheets resolve was wrong, and is corrected along with the comment above the op). `gridProperties` is sent **only when asked for**, because an explicit `{}` is itself a request to size the tab and every pre-existing caller has been getting Google's 1000x26; the confirmation reports **the grid Google replied with**, not the one requested, since a clamped `rowCount` reported as created is what the next write would be sized against. `writeRange` keeps Google's own text (it names the real limits) and appends the part it never says — which of the three routes grows a grid — matched on the message because Google sends no machine-readable reason for it; and the REST `/write` route maps an upstream **400 to 400** instead of through `sendUpstreamError`, which knows only 404 and 403 and would report the caller's own range as a 500 "server problem, retry". Two gaps the ticket names are **deliberately left open**: `pasteData` (the `/write` + `/append` pair is the bulk path now, and at 5 MB it takes the whole 360 KB export in one request) and Drive **upload** — that plane is GET-only, so a CSV still cannot be imported as a sheet without passing through the model's context. The second is a multipart-upload feature, not a parameter, and is not in this change.
