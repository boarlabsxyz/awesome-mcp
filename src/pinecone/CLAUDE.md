# Pinecone — notes for Claude

## Known Limitations

- **Pinecone's Developer MCP is STDIO-only, so this connector reimplements its 9 tools — and in API version 2026-07 the surface they target is labelled LEGACY:** there is no hosted remote Developer MCP (the only remote one is the separate *Assistant* MCP, which serves one Assistant rather than indexes), so `src/pinecone/` speaks Pinecone's REST API directly, with the tool names and parameter shapes of `pinecone-io/pinecone-mcp` so a model that has used one works with the other. Three facts about that API are not guessable and were read raw from `https://docs.pinecone.io/llms.txt` → `pinecone-io/pinecone-api@main/2026-07/*.oas.yaml`. (1) **`X-Pinecone-Api-Version` is REQUIRED on every call** — omitting it is a rejection, not a default-to-latest — and it is pinned in `apiHelpers.ts` rather than read from env, because changing it changes the shape of `schema.fields`, which the classifier reads. (2) **The data plane is a PER-INDEX HOST** (`https://{index.host}/…`), and the only way to learn `host` is `GET /indexes/{name}` — so every search, stat and upsert costs a describe, which is exactly why classifying the index is free and `indexCatalog.ts` caches host+kind for 10 minutes. That cache is **not** a contradiction of `mcpProxyClient`'s no-caching rule: an `Mcp-Session-Id` is replica-affine, while `host` and `kind` are properties of the index and identical on every replica. (3) **The upsert body is `application/x-ndjson`, not a JSON array**, capped at 1000 records and 2 MB — `application/json` there yields a 400 that reads like a schema error. **The legacy label is the thing to re-check before extending this:** `create-for-model` and the Records API (`/records/namespaces/{ns}/{search,upsert}`) are what the 9 tools use, they are **not** marked `deprecated: true` and still work, but Pinecone directs new work to a **Documents API** (`/namespaces/{ns}/documents/*`) this connector deliberately does not call. So an index created in the Pinecone console today may well be a *document index*, and against one the Records API answers a bare 400 naming neither the index nor the reason. `indexKind.ts` therefore classifies from `schema.fields` first — **`semantic_text`** = legacy integrated (supported), a **`string`** field with `embed`/`sparse_embed` = document index, only the reserved **`_values`/`_sparse_values`** = vectors index — and refuses with the evidence and the API that *would* serve it. `semantic_text` is tested **first**, so the one supported kind can never be misclassified as one we refuse; and **`unknown` is NOT a refusal** — `schema.fields` is a young, moving surface and a classifier that fails closed on unfamiliarity breaks the connector on Pinecone's next release, so an unrecognised schema proceeds and the evidence is attached to whatever Pinecone answers. **`upsert-records` refuses a batch over 1000 rather than chunking it**, and that is a rule, not an ergonomic choice: a Records upsert is **not atomic across the NDJSON body**, so a rejection at record 500 of 900 leaves the first 499 written with no rollback — chunking would manufacture exactly the partial state this repo refuses to create, and a refusal has no side effect to clean up. For the same reason the per-record `_id` and `field_map` text-field check runs **locally, before the first byte**, using the field name the describe already gave us. The success report is synthesized (Pinecone answers 201 with an empty body) and must never say "indexed": embedding is **asynchronous**, so a search immediately after legitimately may not see the records. A **403 from `/rerank` is about the MODEL, not the key or any index**: the generic mapping explained every 403 as an index in another project, which is impossible on a path that touches no index, so `rerank` now raises its own message naming the model and pointing at plan availability (the `cohere-rerank-*` family is not on every Pinecone plan). Finally **`search-docs` sends no credential at all** — it proxies a public Pinecone documentation MCP at `prod-1-data.ke.pinecone.io` (tool `get_context`) — which is why it stays callable when the connection itself is broken: it is the tool that explains how to fix one. The connector is **seeded but hidden behind `PINECONE_ENABLED`**, exactly as `browserbase` and `peopleforce-v4` are (strict `=== 'true'`; a restart, not a deploy).
- **Pinecone access rules are a real boundary, not a guardrail — and the default namespace is the trap in them:** unlike Browserbase's domain rules, which can only bind `navigate` because `act` can click through to anywhere, every Pinecone tool that touches data **names its index and namespace as a parameter**, so `src/pinecone/accessRules.ts` binds all nine and the descriptions say so without qualification. They still do not limit the API key, which the user can point curl at. **`getRules` returns a discriminated `{loaded | unavailable}` state rather than `rules | undefined`, and that is the load-bearing difference from Browserbase**, which collapses a read *failure* into a read that found *nothing*. That is right there — both mean unrestricted — and wrong here: index and namespace rules fail **OPEN** (the stored default is unrestricted, so failing closed protects nothing while breaking every call), but `assertWriteAllowed` fails **CLOSED**, because a database blip must not silently un-flip a read-only switch; its message says the failure is temporary so it is never read as a configured restriction. That split is only safe because **both write tools call `assertWriteAllowed` as their FIRST statement** — `PINECONE_WRITE_TOOLS` is exported so a test catches a third write tool added without it. **The default Pinecone namespace is `__default__`, NOT the empty string — and shipping it the other way broke every records operation (reported live, fixed 2026-10-21).** The first version documented `""` everywhere, reasoning that `encodeURIComponent('')` yields nothing and so `/records/namespaces//search` was its address. That was inference about URL building, never verified: Pinecone requires a namespace to be 1-512 characters and refuses `""` with a 400 **naming `__default__`**, which is also what `describe_index_stats` reports. So `upsert-records`, `search-records` and `cascading-search` all failed for anyone who followed the docs. The translation now lives in **`wireNamespace`, at the single wire boundary in `apiHelpers.ts`**, so the MCP tools, the REST routes and anything added later cannot disagree about it; `""` is still accepted and translated rather than refused, because every description shipped telling callers to use it. Access rules canonicalise through `canonicalNamespace` so a rule **already saved** as `""` keeps matching. Note what this retires: the old reasoning that no sentinel could be safe (since any sentinel is a name a real namespace could have) — Pinecone settles that itself by reserving the name, so the collision cannot arise. `toNamespaceList` still must not drop the entry the way the domain-rules `toList` drops blanks, or the user watches their own checkbox un-tick. Index names match **exactly and lowercased** (not Browserbase's suffix match: an index name is a flat token with no `.` to anchor to, so `prod` would match `not-prod`), namespaces match **exactly and case-SENSITIVELY** (index names are normalised upstream; namespaces are opaque user strings where `Prod` and `prod` hold different vectors). Three behaviours carry their own reasoning: **`cascading-search` refuses the whole call** when any target is denied, because its output is one *fused ranking* where dropping a source silently changes the order, scores and `topN` cut of everything remaining and there is no honest way to label that partial — unlike Slack's `listChannels`, whose dropped rows are countable (and note its dedup key is **`(index, namespace, _id)`**, never `_id` alone: ids are unique only *within* a namespace, so keying on the id silently discarded one of two genuinely different records, which is how it shipped and was caught live; each document also carries `_index`/`_namespace` so a fused row can be attributed, and the output is a numbered list rather than the raw rerank payload, whose `index` field is a position in an array the caller never saw); **`list-indexes` hides denied rows but states outright that they exist**, with `describe-index` answering a hidden name with the **denial rather than a 404**, which makes it this connector's `diagnoseChannelAccess` and is why no tenth tool is needed (it leaks nothing, since the refusal is decided from the rules before any API call, and the message says so); and **`create-index-for-model` takes the ordinary index assert** — self-amendment is out on principle, and creating an index every other tool then refuses is a success that is useless, so the workflow is add the name to the allowlist first, which denies nothing while it does not exist. `rerank-documents` and `search-docs` are exempt from all three rules because they touch no index at all.
- **A cascading sub-search that could not be READ was reported as one that found NOTHING, and that is the whole bug (reported live, fixed 2026-10-21):** a cascading call returned 4 records all from `ns-a` and labelled itself `from 2 of 2 target(s)`, while `ns-b` — which held 3 records and returned all 3 when searched alone — contributed nothing; it did not reproduce on four re-runs, which is the signature of a transport-level empty rather than a query that matched nothing. The cause is one line: `res?.result?.hits ?? []`. **`jsonApiRequest` resolves to `undefined` for a 204 and for ANY 2xx whose content type is not `application/json`** — a proxy interstitial, a truncated body, an empty 200 — so "Pinecone could not be read" and "Pinecone found nothing" arrived at the call site as the same empty array, and the target was then counted as *searched*. `readSearchHits` (in `apiHelpers.ts`, shared by the MCP and REST `searchOne` so the two surfaces cannot disagree) now **refuses an unreadable answer**: `result` present with a `hits` **array** is the only shape that proves Pinecone answered the question, because an empty `hits: []` is positive evidence of zero matches where an absent envelope is no evidence at all (both fields are required in Pinecone's own schema, so a missing one is shape drift and is reported naming what arrived). `searchRecords`' return type is now honestly `| undefined` rather than the comfortable lie that let `?? []` look safe. **The second half is that "searched" and "contributed" are different facts**, and reporting only the first let a ranking missing an entire namespace read as covering it: every target's own contribution is now in the output (`Per-target contribution:` with hits, kept, and duplicates collapsed), a target that answered with nothing is **named** along with the three reasons that happens (query matched nothing / filter excluded everything / still being embedded) and pointed at `search-records` on that one target, and a target that failed is listed separately as `NOT SEARCHED` under the existing `PARTIAL RESULT` banner — so the two are never confused. REST carries the same findings as **data** (`targets[]`, `emptyTargets[]`), which matters because a client checking only `partial` saw `false` for exactly this case. One guard was also too eager: "reached none of the N targets" threw whenever nothing was found and *anything* had failed, so one failure plus one legitimately-empty target reported that nothing was reached — it now throws only when **every** target failed. Four smaller findings from the same report, all fixed: **`create-index-for-model` warns when the existing index differs** from the request — "already exists" was reported as an unqualified success even when that index embeds a different model or a different field, and **neither can be changed after creation**, so the caller then upserts records refused for a missing field, or embedded by a model they did not choose (reported, never refused: reusing the index is usually what was meant, not saying so never is; REST answers `configDrift[]`). **A cascading call naming a missing index now says which one** — `resolveIndexes` used `Promise.all`, which rejects with whichever describe lost the race and carries no index name, so a four-index call with one typo answered "no index by that name" without ever naming it and hid any second failure; it is `allSettled` now, listing each unresolvable name with its own reason (404 vs the 403 that an index **in another project** answers) and which names were fine. **`rerank.topN` above the candidate pool is reported** rather than silently doing nothing — reranking narrows candidates and cannot add to them, so the note is computed from the candidates that ACTUALLY reached the reranker (which is what makes it correct for cascading, where the pool is topK *per target*) and it names `query.topK` as the parameter that would help; the `topN` description no longer asserts a `<= topK` rule nothing enforces. And **scores are no longer rounded to 4 decimals unconditionally**: Pinecone's reranker scores the tail of a ranking in the 1e-5 range, where `toFixed(4)` renders every one of them as the identical `0.0000`, hiding both the ordering and that the tail was scored at all — `formatScore` keeps 4 decimals at or above 0.001 (so every ordinary score renders exactly as before) and switches to exponential with three significant digits below it, with an exact zero printed as `0` rather than dressed up as a measurement. Finally the namespace description **no longer says Pinecone rejects `""`**: true of the raw API, misleading here, since `wireNamespace` translates it — telling a reader the API refuses a value this connector accepts invites a workaround for a problem that does not exist on this surface.
- **The Pinecone REST plane enforces the same access rules as the tools, and two of its shapes are forced rather than chosen:** `/api/v1/pinecone/*` is registered from the tables in `src/pinecone/restRoutes.ts` (7 reads + 2 writes), each validated with the MCP tool's own Zod schema and running the same `perform*` guards — **including `assertWriteAllowed`**, because this plane accepts the **permanent dashboard API key** and a connection set read-only must refuse a curl exactly as it refuses a tool call. A rules denial answers **403 naming the rule**; a refusal this connector decided (wrong index kind, a record missing its text field, a batch over the cap) answers **400**, since the caller's request is wrong and a 500 would read as "retry, it is us". **`search-records` and `cascading-search` are POSTs despite being reads** — their bodies carry a metadata filter and rerank options that do not fit a query string. **The namespace is always in the BODY, never the path** — it sits beside the filter and rerank options it is used with, and moving it now would break every caller. (The original rationale, that the default namespace was the empty string and so could not be a path segment, was wrong: the default is `__default__`, see the namespace entry above; `src/pinecone/restRoutes.ts` records the correction.) **`upsert-records` was exposed with explicit sign-off** and is the bulk-load path the data plane exists for; `/api/v1/pinecone/indexes` is in `REST_LARGE_BODY_PREFIXES` so the 5 MB parser covers it, since the global 100 kb would 413 the entire use case. It answers **`accepted`, never `indexed`** (embedding is asynchronous and Pinecone answers 201 with an empty body), and `create-index-for-model` answers **200 with `created: false`** when the index already existed, because a 201 there would claim something that did not happen. `public/openapi-pinecone.json` is generated **from the Zod schemas**, so the published request bodies — including the 1000-record cap and the `__default__` namespace — cannot drift from what the routes validate.

## Source Files

| File | Contains |
|------|----------|
| `src/pinecone/server.ts` | Pinecone tool definitions (the same 9 tools as Pinecone's own Developer MCP, which is STDIO-only) |
| `src/pinecone/apiHelpers.ts` | `PineconeClient` — one client over three planes: control + inference at `api.pinecone.io`, and the per-index data host; also the camelCase-to-snake_case translation the SDK would otherwise do |
| `src/pinecone/indexKind.ts` | Pure index-kind classifier, its refusal messages, the per-record pre-validation and the NDJSON upsert builder with both caps |
| `src/pinecone/indexCatalog.ts` | The index host/kind TTL cache and `resolveIndex` — stateful, so kept out of the pure classifier and the stateless client |
| `src/pinecone/accessRules.ts` | Per-index / per-namespace allow-deny plus the read-only switch; pure `assert*`, with the split fail-open / fail-closed posture |
| `src/pinecone/docsProxy.ts` | `search-docs` over the shared MCP proxy client — a public, unauthenticated Pinecone endpoint, so it sends no credential |
| `src/pinecone/restRoutes.ts` | The REST data plane as data: one descriptor per endpoint, registered from a loop in `webServer.ts` |
| `src/pinecone/restOps.ts` | One `perform*` per route returning DATA where `ops.ts` returns prose; runs the same access-rule asserts |
