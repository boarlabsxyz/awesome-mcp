# ClickUp — notes for Claude

## Known Limitations

- **ClickUp Docs search is entirely client-side:** `GET /api/v3/workspaces/{id}/docs` has **no text-search parameter and no sort parameter**, and `limit` defaults to **50** (max 100, min 10) with opaque `cursor`/`next_cursor` paging. `listDocs` and `searchDocs` hit the *same* endpoint — `listDocs` is just the unfiltered call — so matching, paging, and ordering all live in `ClickUpClient` (`matchesDocQuery`, `sortDocsNewestFirst`, `searchAllDocs`) and both the MCP tools and the REST handlers share them; do not re-add a per-caller filter. `searchDocs` **auto-pages** the whole workspace (cap `DOCS_MAX_PAGES = 20` → 2000 docs) then sorts newest-first, and **always reports the scan extent** — a bare "No docs found" reads as "that doc doesn't exist" and is the bug this replaced (ticket 86cb5r680). Title matching is **token-AND, not substring**: every whitespace-separated word must appear, in any order, because titles are punctuation-heavy (`"AWESOME Sync"` must match `[AWESOME] Sync - 08/15/2026`). `parentType: 'EVERYTHING'` is **dropped rather than forwarded** — ClickUp accepts it but matches nothing, whereas omitting the filter returns the whole workspace; `SPACE`/`FOLDER`/`LIST` require `parentId` (Zod-enforced). `request()` has no 429 backoff, so a mid-scan rate limit returns partial results flagged `rateLimited` instead of throwing away the pages already fetched. Note `createDoc.parentType` is a **different** parameter (numeric 4/5/6 in the POST body) — do not unify it with `searchDocs.parentType`.
- **ClickUp returns the 25 newest task comments and NOTHING that says so, so `getTaskComments` pages to the end (ticket 1245xaweyh4):** `GET /task/{task_id}/comment` has no `limit`, no page number, and its response carries **no total and no cursor** — older comments are reached only by repeating the request with `start` (the `date` of the **last**, i.e. oldest, comment of the previous page) and `start_id` (that comment's `id`), until a page holds fewer than 25 ([ClickUp's own pagination doc](https://developer.clickup.com/docs/task-comments-pagination), which is the authority here — read it raw). The wrapper sent the first request only, so a 40-comment grilling log read back as its newest 25 and an agent summarising it wrote from the second half of the discussion as if it were all of it. **The reporter's "ClickUp's own paging parameters change nothing" was not evidence:** they tested through `GET /api/v1/clickup/tasks/{taskId}/comments`, whose handler passed `taskId` and nothing else — `start`/`start_id` were dropped before they ever reached ClickUp (the same "control that wasn't one" as the Sheets `batchUpdate` body). ClickUp honouring the cursor is now **verified live (2026-10-15)**: a task seeded with 40 comments read back all 40, oldest first, in `pagesScanned: 2` — so the reporter's claim was entirely an artifact of the dropped parameters. `stalled` is kept anyway, because that verification is one workspace on one day and an ignored cursor is indistinguishable from a working one except by its result: paging lives in `ClickUpClient.getAllTaskComments` (so the tool and the REST route share one implementation, as `searchAllDocs` does), it **deduplicates by comment id**, and a full page that adds nothing new is reported as *ClickUp returned the same page again* rather than looped on — without that, an ignored cursor would re-read the same 25 for all 40 pages and hand back a plausible-looking array of duplicates. **`complete` is the only field that means "this is the whole history", and it is set by exactly one thing: a short page.** Every other stop is named separately (`hitLimit`, `hitCap`, `stalled`, `rateLimited`, `cursorUnavailable`) with the resume cursor when one could be built, because "25 comments" and "25 comments and that is all of them" are the two cases this exists to separate — and an empty result from a *failed* scan is rendered as "NOT evidence that the task has no comments", never as `No comments on this task.` A task with **exactly 25** comments costs a second request and must not report `hitCap` for it: 25 is indistinguishable from a full page with more behind it without asking (verified live — 25 and 26 both return `complete` in `pagesScanned: 2`, and `allPages=false` returns the newest 25 as `complete: false` with a cursor that resumes exactly where it stopped: `limit=10` then its cursor yielded 10 + 30 = 40 with no overlap and no gap). A `limit` that lands on the last comment of a short page reports `complete`, **not** a cursor pointing at comments that do not exist. Both halves of the cursor are **refused in `execute`, not in Zod** — a Zod rejection surfaces as FastMCP's generic `InvalidParams`, and ClickUp ignores one half without the other and answers with the newest 25 again, the silent no-op that produced this bug report (identical reasoning to `resolveDueDateUpdate`). The REST route pages to completion **by default** (`?allPages=false` for just the newest 25, `?limit=N`, `?start=&start_id=`, `startId` accepted as an alias and refused when the two spellings disagree); it keeps the `comments` key and element shape it has always had and adds `scan` alongside, and it **refuses `page` and `cursor` by name** rather than ignoring them, since ignoring them is how a caller concludes paging does nothing. Order is ClickUp's **newest-first** and is now stated in the output, with `oldestFirst` to read a thread as it was written — flipping the default was rejected as a silent change to an existing contract, but an unlabelled reverse-chronological dump is what makes an LLM invert a Q&A narrative. **Threaded replies remain unreachable and that is a ceiling, not an oversight:** `GET /comment/{comment_id}/reply` is not exposed here and ClickUp gives it **no paging parameters at all** (verified in its OpenAPI: `comment_id` is the only parameter), so a tool for it would carry a first-page cap nothing could work around; `formatComment` prints `[N threaded replies, not included]` so a threaded discussion is merely *unread* rather than *invisible*. Note the route still reports an upstream 404 as a 500 — the pre-existing symbol-tagged-status defect below, deliberately left for the one pass that fixes all ~24 ClickUp GETs together.
- **ClickUp Doc images are self-hosted:** ClickUp has no image-upload API for Docs, and its SPA `/v1/attachment` route needs a browser session JWT this server doesn't have (ClickUp auth here is a per-user OAuth token). So `insertImageIntoPage`/`uploadClickUpDocImage` re-host the image themselves: fetch a public image URL (SSRF-guarded, 20 MB cap), store the bytes in Postgres (`clickup_doc_images`, `src/clickup/docImageStore.ts`), and embed `![](BASE_URL/images/clickup-doc/<id>)` via the existing markdown `editPage`. The serve route (`registerClickUpDocImageRoutes` in `webServer.ts`) is public/unauthenticated (ClickUp's renderer must fetch it; ids are unguessable UUIDs). Requires `DATABASE_URL` + `BASE_URL`; without Postgres the tools return a clear error. Input is a remote URL only (no base64 yet). **These images must never be stored `ephemeral`:** ClickUp's renderer re-fetches the URL on every page view, so an expiring blob would 404 the day it lapses — retention in `image_blobs` is opt-in per call site precisely so a global TTL can't break this path.
- **ClickUp task types are a bare number, and `listTaskTypes` exists because two of them are invisible:** `createTask`/`updateTask` take `taskTypeId` and send it as `custom_item_id`; `0` is the default "Task" (and is what resets a task back to one), `1` is Milestone. `GET /team/{id}/custom_item` returns **only the workspace's *custom* types** — the two built-ins are absent — so rendering that payload as-is reads as "this workspace has no Task type"; `listTaskTypes` prepends them and labels the counts (`2 built-in + N custom`). `formatTask` shows `Task type:` only when the value is a real type: `0` is the default and a line saying so on every row of a 100-task list carries no information (same rule as `Archived:` and `Top-level parent:`). It renders the **number**, not a name — ClickUp's task payload carries no type name, exactly like `parent` — so the description points at `listTaskTypes` rather than paying an N+1 lookup per row. Note ClickUp's own docs warn that **changing the type changes which custom fields apply**, so a `getTask` after a type change can return a different `custom_fields` set.
- **Re-parenting a ClickUp task goes through `updateTask.parentTaskId`, and the wrapper is most of the feature:** ClickUp's `PUT /task/{id}` has always accepted `parent`, and `ClickUpClient.updateTask` has always declared it — it was simply never populated, and FastMCP's `additionalProperties: false` meant an LLM could not pass it at all, so restructuring a hierarchy meant recreating tasks and losing their comments, history and custom fields (ticket 1245xawcebz). `parentTaskId` is **`.nullable()` and deliberately not `.min(1)`**: a Zod-level rejection surfaces as FastMCP's generic `InvalidParams` ("Expected string, received null"), which is the unexplained failure the parameter exists to replace — letting `null`, `''` and self-reference reach the body is what buys one clear voice for all of them. **ClickUp cannot clear a parent**, so null is refused rather than sent: a subtask can be moved between parents but never promoted back to top level. The re-parent path costs **three calls; a plain update still costs exactly one** and returns the byte-identical string it always did (there is a test on that). The **pre-flight `getTask(parent)` is the only source of the parent's name** — ClickUp's payload carries `parent` as a bare ID and no name anywhere — and it also yields the parent's list and turns an unknown ID into a message naming it instead of the raw 400 body `request()` would surface (it has no 400/404 special-casing). It is a **hard gate because nothing has been mutated yet**; the post-write re-read is the opposite, **best-effort**, because failing a move that did happen is worse than not confirming it. The re-read exists because **a stale PUT echo would let a silent no-op read as success** — the exact bug the ticket is about — so a mismatch is reported as `⚠ Re-parent did NOT take effect`, never as "updated successfully". The cycle check only sees the candidate's immediate parent and its root, so **a deeper cycle still relies on ClickUp's own rejection** (wrapped with the parent's name and list). The PUT is **atomic**, so a rejected parent loses the other fields in the same call — hence the tool description telling the model to re-parent standalone. **ClickUp emits no webhook event for a parent change at all** (`taskMoved` is a LIST move), so `getTaskEventHistory` can never show one and an empty result there never means "nothing was re-parented"; do **not** synthesise a row for it — it would capture only moves made through this MCP, leaving a ClickUp-UI drag invisible, so the history would be partial in a way that reads as complete (and `ClickUpTaskEvent` requires a `subscriptionId` FK a user without a subscription does not have). `formatTask` renders `Parent:`/`Top-level parent:` for **all five** task tools and the REST `Accept: text/plain` twin from one place; `Top-level parent` is suppressed when it merely repeats `parent` or the task's own id, so it only appears when nesting is deeper than one level. Finally, the uncatalogued **`PATCH /api/v1/clickup/tasks/:taskId` forwards `parent` raw and bypasses every guard above — on purpose**: those guards are error-message quality for an LLM, not integrity checks (ClickUp itself rejects null parents and cycles), and that route's caller is a dashboard API key holder. **Cross-list parents: unverified.** The tool reports the parent's list and the task's list after the move rather than asserting a rule; fold the observed answer into this bullet and the tool description once a real cross-list move has been run.
- **Clearing a ClickUp task due date needs `clearDueDate: true`, because `dueDate` CANNOT express it:** `dueDate` is a string and every path funnels it through `toClickUpTimestamp`, which refuses anything that does not parse — so `""` answers *"dueDate is not a valid date"* and there was no value at all that meant *remove the date* (reported bug: task 1245xawdeqp). That refusal is **correct and must stay**: an unparseable date yields `NaN`, `JSON.stringify` serialises `NaN` as **`null`**, and ClickUp reads a null `due_date` as *clear the date* and answers 200 — so accepting `""` or a typo'd ISO string would wipe the date and report success. Which is also why the field is a **separate boolean rather than making `dueDate` `.nullable()`**: a client sending null by accident would then destroy data in the other direction, and an explicit flag cannot be arrived at by accident. Passing **both** `dueDate` and `clearDueDate` is **refused with nothing written** rather than resolved by precedence — which one was meant is unknowable — while `clearDueDate: false` means *no change*, since that is what a templated body sends. The resolution lives **once**, in `resolveDueDateUpdate` (`src/clickup/restWrites.ts`), because the MCP tool builds its update body **inline** rather than through `buildTaskUpdateBody`, so the refusal and the null would otherwise exist in two copies that could disagree. **The clear is verified, like the re-parent above:** ClickUp answers an update it ignored with 200, and `formatTask` renders `Due:` only when a date is present, so a clear that did nothing differs from one that worked only by an absent line — and an absent line is not evidence. The PUT echo is trusted when it **agrees** with the request (so a clear costs exactly one call, and a plain update is byte-identical to before); only a **disagreeing** echo buys a `getTask`, because a stale echo and a silent no-op are indistinguishable from the echo alone and reporting a successful clear as a failure is as wrong as the reverse. REST reports it as three-valued `dueDateCleared` (true / false / **null = unconfirmed**), the same contract as `reparentConfirmed` and `addTaskToList`'s `confirmed`. Two things to know about the evidence base: ClickUp honouring an explicit JSON `null` to clear a task field is **verified live** (2026-10-12, `priority: null` on `PUT /task/{id}`), but **`due_date: null` specifically has not been exercised end-to-end** — which is exactly why the runtime verification exists rather than a comment asserting it. And **`start_date` has the identical gap**, deliberately left alone: the same flag would fix it and nobody has asked. Finally, the bug report's other two routes were **not** this bug — see the REST body-parser entry: the dev deployment predated that fix, so `{"dueDate": null}` on `/update` and native `{"due_date": null}` on the legacy PATCH both failed because **`req.body` never arrived**, not because null was dropped or ignored (a plain `{"name": "x"}` failed identically, which is the control that proves it).
- **Every ClickUp date must travel with its `*_date_time` boolean, and omitting it SILENTLY MOVES THE DATE (verified live 2026-10-13):** ClickUp pairs `due_date`/`start_date` with `due_date_time`/`start_date_time`, and the boolean defaults to **false** — which does not mean "no opinion", it means *discard the time of day*: ClickUp converts the instant to the **workspace's** timezone, keeps the **local calendar date**, and pins the result to **04:00 local**. `grep -rn due_date_time src/` returned **zero** before this, so every date this server had ever written was normalised that way. Proof: `2026-10-20T09:00:00Z` and `2026-10-20T18:30:00Z` both stored as `2026-10-20T01:00:00Z` (= 04:00 in a UTC+3 workspace), and the older probe's `2026-12-01T00:00:00Z` stored as `02:00Z` (= 04:00 at UTC+2 — same rule, different DST offset). **The severe half is not the lost time, it is that the date kept is the LOCAL one:** `2026-10-20T23:30:00Z` is 02:30 on the 21st in that workspace and came back as `2026-10-21T01:00:00Z` — a task due **a day later** than asked, with nothing in the 200 to say so. So any caller passing a UTC instant late in the UTC day got the wrong date. The flag is derived from the **input's shape**, never a new parameter (`inputCarriesTimeOfDay` in `src/clickup/restWrites.ts`): an ISO value with at least `HH:MM` sends `true`, a bare `2026-10-20` sends `false`, and a **Unix-ms value sends `true`** because it designates an instant — the caller chose millisecond precision and deciding they meant a whole day would be deciding for them. A separate parameter was rejected precisely because it could contradict the value beside it. `toClickUpDateValue` wraps `toClickUpTimestamp` (keeping all of its NaN/Infinity/range refusals) and returns `{ ts, hasTime }`; the two flags are **independent**, so one date may carry a time while the other does not. A **clear sends no `due_date_time` at all** — there is no date left for it to qualify and a flag beside a `null` is a contradiction ClickUp need not resolve (see [[clearDueDate]] above). Fixed on `createTask`, `updateTask`, `buildTaskUpdateBody`, `updateList` and `performUpdateList`; **`getTimeEntries`' `start_date`/`end_date` are deliberately untouched** — they are query filters on a read, not stored values, and the boolean has no meaning there. The **legacy native passthrough routes are also untouched by design**: their caller sends ClickUp's own snake_case body and can pass `due_date_time` itself. Two things this does NOT fix: a date-only value is parsed as **UTC midnight**, so in a workspace at a *negative* UTC offset its local date is the day before — fixing that needs the workspace timezone, which this layer does not have — and the behaviour change is **intentional and visible**: a caller who passed `09:00Z` and had been getting 04:00 local will now get 09:00Z.
- **ClickUp's Tasks in Multiple Lists answers a disabled ClickApp with 401, and the pre-flight is the feature:** `addTaskToList`/`removeTaskFromList` wrap `POST`/`DELETE /list/{listId}/task/{taskId}`, which ClickUp gates on the **"Tasks in Multiple Lists" ClickApp** — and when it is switched off the endpoints answer **401**, the *same* status ClickUp uses for a revoked token and for an ID it cannot resolve (`OAUTH_027` "Team not authorized", the same collision `updateTask`'s re-parent pre-flight documents). Nothing in the body separates the four causes, so the raw `ClickUp API error (401)` sends the user off to re-issue a credential that works perfectly — the reported bug. Since the response cannot be read to tell which it is, both tools **rule the others out first**: they `getTask` then `getList`, and only a 401 *after* both reads succeeded is attributed to the ClickApp (a non-401 rejection never is). Those reads are not garnish — they are also the only source of the two **names** the confirmation quotes, because both endpoints answer **200 with an empty body**. That empty body is also why every path re-reads the task afterwards, and why the verdict is **four-way, not two**: a failed re-read reports the *requested* state, a payload carrying no `locations` array reports *unconfirmed* (that absence is what a disabled ClickApp looks like), and only a payload that actually disagrees is reported as `⚠ did NOT take effect` — collapsing those would turn a share that did happen into an error. **`locations` is read as evidence only when present**, never as proof of absence, which is why the "already in that list" / "not in that list" shortcuts fall through to the API when the key is missing instead of fabricating a no-op. Two refusals are local and cost no write: ClickUp **cannot remove a task from its home list** (documented), and adding a task to its own home list is a no-op ClickUp accepts with 200, which would read as a successful share. `formatTask` renders `Also in lists:` for all five task tools and the REST `Accept: text/plain` twin from one place — without it these writes would be **unobservable** through this server — and it subtracts `task.list` rather than echoing `locations`, because ClickUp's schema ("Lists where the task has been added") never says whether the home list is among them and the subtraction is correct either way. Sharing a **subtask** needs the separate **"Subtasks in Multiple Lists"** ClickApp, so the 401 message names both. Custom task IDs are unsupported here (no `custom_task_ids`/`team_id` forwarding), and the two writes now DO have REST siblings (`POST /api/v1/clickup/tasks/{taskId}/lists/{listId}` and `.../remove`) which deliberately skip the `getTask`/`getList` pre-flight: a REST 401 is therefore **never** attributed to the ClickApp, because without those two reads there is nothing to rule out a revoked token or an unresolvable ID. They do keep the empty-body re-read, so `confirmed` stays three-valued. **Every ID is `encodeURIComponent`d before it enters a path** — a `?` or `#` would truncate it, so the pre-flight could validate one task while the write hit the prefix, with the tool reporting the ID it was handed either way. Finally, a failed write is only reported as "the task was not changed" when ClickUp **answered that it refused**: `request()` tags each error with whether ClickUp answered and with the status, and only a **4xx** is a refusal — an answered **5xx** joins timeouts and dropped connections in the "outcome UNKNOWN" branch, because a 500 can be raised after the write committed and a 502/504 is usually a proxy that never learned either. Claiming otherwise would be the same lie as reporting a silent no-op as success.
- **A task shared into a second ClickUp list is INVISIBLE when you browse by list unless `include_timl=true` (verified live 2026-09-29):** this is the half of Tasks in Multiple Lists that has nothing to do with the write path — `addTaskToList` can succeed and the task still reads back as absent. `GET /list/{list_id}/task` **excludes** tasks whose home list is elsewhere by default, so `listTasks` answered `No tasks found` for a list that demonstrably contained the task. `listTasks` therefore sends `include_timl` **on by default** (`includeMultiListTasks=false` opts out), on the plain and close-window paths and on the REST twin `GET /api/v1/clickup/lists/{listId}/tasks?includeMultiListTasks=false`. The default is read as **`args.includeMultiListTasks !== false`, not from Zod's `.default(true)`** — if the schema layer is ever bypassed, `undefined` must still mean ON, because the off direction fails by silently omitting tasks that are really there. Turning it on creates a second-order confusion the tool has to answer for: `formatTask` renders each task's **home** list, so a shared row's `List:` line names a list you did not ask about — `sharedTaskNote` counts those rows and names their home lists rather than leaving them looking like a bug. **The sibling endpoint has no such parameter and cannot be fixed:** `GET /team/{team_id}/task` (`filterTeamTasks`, and `searchTasks` on top of it) accepts **no `include_timl`**, so its `list_ids` filter matches a task's **home list only** — both the client method and the `listIds` description say so, and point at `listTasks` for a list's complete membership. Do not "fix" that by adding the parameter: ClickUp ignores unknown query keys, so it would read as support while changing nothing.
- **ClickUp cannot create or edit custom FIELD DEFINITIONS, and no amount of tooling here changes that:** the public API exposes only reads (`GET /list|space|folder|team/{id}/field`) and per-task value writes (`POST`/`DELETE /task/{taskId}/field/{fieldId}`) — which is what `getAccessibleCustomFields` / `setCustomFieldValue` / `removeCustomFieldValue` already cover. There is **no create-field, update-field, or edit-dropdown-options endpoint on v2 or v3**; a field (and every option on a drop_down) has to be created in the ClickUp UI first, and ClickUp's own feature request for it has been **open since September 2019** with an explicit staff confirmation that only get/set/remove of *values* is available. So a workspace cannot be provisioned or migrated field-schema-and-all through this server, and a tool claiming to do it could only be a throwing stub — the same reason HubSpot's `searchData` is omitted rather than advertised. Do not add one; re-check the feature request before assuming the ceiling has moved. The check to run is **`curl -s https://developer.clickup.com/llms.txt | grep -i field`** — ClickUp's own machine-readable endpoint index, which lists exactly the four reads plus set/remove value and nothing else. Read it raw: a summarised fetch of that file is how you end up trusting a paraphrase of an API surface. Because the request that reaches for this arrives as "create a field", the ceiling is stated **in the tool descriptions** of `getAccessibleCustomFields` and `removeCustomFieldValue`, not only here — a model that cannot see this file still has to stop offering it. Values themselves are confirmed working live (2026-09-29) for `drop_down`, `number`, `labels` and `url`, including re-setting a drop-down and clearing it.
- **`setCustomFieldValue` normalises the value before it writes, and `value` is a typed union rather than `z.any()` (ticket 86cba13av):** ClickUp stores every array-valued field type (`labels`, `users`, `tasks`, `list_relationship`, `attachment`) as a JSON array and answers a scalar with `{"err":"Value must be an array","ECODE":"FIELD_144"}` — and `z.any()` renders as the **empty JSON Schema `{}`**, which gives a client nothing to keep an array *as* an array, so the array arrived as its own JSON text and **every labels and users field in the workspace was unwritable from an agent** while text/number/drop_down wrote cleanly through the same call. The schema is now an explicit union (string | number | boolean | array | object) **and** `src/clickup/customFieldValue.ts` revives what still arrives serialised — both fixes, because neither alone covers a client that ignores the schema. **Reviving a string is only unambiguously safe once the field TYPE is known**: `["a"]` in a `text` field is a legitimate literal, so the tool looks the definition up first (`getTask` → its list → `getAccessibleCustomFields`) and the type decides. That lookup is spent **only when the value could still need it** (`needsFieldLookup`): an array of UUIDs, a number or a boolean is already in ClickUp's shape and still costs exactly one request, the same rule the re-parent pre-flight follows. It is **best-effort, not a gate** — a failed lookup degrades to reviving only a string that parses as a JSON array/object (never a scalar: `"12"` stays the string) and the response says option names were not resolved. Unknown label/drop-down options are **refused before the write**, naming the options that do exist, because the raw 400 names neither the field nor its options — and ClickUp has no API to create one, so an unknown option can only be a mistake. **A drop-down has two working value forms and the tool never downgrades one:** ClickUp documents the value as the option **UUID**, while this tool has always sent the **orderindex** — and that form is verified live (2026-09-29), so a UUID passes through unchanged, a number or numeric string stays an orderindex (the contract every existing caller was written against), and only a *name* is resolved, to the documented UUID. **A numeric string is an orderindex, never an option name**: the live `Triage Score` field has options *named* `1`..`10` whose orderindexes are `0`..`9`, so name-matching would write 2 where the caller asked for 3 — the collision is reported with the option's UUID instead of being resolved silently, and an orderindex **no option has** is refused rather than sent, since it can only set the wrong option or nothing. **`users` and relationship fields have two legal shapes, and the second is an OBJECT:** ClickUp documents an incremental `{"add": [...], "rem": [...]}` (either key alone) for People and `tasks`/`list_relationship` fields, which says something an array cannot — change membership without replacing it — so it passes through untouched in both the object and the serialised-string form. Wrapping it in an array, which is what array-valued handling does to any other object, would break a call that worked before any of this existed; an object that is neither shape is refused instead of wrapped. `attachment` is deliberately **not** in the array-valued set — its value shape here is unverified. Finally there is **no post-write re-read**: ClickUp answers this POST 200 with an empty body and omits a field from a task's payload entirely when it does not apply to that task's type, so a confirming `getTask` would report a successful write as a failed one (see the `applied_objects` bullet above).
- **A ClickUp task payload carries only the custom fields that apply to its task TYPE, and an omitted field is not an empty one (verified live 2026-09-29, task `1245xawcvnn`):** six fields were set on a task and `getTask` rendered exactly **one**. It was not an endpoint difference (`getTask` and `searchTasks` returned the identical set), not field type (two `drop_down`s, only one shown), and **not this repo's formatter** — the raw payload from `GET /api/v1/clickup/tasks/{taskId}` contained a `custom_fields` array of **length 1**. The cause is `applied_objects` on each field definition: it lists the task-type IDs the field applies to, and ClickUp drops from a task's payload every field whose list excludes that task's `custom_item_id`. Here the task was type `0` and only "Mode" listed `object_id: 0`; the other five were scoped to Project (1005), Tactic (1006), Operation (1007) and LI Snapshot (1011) — real types from `listTaskTypes`, which is what confirms `object_id` is a task-type ID. **The stored values are untouched and still match the `searchTasks` `custom_fields` filter**, because filtering runs server-side against the stored value and ignores applicability — so the filter matching while the render shows nothing is the signature of this, not a contradiction. That asymmetry is why the omission is so misleading: a field you can successfully filter on reads as unset. `getAccessibleCustomFields` is the **only** place this is diagnosable (the task payload has no trace of the missing field at all), so it now renders `Applies to task types:` per field — `all` when `applied_objects` is absent, since the scoping is opt-in — plus a trailing note, emitted only when something really is type-scoped, stating that an omitted field may still hold a value. `getTask`'s description says the same, because a model reading one task never sees the field list. Numbers are printed unresolved and `listTaskTypes` named, for the same reason `formatTask` prints a bare `custom_item_id`: the field payload carries type IDs and no names, and this tool has no workspace ID to resolve them with. Note this sharpens the older warning that changing a task's type changes which custom fields apply — it does not merely change which are *editable*, it changes which are **returned at all**.
- **ClickUp and Outline now have full REST planes (18 GET + 32 POST), and ClickUp carries TWO write-body contracts on purpose:** the pass that wired them found that `webServer.ts` had been serving **nine ClickUp POSTs plus five PATCH/DELETE routes all along, uncatalogued** as ChatGPT Custom Actions compat — invisible in every generated doc, forwarding `req.body` to ClickUp with no validation beyond the occasional `if (!listId)`. Three of those were already **destructive** (`DELETE /tasks/{id}`, `DELETE /lists/{id}`, `DELETE /tasks/{id}/fields/{fieldId}`), so the permanent dashboard API key could already delete ClickUp tasks and lists before any of this; cataloguing them made existing blast radius *visible* rather than new, which is what the destructive sign-off was actually about. **The load-bearing discovery is that those routes take ClickUp-NATIVE snake_case bodies** (`due_date`, `custom_item_id`, `comment_text`, `tid`, `parent`) and `public/openapi-clickup.json` has **published that contract with real request schemas** — while the MCP tools' parameters are camelCase translators. So the skill's usual "validate `req.body` with the MCP tool's own Zod schema" would have **400'd every generated client**: reusing the tool schema is only free when the route is new. The resolution is that the legacy paths keep their native contract (documented in the catalog `notes`, which is why the generated docs now say "native body forwarded verbatim"), and the camelCase equivalents live on **separate action paths** (`POST /tasks/{id}/update`, `/lists/{id}/update`, `/tasks/{id}/delete`) validated by `src/clickup/restWrites.ts` — one path must mean one body shape, or the two contracts are indistinguishable at the call site. **The anti-drift mechanism is a field OBJECT, not a shared schema:** each write's camelCase fields (with their `.describe()` text) live once in `restWrites.ts` / `restOps.ts` as `taskUpdateFields`, `createDocumentFields` and friends, and both surfaces spread them — the MCP tool adds the id as a parameter, the route takes it from the path, and the REST side adds the `.refine()` guards the tools express in prose instead (an empty body is a silent 200 no-op over curl). Sharing a whole schema could not work, because the two compose the same fields differently. `src/__tests__/restWriteSchemaSharing.test.ts` guards the two ways that rots: a field re-added to a tool's inline object instead of the group, and a lost `.describe()` — which nothing else would catch, since it breaks no shape. Both services register from a **table plus one generic handler** (13 ClickUp writes, 16 Outline reads, 9 Outline writes): past about four endpoints that is not a style choice, it is what keeps the `safeParse` 400, the status branch and the error mapping in one place and keeps new-code coverage above the Sonar gate (measured 88.9%). `insertImageIntoPage`'s ingest helpers were **hoisted** out of `clickup/server.ts` into `src/clickup/docImageIngest.ts` so the REST route reuses the guarded path rather than growing a second URL fetch — the URL is fetched *by this server*, so its per-redirect-hop SSRF guard in `fetchImageBytes` is the only thing standing between an API key holder and the internal network; neither service has a filesystem-path parameter and neither may grow one. Declined deliberately: ClickUp `subscribeToTaskEvents`/`unsubscribeFromTaskEvents` (no body, no pipeline, and they mint webhook secrets) and Outline `deleteDocument`/`deleteCollection` (the latter destroys every document in the collection with no undo). Note `POST /api/v1/clickup/spaces/{spaceId}` requires the **WORKSPACE** id in a path segment named `spaceId` — a published misnomer kept rather than fixed, and now stated in the catalog `notes`.
- **ClickUp tags its upstream HTTP status under a SYMBOL, so `sendUpstreamError` cannot see it — every ClickUp REST read answers 500 for a 404:** `ClickUpClient.request` throws `answered(new UserError(...), res.status)`, and `answered` stores the status on `err[CLICKUP_STATUS]` where only `clickUpErrorStatus(err)` can read it. `sendUpstreamError` looks at `err.code`, then `err.response.status`, then `err.status` — none of which ClickUp sets — so it falls through to **500 with the message "ClickUp API error (404): …"**: the status is in the prose and not in the status line, which is precisely the "flat 500 a client cannot route on" the REST skill warns about. Worse, because the thrown error *is* a `UserError`, a handler that also branches on `err?.name === 'UserError'` reports a **missing task as 400 "fix your request"**. The new ClickUp routes copy the symbol-tagged status onto `.code` before classifying, which is why they return real 404s; **the ~24 pre-existing ClickUp GET routes still do not and remain affected** — a known defect left alone rather than silently changing live behaviour on endpoints nobody asked about. Fix them together, in one pass, with the translation in a shared helper. Relatedly, a feature the deployment has not configured is **not** a fault: an unset `IMAGE_PUBLIC_BASE_URL` now throws a `ServiceNotConfiguredError` answered as **503**, because `getImagePublicBaseUrl` throws a plain `Error` and `sendUpstreamError` only special-cases 404 and 403 — everything else becomes a 500 telling the caller to report a bug when the fix is a config value.
