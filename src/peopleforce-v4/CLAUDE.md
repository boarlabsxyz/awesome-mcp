# PeopleForce v4 — notes for Claude

## Known Limitations

- **PeopleForce v4 is a SECOND connector (`peopleforce-v4`), not an upgrade of the first:** PeopleForce ships three non-overlapping key types — a **Company** key works on v1–v3, a **Career** key on published vacancies, and a **Service account** key (Settings → API keys, new with the v4 open beta) on `https://app.peopleforce.io/api/v4/*` and nowhere else. The v4 docs are explicit: "a service account API key only works against v4 - you can't use it to access v3, v2 or v1 APIs", and v4 rejects Company/Career keys in turn. One connection therefore cannot serve both surfaces, which is why `peopleForceV4AccessToken` is a **separate session field** and `getPeopleForceV4Client` deliberately does **not** fall back to `peopleForceAccessToken` — using the Company key there would turn a clear "not connected" into a provider 401. **v4 is a different set, not a superset:** it has no recruitment, leave requests/balances/types, knowledge base, skills, competencies, KPIs or employee custom tables (all still v2/v3 only), while adding termination dates + reasons, terminated-people/birthday/anniversary feeds, salaries, lifecycle records, review cycles/responses, Pulse surveys and compliance cases. Resources are renamed (`/api/v4/people`; `/api/v4/employees` is a **404**, verified live 2026-09-17) and the pagination envelope changed (`pages`→`total_pages`, `count`→`total_count`, `items`→`per_page`, and `per_page` is now the *requested* size rather than the current page's row count) — reading a pre-v4 field name off a v4 payload yields `undefined`, which renders as a missing total rather than an error. **The two silent-corruption behaviours are what the formatters exist to defeat:** a record outside the service account role's population is **omitted from a 200 with a shorter list**, not denied (so every count is a floor, an empty list gets the role-population note instead of "none found", and a **404 is reported as "does not exist OR outside this role's population"** — the response cannot tell them apart); and a field the role does not grant is **absent from the JSON rather than null**, so `formatPerson` diffs the payload against the documented field list with `in` and names what was withheld — rendering a blank would assert "this person has no manager" when the truth is "this key was not shown one". Writes are **additive only**: create/update for people and org structure. v4's delete, terminate and activate endpoints are **deliberately not exposed** (irreversible, and an MCP call has no confirmation affordance), and **department/position/job level/location/work type/manager are not writable at all** — v4's person create/update body has no such fields, so `personBody` drops them rather than letting a silent no-op read as success. Note v4 also still has **no per-vacancy API restriction**, the access-control gap the migration was evaluated for.
- **`peopleforce-v4` is seeded but hidden (`PEOPLEFORCE_V4_ENABLED`):** the row is still written on every boot with `isActive: false`, and *both* catalog backends filter on it (`WHERE is_active = true` / `catalog.filter(e => e.isActive)`), so it drops out of `/api/v1/catalogs` and therefore out of the dashboard's Add Tool list and the public integrations page. Set `PEOPLEFORCE_V4_ENABLED=true` to restore it — the seed upserts on boot, so that is a **restart, not a deploy**. The row is seeded rather than skipped on purpose: dropping it would orphan any existing connection, and `renderInstanceRow` degrades to the raw slug and a fallback icon when a catalog entry is missing — the row survives but `getMcpUrl` returns `''`, so Copy URL silently yields nothing. The comparison is strict `=== 'true'`; `PEOPLEFORCE_V4_ENABLED=yes` leaves it hidden. Note the `mcp:peopleforce-v4` scope stays in `scopeMap.ts` either way, so an already-connected instance keeps working while hidden.
