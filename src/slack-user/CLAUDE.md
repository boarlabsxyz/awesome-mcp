# Slack user server (slack-user) — notes for Claude

## Known Limitations

- **`listChannels` surfaces org-blocked channels rather than hiding them — and says when it could not check:** a channel blocked *only* by the organisation rule is listed with a `⚠ Not readable: shared with <Org Name> (ID)` warning, so the user can see which org to tick instead of watching the channel vanish. This is guarded by `passesNonOrgRules`: the row is surfaced **only if the user's own whitelist/blacklist/public-only rules would have allowed it**, otherwise a channel their patterns exclude would leak into the output on an org technicality. It applies on **both** paths now — previously only `verifyBackfilledChannel` (the org-unknown path) flagged, while a channel whose `shared_team_ids` were already in the `conversations.list` payload was silently dropped, which is exactly what made the tool description's promise false and made the two paths blame different rules (`whitelist-empty` vs `org-not-allowed`) for the same channel. Shared channels past `CHANNEL_INFO_BACKFILL_MAX` (25) are now marked `caution` (`⚠ Organisation unverified`) instead of rendering as ordinary readable rows — the trailing note alone was too easy to miss, and an agent planned work against channels every read then refused. **`warning` and `caution` are deliberately different:** `warning` means *we know this is blocked* and withholds topic/purpose; `caution` means *we could not check*, so nothing has denied it and its free text stays. The summary counts all three buckets separately.
- **Slack search is user-token-only and post-filtered:** `searchMessages`/`searchFiles` are registered on the **slack-user** server alone — `search.messages`/`search.files` reject bot tokens with `not_allowed_token_type`, so there is deliberately no stub on `slack-bot` (same reasoning as the omitted HubSpot `searchData`). They need **`search:read`**, added to the OAuth seed in `mcpCatalogStore.ts`, so **already-connected users must reconnect/re-consent** — which the dashboard only started allowing once `renderInstanceRow` grew a `showReauthorize` branch: `needsReconnect()` returns false for every non-Google provider (their tokens never expire), so a Slack row rendered *Copy URL* and no Reconnect button at all, and the tools' "reconnect from the dashboard" instruction pointed at an affordance that did not exist. Scope changes, not expiry, are what make re-consent necessary for these providers. Until they do, `callSearch` rewrites Slack's `missing_scope` into a "reconnect from the dashboard" message — carrying through Slack's own `needed`/`provided` fields (`formatScopeDetail` in `apiHelpers.ts`), because `provided` is the authoritative list of what the stored token actually holds and is the only way to tell a reconnect that never happened from one that happened and still didn't grant the scope. **Access control is the subtle part:** `enforceAccess` can't run (it takes one `channelId`; a search has none), and Slack's query DSL has no channel deny-list, so results are over-fetched and dropped client-side — `buildChannelFilter` (`src/slack-user/server.ts`) runs `fetchChannelMeta` + `assertAccess` + `assertDmMemberAccess` per distinct channel — the DM/group-DM check matters because without it a result from a DM with a non-allowed org, or a group DM holding a blacklisted member, would pass a filter a direct read rejects — memoised per call on top of the 5-minute meta cache, and **fails closed** on any error. A file is shown if *any* channel it's shared into is allowed. Because filtering happens after Slack pages, **page numbers are Slack's, not the filtered list's** — a page can come back empty while more matches exist, and the response says so plus how many results the rules hid (a silent drop would read as "Slack found nothing"). `search.*` pages by `page`/`count`, **not** by `cursor` like every other Slack call here. No REST sibling: the REST plane is hard-gated on `slackBotToken` precisely because access rules can't be applied there.
- **Slack list/read parity is one rule engine with one deliberate seam:** `listChannels` used to run a *second*, hand-written copy of the access rules that skipped the org check whenever `conversations.list` returned no team IDs — so a Slack Connect channel was advertised as available and then failed every read with an opaque team ID. `filterChannelList` is now a thin wrapper over `classifyChannelList`, which calls the same `assertAccess` a read calls; keep it that way. The one surviving difference is intentional and tested: a shared channel whose *list* payload names no org is `needsOrgBackfill`, not denied — "unknown" is not "denied", and resolving it costs a `conversations.info`. `listChannels` spends that call for up to `CHANNEL_INFO_BACKFILL_MAX` (25) channels, which is half the tier-3 minute budget because the same handler already pays for DM and group-DM member lookups; channels past the cap are reported, never silently unchecked. **`assertAccess` checks orgs before channel patterns**, so an org denial says nothing about whether the whitelist would have allowed it — anything that treats an org denial specially must call `assertNonOrgAccess` first, or a channel the user's own whitelist excludes leaks out on an org technicality. Denials are typed (`SlackAccessDenied`, with `reason`/`orgIds`/`patterns`) so the message text is no longer the API; the text itself is unchanged so callers that only print it are unaffected. Org-denied rows are **listed but flagged** (with `topic`/`purpose` withheld — structural facts about a channel the rules refuse to read are fine, its free text is not); rows denied by the user's own channel patterns are **hidden but counted**, because listing them would dump the names of channels they deliberately excluded. `diagnoseChannelAccess` is the generic answer to "why can't I see #x" — it was chosen over hardcoding an exemption for the support channel, which would have been spoofable by any workspace creating a channel with that name. Error messages name the org via `resolveTeamNames` (`src/slack-user/teamNames.ts`), whose cache is **keyed by token and bypassed entirely without one**: whether `team.info` succeeds depends on the calling token, so a bare team-ID key would serve one tenant's names to another. Expect the name to be missing — `team.info` on a foreign org usually fails even with `team:read`, and every org in a denial is by definition foreign — which is why the raw `T0…` ID is always kept alongside it: that ID is what the dashboard's Organizations checkbox is labelled with, and matching the two is how the user actually applies the fix.
- **Slack `allowedOrgs` is an allowlist you can only tick what the dashboard found:** the Organizations checkboxes in Access Rules come from `discoverConnectedOrgs` (`src/slack-user/orgDiscovery.ts`), and an org missing from that list has no checkbox, so it can never be allowed, so its channels and Slack Connect DMs stay invisible with no way for the user to say otherwise — **under-reporting here is a silent access failure, not a cosmetic one**, which is why every cap in the module is reported back as `orgDiscovery.truncated` + notes and rendered as a warning instead of quietly shortening the list. Discovery sweeps five sources because no single one is sufficient: `conversations.list` (public+private, workspace-wide, `limit: 1000`), **`users.conversations` for public+private** (member-scoped — the workspace-wide sweep is paged, so a workspace with more channels than `LIST_MAX_PAGES` covers burns its whole budget on internal channels and never reaches the shared ones; this is what made the partner org of a **private** channel the user was plainly in untickable, and a member-scoped set is bounded by the human rather than by the workspace, so it fixes the common case whatever the cap does), `users.conversations` for `im,mpim` (**conversations.list never returns DMs**, so an org you only Slack-Connect-DM was previously undiscoverable while `filterDmsByOrg`/`assertDmMemberAccess` still enforced `allowedOrgs` on it), `users.list` (every visible user carries its own `team_id`, including external counterparts), and `conversations.info` only for shared channels whose list payload named no team — the old code called `conversations.info` on **the first 10 shared channels and nothing else**. **Never read `shared_team_ids` directly:** Slack Connect puts the partner org in `connected_team_ids` (and `pending_connected_team_ids` before the invite is accepted) while `shared_team_ids` stays internal-only, so both discovery and enforcement go through `channelTeamIds()` (`src/slack/apiHelpers.ts`), which unions them — `includePending: true` for discovery (the org should be tickable early), **false** for enforcement (an unaccepted invite must not deny a channel that org cannot read yet). Enforcement is **all** the channel's orgs must be allowed, not `some`: `some` passed any channel that included your own workspace, which is always in `allowedOrgs`. Saved orgs are always returned even when nothing rediscovers them, because the dashboard rebuilds `allowedOrgs` from rendered checkboxes — a missing row used to mean opening the modal and pressing Save revoked an org nobody asked to revoke (the client now merges unrendered saved orgs too). **The same starvation then reappeared one step downstream, in the enrichment queue:** the shared channels whose list payload names no partner all go into one queue for `conversations.info`, and the workspace-wide sweep fills it before the member-scoped one does — so in a workspace with hundreds of shared channels the 100-call budget was spent on channels the user is not in, and the *private* Slack Connect channel they are in fell off the end with no checkbox (reported from the dashboard, the note reading `93 shared channel(s) beyond the first 100 were not inspected`). The queue is ranked by `infoPriority` — member+external, member, external, rest — **not by discovery order**, and `is_shared` alone does not mean external (an Enterprise Grid sets it for internal sharing too, so `is_ext_shared`/`is_pending_ext_shared` is what ranks a channel up). A failed lookup is **counted and reported**, not swallowed: 100 sequential tier-3 calls routinely hit a 429, and a lookup that never happened is indistinguishable from an org that is not there. Because every cap here can still leave a user with no checkbox to tick, the Access Rules dialog also takes a **workspace ID by hand** (`addOrgById`, `T…`/`E…`, shape-validated only — `team.info` on a foreign org fails by design, so confirming the ID would reject exactly the ones the control exists to accept); a manually added org is saved like any other and comes back as a `saved` row. Results are cached 5 min per `(instance, saved allowlist)`; the dashboard passes `tokenKey` (the Slack token, the same key the MCP server's `getTokenKey` returns) so names resolved here are reused by access denials and vice versa — omitting it bypasses the name cache entirely and re-spends the `team.info` budget on every open. `team.info` on a **foreign** team usually fails even with `team:read`, so an org shown as a raw `T0…` ID with `nameResolved: false` is expected, not a bug.
