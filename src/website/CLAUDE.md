# Web server, dashboard auth and the REST plane — notes for Claude

## Known Limitations

- **Email sign-up is verify-first — the account does not exist until the link is clicked:** `POST /api/auth/register` creates **nothing** in `users`. It bcrypt-hashes the password, parks it in `pendingRegistrationStore.ts` (Redis `pending_registration:<sha256(token)>`, 24h TTL, memory fallback bounded at 10k with oldest-first eviction), and mails a link; `GET /auth/verify?token=…` is **inert** — it only serves `public/verify.html`; the `POST /auth/verify` that page submits is what calls `createPasswordUser` and opens the session. **That split is load-bearing, not ceremony:** when a single GET both consumed the token and created the account, a mail scanner following the link (Outlook SafeLinks and friends do) completed the sign-up on the recipient's behalf and burned their link, so the human then clicked it and was told it was invalid. Single-use does *not* prevent that on its own — it only stops a second account — which is why the redemption had to move to a request a prefetch will not make. Consequences worth knowing: **the token is stored only as a SHA-256** (it is a bearer credential that can bring an account into existence, so a Redis dump must not yield a usable one — no work factor needed, the input is 32 CSPRNG bytes); it is **single-use, deleted before the record is returned**, so one link can never create two accounts; and unknown/used/expired all answer the **same** `/login?verify=invalid`, because distinguishing them tells a probe which tokens once existed. `/auth/verify` sets `Referrer-Policy: no-referrer` — the token rides in the query string and would otherwise leak in the Referer of anything the next page loads. **Registration answers 202 identically whether or not the address is taken** (`REGISTRATION_ACCEPTED`), replacing the old 409: the owner of a taken address gets a "someone tried to sign up" mail carrying **no link**, and the password is hashed on *both* paths so the ~190ms bcrypt cost cannot be used as a timing oracle for what the identical body refuses to say. Two sign-ups for one address mint two valid tokens (nothing exists yet to reject the second); whichever link is clicked first wins and the other gets `?verify=exists` — `DuplicateEmailError` is caught rather than 500ing, and the loser is **not** signed in, since that request never proved its password. **Mail goes through Resend over plain `fetch`** (`mailer.ts`, no new dependency; `RESEND_API_KEY` + `MAIL_FROM`). Without a key: outside production the message body — including the link — is logged so local sign-up works with no provider; in production `register` throws `MailNotConfiguredError` → **503, nothing created**, because reporting "check your email" for a mail that was never sent strands the user. `isMailConfigured()` requires **`MAIL_FROM` as well as the key in production** — the fallback sender is Resend's sandbox address, so a key-only deployment would otherwise pass preflight, build pending state, and fail at the provider (or send from an identity nobody chose). **Pending records are cleaned up when we fail, not when the user does:** an undelivered link's record is deleted (it is unreachable — the token existed only inside that request), and a redemption that fails for a non-duplicate reason *restores* the record, so a database outage does not spend a valid link. A `DuplicateEmailError` keeps it consumed, since an account now exists. Registration logs one **branch-independent line with no address**, so the logs cannot answer what the identical 202 refuses to. The per-email rate-limit bucket is what stops this endpoint being used to mail-bomb an arbitrary address.
- **`HIDE_GOOGLE_SIGNIN=true` hides the Google button, but never the route:** the `<!-- google-signin:start/end -->` block in `public/login.html` and `public/dashboard.html` is stripped **server-side** by `sendSigninPage` (`webServer.ts`), so the button never reaches the browser and cannot flash before a script removes it — which is why `/login` and `/dashboard` are read-and-sent rather than `sendFile`d. **`GET /auth/google` stays live on purpose:** a Google-created account has `password_hash` NULL, so the email form cannot sign it in (`verifyPassword` against a null hash is always false) and there is no password reset, so removing the route would strand every such account with no way back in. The flag is presentation only, defaults to showing the button, and is reported at `/api/config` as `googleSigninHidden`. The dashboard overlay's focus call falls back to the email link (`'.btn-google-login, .login-alt a'`) so hiding the button does not leave focus nowhere. Note `public/index.html`'s marketing copy still mentions signing in with Google — it is not behind the flag.
- **Dashboard login is Google OAuth *or* email+password:** `/login` serves `public/login.html` (both methods side by side) — it used to 302 straight to `/auth/google`, which is why `/connect/:mcpSlug`'s park-and-login now also targets `/login`. `POST /api/auth/register` + `POST /api/auth/login` (`webServer.ts`) back the email path; hashing lives in `src/auth/password.ts` (bcrypt cost 12). **Passwords over 72 bytes are rejected, not truncated** — bcrypt silently discards past that, so accepting them would claim a passphrase protects the account when only its first 72 bytes do. Login runs `verifyPassword` **unconditionally**, including for unknown emails and Google-only accounts (hash `null` → compared against a dummy hash of the same cost), so response time is not an account-existence oracle; registration no longer answers 409 at all — it returns the same 202 either way and mails the owner instead (see the verify-first entry above), so neither endpoint is an existence oracle. `src/website/loginRateLimit.ts` caps attempts per **IP and per email** (8 / 15 min, Redis-backed, in-memory fallback that is per-process); it counts **every** attempt, not just failures — counting failures alone lets one valid login reset the window — and the **email bucket is the load-bearing half**, since `trust proxy: true` makes `req.ip` spoofable via `X-Forwarded-For`. **The load-bearing change is that sessions are keyed by `userId`, not `googleId`:** ~13 dashboard routes did `getUserByGoogleId(req.session.googleId)` inline, which 401s for an account whose `google_id` is NULL, so all of them now go through `resolveSessionUser` (userId first, googleId fallback so pre-existing sessions survive their 7-day TTL). The `/connect/:mcpSlug` OAuth state carries `userId` for the same reason — without it a password user consents at the provider and gets "User not found" on the way back. `regenerateApiKey(googleId)` was **deleted rather than kept**: its `WHERE google_id = $1` matched zero rows for these accounts and reported "user not found" on a valid one; `regenerateApiKeyByUserId` is the only version. Linking Google to an existing password account (same email) **updates that row and keeps the password + `auth_method='password'`** — both the DB `ON CONFLICT (email)` path and its file-store sibling — because the dashboard renders `authMethod` verbatim and relabelling would announce the loss of a credential that still works. `password_hash` is deliberately absent from `DB_USER_COLUMNS` and from `UserProfile`, so nothing that serializes a user can leak a hash it never selected. **There is still no password reset**, but the blocker is gone: `mailer.ts` + `authEmails.ts` now exist, so a reset is a token store and two routes away rather than a mail-provider decision. Until then a forgotten password has no self-service path.
- **HubSpot and Redmine both have a live REST plane now (35 GET + 10 POST), and three things about it are not obvious.** (1) **Both must refresh at call time.** `hubspotRestClient`/`redmineRestClient` run `maybeRefreshHubSpotToken`/`maybeRefreshRedmineToken` before building a client, never `new XClient(token)`: HubSpot access tokens expire in ~30 min and Doorkeeper's in ~2h *and* rotate the refresh token on use, so a connection the dashboard reports as healthy 401s on every call without it — and the helpers are single-flight per connection precisely so two concurrent REST calls cannot race to spend the same rotating refresh token. Both helpers mutate the session in place, which is why `getXClient` is called *after*. (2) **Neither uses `sendUpstreamError` alone, and that is deliberate.** HubSpot keeps the missing-scope 403 path (`parseHubSpotMissingScopes` → `fetchHubSpotGrantedScopes` → `formatHubSpotScopeError`) because every deal endpoint 403s on a connection that looks perfectly healthy until the user reconnects, and a bare `Permission denied` sends them to inspect HubSpot user permissions instead; `granted` is still the half that separates *"the reconnect never happened"* from *"it happened and still didn't grant it"*. Redmine goes through `mapRedmineError` for the message because its bare status misleads three ways — 403 means *an admin switched the REST API off* about as often as *missing permission*, 422 carries Redmine's own `errors` list that a 500 would bury, and an unreachable self-hosted instance throws with **no status at all** (undici reports every one as the string `fetch failed`). Redmine's upstream **401 is mapped to 502, never echoed**: on this plane a 401 means *your REST bearer is bad*, so echoing it sends a client to re-mint a bearer when the stored Redmine credential is the problem. (3) **The Redmine GET routes `safeParse` their query params with the MCP tools' own schemas**, which is not ceremony: Redmine *drops* a filter it does not recognise and silently caps `limit` at 100, so an unvalidated query fails **open** — a bad tracker ID returns a plausible-looking wrong page rather than an error. `redmineCustomFieldFilters` (`src/util/queryParams.ts`) collects only `cf_<digits>` keys for the same reason, and **a `cf_<digits>` key given twice is a 400, not a dropped filter**: Express parses `?cf_3=a&cf_3=b` into an array, and since Redmine answers a *missing* filter with MORE rows, skipping it would hand back a wider result set than was asked for — the exact failure the guard exists to prevent. Redmine wants one comma-joined value. Relatedly, `GET /hubspot/tickets` clamps `maxRetries`/`retryDelay` to 3/2 where the MCP tool leaves them unbounded: `searchTickets` sleeps `retryDelay * (2^maxRetries - 1)` seconds, so the MCP bounds would let one curl hold a socket for ~8.5 hours, still retrying into the rate limiting that caused it, long after the client gave up. An LLM session has no socket to strand, which is why only the REST side is capped. The camelCase→filter mappings are **not** re-derived in `webServer.ts`: `issueListQuery`/`projectListQuery`/`userListQuery`/`timeEntryListQuery`/`searchQuery` and `issueBody`/`timeEntryBody`/`wikiPageBody` are exported from `src/redmine/ops.ts`, and HubSpot's `fetchCompanyActivity`/`fetchCompanyDeals`+`renderCompanyDeals`/`fetchTickets`/`fetchRecentConversations`/`fetchTicketConversationThreads`/`performCreateCompany`/`performCreateContact`/`performCreateEngagement` are exported from `src/hubspot/server.ts` — each is the half of an op that decides what the answer *is*, so the ops became thin formatters over them. Lists answer `{ items, page }` for Redmine and raw upstream JSON for HubSpot; every read also takes `?format=text`. Note `performCreateCompany`/`performCreateContact` return `created`, which is what makes 201-vs-200 honest — those calls are a **no-op** when a match already exists — and `performCreateEngagement` returns the association outcome as data because `attempted && !attached` is an **orphaned** engagement that exists on no timeline, and a 201 alone would read as an unqualified success (it is still 201: the record *was* created, so claiming otherwise would invite a duplicate retry).
- **The REST large-body parser has to be mounted before the global `express.json()`, not beside the handler.** `REST_LARGE_BODY_PREFIXES` (see the constant in `webServer.ts` for the current list) gets `express.json({ limit: REST_LARGE_BODY_LIMIT })` from `registerRestBodyParsers`, which every app factory calls before `registerRestApiRoutes`, thousands of lines from the routes it serves, because `body-parser` sets `req._body` on the first parse and every later `json()` skips it — **but the reverse does not hold**: a per-route parser registered next to the handler never runs, since the 100 kb global would already have 413'd the request. A Redmine wiki `text` or a HubSpot call transcript is exactly the large body those endpoints exist for, so the default would 413 the use case. A small `/api/v1` error handler sits right after the parsers (Express walks *forward* from a throw looking for a handler, so it must precede the routes) turning `entity.too.large`/`entity.parse.failed` into JSON — a curl client told this API speaks JSON cannot tell an oversize body from a proxy fault when it gets Express's HTML page back.
- **Which HubSpot/Redmine writes were left MCP-only, and why.** Exposed: HubSpot `createCompany`/`createContact`/`createDeal`/`createNote`/`logCall`/`logMeeting` and Redmine `createIssue`/`updateIssue`/`createTimeEntry`/`updateWikiPage` — each has either a long free-text body or a bulk-import-through-a-pipeline story. **Not** exposed, on purpose: every Redmine `delete*`, `archiveProject`, the project/version/category/membership admin creates, HubSpot `deleteEngagement`, the one-field `update*` records and the property-schema writes. Redmine has no recycle bin, `deleteProject` cascades into subprojects, and a curl has no `destructiveHint` affordance to confirm against. **The consequence to state out loud:** `createServiceAuth` accepts the *permanent dashboard API key* alongside the 5-minute bearer, so that long-lived key can now mutate HubSpot CRM records and Redmine issues, time and wiki content, where before it could only read them. `POST /api/v1/redmine/issues/{issueId}` is an **update** (Redmine itself takes a PUT there) because the catalog's method union is `GET | POST`.
- **A REST POST on a per-service subdomain had NO body parser, and the symptom named the wrong layer (fixed, ticket 1245xawe935):** `createMcpOnlyApp` — the factory `MCP_MODE=mcp` boots for every per-service Railway domain (`google-sheets.awesome-mcp.xyz`, …) — called `registerRestApiRoutes` but mounted **no `express.json()` at all**, so `req.body` was `undefined` on every REST POST it served. Every handler does `safeParse({ ...req.body, id: req.params.id })`, and spreading `undefined` yields `{}`, so the route answered **400 `"range": Required, "values": Required`** to a request that carried both — a message that accuses the caller and sends them to re-read the schema, when the schema was never the problem. GET routes worked throughout, which is what made it read as a proxy dropping bodies. The parsers are now one function (`registerRestBodyParsers` + `registerRestBodyParseErrorHandler`), and **every factory that calls `registerRestApiRoutes` must call it first** — that is the invariant to preserve, since the third factory was added without it and nothing failed until a POST was tried on a subdomain. The mount in `createMcpOnlyApp` is **scoped to `/api/v1`, not global**, and that difference is load-bearing: this app also proxies `/mcp` and `/sse`, and a global `express.json()` would consume those request streams before `http-proxy-middleware` could forward them — fixing the REST POSTs by breaking every MCP call on the same subdomain. `src/__tests__/restRoutes.mcpOnlyApp.test.ts` pins both halves; the parser assertion is the load-bearing one, because the auth gate answers 401 before a body is ever parsed, so a POST reaching 401 proves nothing on its own.
