# Slack (shared + slack-bot) — notes for Claude

## Known Limitations

- **Slack files need `files:read` + a reconnect:** attachments are surfaced as `📎 <name> — <mime>, <size> — file ID: F…` lines under each message (`formatFileRef`/`formatFiles` in `src/slack/helpers.ts`, reached through `formatMessage`, so both the bot and user servers get it from one place), and `downloadFile(fileId, channelId, format)` retrieves the content. `files:read` is in the OAuth scope seed and the dashboard's bot-scope copy, but **already-connected users must reconnect/re-consent** — without it Slack returns file stubs with `file_access: 'check_file_info'` (rendered as "file hidden") and `files.info` 403s. **Formats:** `url` (default) re-hosts images through `store()` (`src/images/imageBlobStore.ts`) and returns a `/images/<hash>.webp` link — that link is **public and unauthenticated**, so a screenshot from a private DM becomes publicly fetchable at an unguessable URL — which is why Slack stores it as **ephemeral** (`store(..., { ephemeral: true })`), making it eligible for removal after `IMAGE_RETENTION_DAYS` (default 30, `0` disables) so exposure is bounded rather than permanent. **That is a ceiling, not a guarantee:** blobs are content-addressed, so if the same bytes are also stored for a permanent use (a ClickUp Doc image) the shared row is promoted to permanent and the Slack URL keeps working — `fetch()` enforces expiry at read time so a lapsed row is never served, but a *shared* row simply hasn't lapsed; this is what makes `insertImageFromUrl` work (Google fetches it server-side), and it needs `DATABASE_URL` + `IMAGE_PUBLIC_BASE_URL`. `inline` returns a FastMCP `imageContent` block instead (capped at 1.5 MB, no image host needed) — the **only** tool in this repo that returns anything but a string. Text-like files come back as text; other types return metadata + permalink rather than an error. **Security:** `src/slack/fileDownload.ts` attaches the bearer token **per redirect hop and only for `*.slack.com`**, so Slack's redirect to signed S3 URLs can't leak the workspace token; a token missing `files:read` gets `200 OK` with an **HTML sign-in page** (not a 401), which is rejected explicitly so a login page is never stored as a screenshot. `downloadFile` requires `channelId` and verifies the file is really shared there (`fileShareTargets` unions `channels`/`groups`/`ims` **and** the newer `shares.public`/`shares.private` maps) — on the user server `enforceAccess` runs first, and the share check is what stops a file in a denied channel being laundered through an allowed one.
- **Slack `editMessage` is gated by authorship, not by scope:** `chat.update` needs only `chat:write` — already in the seed and already held by every Slack connection — so **no reconnect is required**, unlike `files:read`/`search:read` above. What it *is* gated on is who wrote the message: a user token edits only that user's own messages, a bot token only the bot's, and Slack refuses anything else with a bare `cant_update_message` that reads as a malfunction when passed through. `handleEditMessage` (`src/slack/helpers.ts`) maps that plus `edit_window_closed` (an **admin-set workspace limit**, not bypassable via the API — the message must be deleted and reposted), `message_not_found` (**timestamps are per-channel**, so a `ts` from channel A with channel B named fails this way) and `msg_too_long`. On **slack-user** `enforceAccess` wraps it exactly as it wraps `postMessage` — without that, a channel denied for reads and writes would still be editable; **slack-bot has no `enforceAccess` on any tool**, access rules being a slack-user mechanism. **The previous text is unrecoverable:** `chat.update` replaces it and the API offers no way to read the old version back (Slack still shows humans an "edited" marker), which is why the confirmation echoes what the message now says — it is the caller's only record, and an edit that hit the wrong `ts` would otherwise be indistinguishable from a correct one. **That echo is now the plain-text path only:** an edit carrying `markdownText`/`blocks` may leave no `text` at all, so it reports the block types Slack stored instead of quoting a body that is absent — see the **"Slack mrkdwn has NO list syntax"** entry. Annotated `readOnlyHint: false` **without** `destructiveHint`, matching every other in-place update in the repo (`updateCompany`, `editPage`, `writeSpreadsheet`); `destructiveHint` is reserved for deletes. The handler lives in the shared `helpers.ts` so `slack-bot` could register it in one `addTool` block, and **it now does** — it was left unregistered while "a bot editing its own status message" was a workflow nobody had asked for, and what changed is that it was asked for, as the way to fix a message's formatting after posting. **Everything about the content parameters, the combination refusals and the rich-content confirmation lives in the "Slack mrkdwn has NO list syntax" entry**, which is also where the newer error mappings (`invalid_blocks`, `msg_blocks_too_long`, `markdown_text_conflict`, shared with the two post paths) are recorded.
- **Slack link previews are per-message and post-time only, and `omitted` must stay distinguishable from `false`:** `postMessage`/`replyInThread` on **both** Slack servers take `unfurlLinks`/`unfurlMedia`, forwarded to `chat.postMessage` as `unfurl_links`/`unfurl_media`. Like `editMessage` this needs only `chat:write`, so **no reconnect is required**. The load-bearing detail is that a flag the caller did not set is **left out of the form body entirely rather than sent as `false`** — Slack's default is not one value: a **bot-token** post does not unfurl primarily text-based links by default but *does* unfurl media, while a **user-token** post behaves like a human's and unfurls both. So `false` for a flag nobody set would silently change behaviour on the bot path, and suppressing *every* preview takes both flags. `request()` already drops `undefined` from the body, but the spread in `chatPostMessage` is written out so that invariant does not depend on a filter several hundred lines away. The two parameters are defined **once**, as `unfurlParams` in the shared `helpers.ts`, because four `addTool` blocks register them and a description that drifts between the copies is wrong on one of them (same reason the ClickUp/Outline REST writes share a field object). **There is no readback:** `chat.postMessage` answers with `ts` and `channel` and carries no unfurl state at all, so the confirmation reports what was **requested**, explicitly saying so — otherwise a caller who passes `unfurlMedia: false` on a bot token and still sees a card cannot tell a flag that was ignored from one that was never sent. The note is emitted only when a flag was given, so the confirmation string is byte-identical for every pre-existing caller (there is a test on that). **`editMessage` deliberately does NOT take them:** `chat.update` accepts the parameters, but whether they strip an unfurl already rendered in the channel is **unverified** — clearing `attachments` is the documented route and nothing here has tested it — and a parameter that silently does nothing is worse than no parameter (the same call as the declined Browserbase `timeoutSeconds`). Two things this is not: it cannot retract a preview from a message already posted, and it is not the per-domain preview control, which is a **workspace admin setting** (Settings & Permissions → message display) no API caller can reach. No REST sibling, since the Slack write plane is hard-gated.
- **Slack mrkdwn has NO list syntax, so `- item` was arriving as a literal hyphen — `markdownText` is the fix and `blocks` the escape hatch:** `grep -rn "blocks\|rich_text" src/slack src/slack-user` returned **zero** before this, so `postMessage`/`replyInThread` could only send `text`, which Slack renders as mrkdwn — and mrkdwn has bold, italic, strike, code and blockquote but **no bullets and no numbered lists**. A reporter confirmed the rendered message contained no list elements at all. Both routes Slack offers were unreachable, and both are now parameters on **`postMessage`, `replyInThread` and `editMessage` on both servers**, defined once as `richTextParams` in the shared `helpers.ts` for the reason `unfurlParams` states (six registrations, so a drifting description is wrong on five of them). **`markdownText` → `markdown_text`** is the path to prefer and the one a model gets right: real markdown, converted to blocks by Slack server-side, 12,000-char cap, and it also buys headings, tables and task lists. **`blocks` → Block Kit**, for layouts markdown cannot express — a list there is a `rich_text` block holding `{type: 'rich_text_list', style: 'bullet'|'ordered', elements: [rich_text_section…]}`, with optional `indent`/`offset`. **The trap that would have shipped silently is `request()`:** it form-encodes every value through `String(v)`, so an array reaching it unserialised goes out as the literal `[object Object]` and Slack answers a bare `invalid_blocks_format` — `blocks` is therefore `JSON.stringify`d **inside `chatPostMessage`/`chatUpdate`**, never at a call site, and there is a mutation-checked test on it (`apiHelpers.test.ts`) because nothing else in that file sends a non-scalar. **Which combinations are legal lives in `resolveMessageBody`, NOT in Zod**, and for two independent reasons: a `.refine()` returns a `ZodEffects` with no `.shape`, which `slack-user/tools.test.ts` walks to assert every parameter carries a `.describe()`; and a Zod rejection surfaces as FastMCP's generic `InvalidParams`, the unexplained failure these messages exist to replace (identical reasoning to ClickUp's `resolveDueDateUpdate`). It refuses `markdownText` + `text` and `markdownText` + `blocks` — Slack's own `markdown_text_conflict` names neither argument — refuses an all-empty call rather than letting Slack answer `no_text`, and refuses **`blocks: []`**, which is not an omitted array: `chat.update` reads it as *remove every block*, so it would read back as a successful no-op. `blocks` **+** `text` is deliberately allowed and encouraged, `text` being Slack's notification and screen-reader fallback. Every refusal runs before the API call, so nothing is written. **Unlike the unfurl flags there IS a readback, and it answers the reporter's actual question:** both methods echo a `message` carrying the blocks Slack stored, so `renderNote` reports `Rendered as: rich_text (rich_text_list ×2)` — i.e. *did my list really become a list* — instead of reporting what was requested. An echo with no blocks is reported as the message *may* have been stored as plain text, never as a flat assertion: an absent `blocks` key is absence of evidence. The note is emitted only when one of the new parameters was passed, so all three confirmation strings stay **byte-identical** for pre-existing callers (there is a test on that). **`broadcast` → `reply_broadcast` is on `replyInThread` only** — the "Also send to channel" checkbox, previously unreachable — and is confirmed from `message.subtype === 'thread_broadcast'`, else reported as requested-but-unconfirmed. Slack's `chat.update` reference **does** list `reply_broadcast` ("Broadcast an existing thread reply"), contradicting the usual assumption that it is post-time only, but that is **unverified end-to-end and deliberately not forwarded**: the response does not echo it, so a no-op would be indistinguishable from success (the declined Browserbase `timeoutSeconds` call). Add it once someone has run it live. **`chat.update` strips blocks on a text-only edit** — Slack's documented rule is that omitting `blocks` while providing `text` *removes* them — so the `editMessage` descriptions warn about it; passing `markdownText`/`blocks` is also how a message already posted as plain text is converted into a list, which is what makes "fix the formatting afterwards" work. **`editMessage` is now registered on `slack-bot` too**, reversing only the "nobody has asked for it" half of the older note: the handler had always been in `helpers.ts` for exactly this, and `src/__tests__/slack/tools.test.ts` is a **new** registry guard for that server, which until now imported nothing and so checked no registration at all. The unfurl flags stay off `editMessage` — that refusal turned on there being no readback, which is precisely what `blocks` does have. All of this needs only `chat:write`, so **no reconnect**, unlike `files:read`/`search:read`; and there is no REST sibling, since the Slack write plane is hard-gated.
- **Slack channel events are a store you poll, not a push:** `subscribeToChannelEvents`/`listChannelEventSubscriptions`/`getChannelEventHistory`/`debugChannelEventSubscription`/`unsubscribeFromChannelEvents` (slack-user only) mirror the ClickUp task-event quartet, including its delivery model — the webhook writes rows and the caller asks later. **Nothing in this repo pushes to an LLM session**; what this removes is paging a channel and keeping your own watermark. **Slack has no per-user subscription API:** event delivery is configured once on the app (Request URL + `SLACK_SIGNING_SECRET`, both operator-set), so subscribing makes *no Slack call* — it inserts a local interest filter. Consequently there's no remote id, no per-row secret and no orphan-rollback, and **one Request URL serves the whole workspace**, so `handleSlackEventIngest` looks subscriptions up by `(team, channel)` and **fans out one delivery to N subscriber rows** (`findSubscriptionsForChannel` returns an array — the ClickUp analogue returned one row). **Dedup is mandatory here and absent in ClickUp:** Slack retries any non-prompt-2xx (flagging `X-Slack-Retry-Num`), so `UNIQUE(subscription_id, event_id)` + `ON CONFLICT DO NOTHING` is load-bearing; Slack's `event_id` is the key ClickUp never provided. **Status contract differs from ClickUp's on purpose** — a non-2xx gets the *whole workspace's* URL disabled, not one user's webhook, so no-subscription/no-match/DB-blip all return 200 and only signature failures 401. Signature is `v0=` HMAC over `v0:{ts}:{body}` with a ±5-min replay window (ClickUp: bare-body HMAC, no window), checked **before** the `url_verification` challenge is echoed. Parsing gotchas: `reaction_added` carries its channel and message ts under **`event.item`**, not `event.channel`, so a naive read drops every reaction; `event.type` is `message` for **all four** of `message.channels`, `message.groups`, `message.im` and `message.mpim` (the tool enum uses *event* names, not subscription names) — and those four are **separate toggles on the Slack app**, so a workspace with only `message.channels` enabled records **nothing** for a DM while every local check reports healthy. `requiredMessageEventSubscription()` maps a channel to the one toggle it needs (from `conversations.info`'s `is_im`/`is_mpim`/`is_private`, falling back to the ID prefix — a `C` prefix no longer implies public), and both `subscribeToChannelEvents` and `debugChannelEventSubscription` name it; join/leave/topic subtypes are dropped as churn but `bot_message` is kept. `matchPattern` is a **literal case-insensitive substring**, never a regex (an LLM-supplied `.*` must not match everything). `enforceAccess` runs on **subscribe and on every history read** — rules are re-read per call, so stored history stops being readable if the channel is later denied. `reactions:read` was added to the scope seed for `reaction_added` (batched with `search:read`, one reconnect). Unlike ClickUp, `[slack-ingest]` log lines **never include message text** — envelope shape only, since a private DM's body has no business in stderr. Because stderr is invisible to an MCP tool, every delivery also leaves a durable breadcrumb in **`slack_ingest_health`** (`recordIngestDelivery`/`readIngestHealth`): one row **per outcome branch**, not append-only, because the ingest URL is public and unauthenticated — keying by branch bounds the table at ~13 rows forever and needs no pruner. `debugChannelEventSubscription` reads it back, which is the only thing that separates *"Slack has never POSTed here"* (Request URL unset/wrong) from *"handshake only"* (no event types enabled on the app) from *"rejected"* (signing-secret mismatch) from *"delivered but unmatched"* (wrong channel, or `matchPattern` filtered it). The health write is **best-effort and never changes the status Slack sees** — a non-2xx to protect a diagnostic counter would disable the workspace's Request URL, which is exactly backwards.

## Source Files

| File | Contains |
|------|----------|
| `src/slack/server.ts` | Slack bot-token tool definitions (`slack-bot` slug, `xoxb-`) |
| `src/slack/helpers.ts` | Shared handlers + rendering for both Slack servers — `formatMessage`/`formatFileRef`, `handleReadChannelHistory`, `handleDownloadFile`; also the ONE definition of each write's shared params (`unfurlParams`, `richTextParams`, `broadcastParam`), the content-combination refusals (`resolveMessageBody`) and the Slack-echo readback (`renderNote`) |
| `src/slack/apiHelpers.ts` | `SlackClient` — form-urlencoded POST client for the Slack Web API; `SlackFileRef`, `fileShareTargets` |
| `src/slack/fileDownload.ts` | Authenticated binary fetch for `url_private_download` — per-hop SSRF checks, Slack-host-only bearer, HTML-login-page detection |
| `src/slack/eventStore.ts` | Postgres layer for channel-event subscriptions + captured events (`slack_event_subscriptions`, `slack_channel_events`, `slack_ingest_health`); `findSubscriptionsForChannel` is the fan-out lookup, `readIngestHealth` the delivery-evidence read |
| `src/slack/eventHelpers.ts` | `verifySlackSignature` (v0 basestring + replay window), `handleSlackEventIngest` (challenge, fan-out, dedup, health breadcrumb), `requiredMessageEventSubscription` (channel type → Slack app toggle), and the subscribe/query/debug flows with injected deps |
